# PRD 6.5 — Settings

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`, milestone 6 (table stakes).
Feature #86.

Requires PRD 5.2 (`prds/5.2-site-allowlist-blocking-settings.md`, branch
`docs/prd-5.2-site-allowlist`) merged: it introduces the settings surface this
PRD extends. From 5.2, main hosts a `settingsView` `WebContentsView` covering
the content area, positioned by `settingsBounds()` in
`packages/core/src/layout.ts`; the renderer bundle mounts a settings view on
`?view=settings` (alongside the existing `command-bar` overlay and default
sidebar `App` in `apps/ui/src/main.tsx`); the settings renderer draws a
section list; the `settings.open` command (accelerator `Cmd+,`) reveals it.
This PRD does not redefine any of that; it adds the general, profiles and
history section bodies, per-section commands, and a settings bridge.

Also requires PRD 6.1 (`prds/6.1-history.md`, branch `docs/prd-6.1-history`)
merged: it adds the history tables and helpers to
`apps/desktop/src/main/db.ts`, `HISTORY_RETENTION_MS` (90 days) and the
`history.clear()` bridge method in `packages/core/src/ipc.ts`. This PRD adds a
`history.stats()` method to that same `HistoryApi` and a history settings
section that reads it and clears history.

Nothing today lets a user change the default search engine, inspect or manage
profiles outside the space menu, or clear history from a stable surface. The
search engine is a hardcoded constant (`DEFAULT_SEARCH_ENGINE` in
`packages/core/src/resolve-input.ts`, with the command bar's search row label
`Search DuckDuckGo for "…"` baked into `packages/core/src/suggest.ts`). This
PRD makes the search engine a persisted choice from a fixed catalog, fills in
the general, profiles and history sections of the settings view, and adds the
settings bridge. The blocking section is PRD 5.2's; this PRD only lists it in
the registry.

## Deliverables

### 1. Settings sections registry (core)

- New pure module `packages/core/src/settings.ts`, Electron-free, exported
  from the `@zeo/core` barrel (`packages/core/src/index.ts`):

  ```ts
  type SettingsSectionId = "general" | "blocking" | "profiles" | "history";
  interface SettingsSection { id: SettingsSectionId; title: string }
  const SETTINGS_SECTIONS: readonly SettingsSection[];
  /** The section after `id` in registry order; unchanged at the last one. */
  function nextSection(id: SettingsSectionId): SettingsSectionId;
  /** The section before `id` in registry order; unchanged at the first. */
  function prevSection(id: SettingsSectionId): SettingsSectionId;
  ```

- `SETTINGS_SECTIONS` order is fixed and total: `general` ("General"),
  `blocking` ("Blocking"), `profiles` ("Profiles"), `history` ("History").
  `nextSection`/`prevSection` are pure index math over this array, clamped at
  the ends (no wrap): `nextSection("history") === "history"` and
  `prevSection("general") === "general"`. They are the single source of the
  section order for both the renderer and the keyboard navigation.
- The settings renderer (from PRD 5.2) draws one row per entry in
  `SETTINGS_SECTIONS` order, each with `data-testid="settings-section-<id>"`
  (e.g. `settings-section-general`). Exactly one section is the selected
  section; its row carries a `--selected` modifier class and the section's
  body is the one shown.
- Keyboard navigation within the section list: `ArrowDown` highlights
  `nextSection(current)`, `ArrowUp` highlights `prevSection(current)`, and
  `Enter` selects the highlighted section (shows its body). Highlight is
  renderer-local; the selected section is the pushed state below.
- Opening a specific section: the settings-view state main pushes to the
  `settingsView` renderer carries `section: SettingsSectionId` (an extension
  of the state PRD 5.2 already pushes for its section list, not a new
  channel). The section-open commands in §7 set this field; on receiving a
  new `section`, the renderer selects and highlights that section. When main
  has pushed no explicit section for the current open, the renderer selects
  `general`.
- Unit tests: `SETTINGS_SECTIONS` has the four ids in the order above with
  their titles; `nextSection`/`prevSection` walk the order and clamp at both
  ends.

### 2. General section — default search engine (core, db, ui)

- Fixed search-engine catalog in core, pure, in `packages/core/src/settings.ts`
  (exported from the barrel):

  ```ts
  type SearchEngineId =
    | "duckduckgo" | "google" | "bing" | "brave" | "startpage";
  interface SearchEngine { id: SearchEngineId; name: string; urlTemplate: string }
  const SEARCH_ENGINES: readonly SearchEngine[];
  const DEFAULT_SEARCH_ENGINE_ID: SearchEngineId; // "duckduckgo"
  /** The catalog entry for `id`, or undefined for an id not in the catalog. */
  function searchEngine(id: string): SearchEngine | undefined;
  /** Builds a search URL: the engine's template + encodeURIComponent(query). */
  function searchUrl(id: SearchEngineId, query: string): string;
  ```

- `SEARCH_ENGINES` order and values are fixed. Each `urlTemplate` is a query
  prefix a URL-encoded query is appended to (matching the existing
  `DEFAULT_SEARCH_ENGINE + encodeURIComponent(trimmed)` construction), so
  `searchUrl(id, q)` returns `urlTemplate + encodeURIComponent(q)`:

  | id | name | urlTemplate |
  |---|---|---|
  | `duckduckgo` | DuckDuckGo | `https://duckduckgo.com/?q=` |
  | `google` | Google | `https://www.google.com/search?q=` |
  | `bing` | Bing | `https://www.bing.com/search?q=` |
  | `brave` | Brave | `https://search.brave.com/search?q=` |
  | `startpage` | Startpage | `https://www.startpage.com/sp/search?query=` |

  `DEFAULT_SEARCH_ENGINE_ID` is `"duckduckgo"`, whose template equals today's
  `DEFAULT_SEARCH_ENGINE`, so behavior with no stored choice is unchanged.
- Persistence: a new `meta` column `searchEngine TEXT NOT NULL DEFAULT
  'duckduckgo'` (schema version 7). `MIGRATION_STEPS[7]` runs `ALTER TABLE
  meta ADD COLUMN searchEngine TEXT NOT NULL DEFAULT 'duckduckgo';` then
  `UPDATE meta SET schemaVersion = 7 WHERE id = 0;`, and the fresh `DDL`'s
  `meta` table carries the column, exactly like the `enabled` column added in
  the version-2 step. The column is read and written only by a narrow pair
  `readSearchEngine(): SearchEngineId` (selects `searchEngine` from the `id=0`
  row, returns `DEFAULT_SEARCH_ENGINE_ID` when the row or a value is absent or
  is not a catalog id) and `writeSearchEngine(id: SearchEngineId): void`
  (`UPDATE meta SET searchEngine = ? WHERE id = 0`), and is deliberately kept
  out of the `writeState`/`readState` full-state flush, mirroring
  `readBlockingEnabled`/`writeBlockingEnabled`.
- Threading the engine into core without making core stateful:
  - `resolveInput(text, engine)` gains a second parameter
    `engine: SearchEngineId`; the `search` target's url is `searchUrl(engine,
    trimmed)`. `DEFAULT_SEARCH_ENGINE` is removed in favor of the catalog; any
    remaining internal use resolves through `searchUrl(DEFAULT_SEARCH_ENGINE_ID,
    …)`.
  - `SuggestOptions` gains `searchEngine: SearchEngineId`. The row-0 search
    label reads ``Search ${searchEngine(options.searchEngine)!.name} for
    "${query.trim()}"`` (e.g. `Search Google for "x"`), replacing the
    hardcoded `DuckDuckGo` literal, and the row's url is `searchUrl(
    options.searchEngine, query.trim())`.
  - Main is the sole holder of the current value: it reads
    `readSearchEngine()` at startup into the in-memory `settings` state,
    passes `store`-independent `settings.searchEngine` to both `resolveInput`
    (in `submitCommandBar`) and `suggest` (in `recomputeSuggestions`), and no
    core module stores or defaults the engine on its own.
- General section UI: a radio group over `SEARCH_ENGINES` in catalog order,
  each control `data-testid="settings-search-engine-<id>"` (e.g.
  `settings-search-engine-google`), the current `settings.searchEngine`
  checked. Selecting one calls `settings.setSearchEngine(id)` (§6). No other
  general-section controls in this PRD.

### 3. Profiles section (ui, reusing the existing bridge)

- The profiles section lists every profile from `TabsState.profiles` (already
  broadcast: `Profile { id, name, createdAt }`) in the order it arrives, each
  showing the profile name, its id, and the number of spaces that reference it
  (counted from `TabsState.spaces` where `space.profileId === profile.id`).
- Controls, each row keyed by profile id:
  - Rename inline: an editable name field `data-testid="settings-profile-
    name-<id>"` and a confirm control `data-testid="settings-profile-
    rename-<id>"` calling the existing `profiles.rename(id, name)`. An empty or
    whitespace-only name is not submitted (the field reverts to the stored
    name); main's existing rename contract is otherwise unchanged.
  - Create: an input `data-testid="settings-profile-create-name"` and a button
    `data-testid="settings-profile-create"` calling the existing
    `profiles.create(name)`; an empty or whitespace-only name is not
    submitted.
  - Delete: a button `data-testid="settings-profile-delete-<id>"` calling the
    existing `profiles.delete(id)`. The button is disabled whenever the
    profile's space-usage count is greater than zero (any space uses it) and,
    for defense in depth, the underlying `store.deleteProfile` already rejects
    a delete of the default profile, an unknown id, or a still-referenced
    profile before any mutation, so a raced delete never wipes a live
    partition.
- The section reads only `TabsState` and calls only the existing `ProfilesApi`
  (`create`/`rename`/`delete`) and the `stateChange` broadcast for refresh; it
  adds no new profiles bridge method and no new channel.

### 4. Blocking section

- The registry lists `blocking` ("Blocking") between `general` and `profiles`.
  Its section body is defined by PRD 5.2; this PRD specifies nothing else
  about it.

### 5. History section (ui, one new bridge method)

- Retention display: the section shows that history is kept for 90 days,
  derived from `HISTORY_RETENTION_MS` (PRD 6.1), in an element
  `data-testid="settings-history-retention"`. No control changes retention.
- Visit summary: the section reads `history.stats()` (§6) and shows the entry
  and visit counts in an element `data-testid="settings-history-stats"`. It
  re-reads `stats()` after a successful clear.
- Clear browsing history: a button `data-testid="settings-history-clear"`.
  The first click enters an inline confirm step, revealing a confirm control
  `data-testid="settings-history-clear-confirm"`; only the confirm click calls
  `history.clear()` (PRD 6.1). A single click of the initial button never
  clears history. After the clear resolves, the summary reads zero entries and
  zero visits, and the confirm step is dismissed.

### 6. Settings bridge (core, main, preload)

- `packages/core/src/ipc.ts`:

  ```ts
  interface Settings { searchEngine: SearchEngineId }
  interface SettingsApi {
    get(): Promise<Settings>;
    setSearchEngine(id: SearchEngineId): Promise<void>;
  }
  interface ZeoApi { settings: SettingsApi }
  ```

  `TabsState` gains `settings: Settings`, so every settings change rides the
  existing `stateChange` broadcast and needs no separate update channel, the
  same way `blocking: BlockingState` does. Channel constants
  `settingsGet: "zeo:settings:get"` (no payload, response `Settings`) and
  `settingsSetSearchEngine: "zeo:settings:set-search-engine"` (payload
  `SearchEngineId`, response `void`). Main, preload, and renderer use these
  constants only. The preload exposes `window.zeo.settings` with the two
  methods.
- `settings.setSearchEngine(id)` contract, executed on the main thread in this
  order, mirroring PRD 5.1's `setEnabled`: (1) if `id` equals the current
  `settings.searchEngine`, resolve without side effects; (2) if `id` is not a
  catalog id (`searchEngine(id) === undefined`), reject with a `TypeError` and
  change nothing; (3) write the new value with `writeSearchEngine(id)`
  synchronously — on failure reject and change nothing (persisted value and
  in-memory state unchanged); (4) update the in-memory `settings.searchEngine`
  and `broadcast()`. `settings.get()` resolves the current in-memory
  `settings`.
- `HistoryApi` (PRD 6.1) gains one method:

  ```ts
  interface HistoryApi { stats(): Promise<{ entries: number; visits: number }> }
  ```

  Channel `historyStats: "zeo:history:stats"` (no payload, response
  `{ entries: number; visits: number }`). A new synchronous `db.ts` helper
  `historyStats(): { entries: number; visits: number }` returns `SELECT
  COUNT(*) FROM history_entries` as `entries` and `SELECT COUNT(*) FROM
  history_visits` as `visits`. History is not part of `TabsState` and is not
  broadcast; the settings section queries `stats()` on demand and after a
  clear.

### 7. Commands (core, main)

- `settings.open` (accelerator `Cmd+,`) exists from PRD 5.2 and is unchanged.
  Because commands take no arguments, opening a specific section needs one
  command per section. `CommandId` gains three ids, appended after the
  existing rows so registry order for existing ids is unchanged, each
  `menu: null` (not in the app menu) and always enabled:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `settings.openGeneral` | Open General Settings | `settings`, `general`, `search`, `engine`, `preferences` | (none) | `null` |
  | `settings.openProfiles` | Open Profile Settings | `settings`, `profiles`, `profile` | (none) | `null` |
  | `settings.openHistory` | Open History Settings | `settings`, `history`, `clear` | (none) | `null` |

  None takes an accelerator, avoiding the taken `Cmd+,` (5.2 settings), `Cmd+Y`
  (6.1 history), `Cmd+Shift+J` (6.2 downloads) and `Cmd+K` (commands mode).
- Each command's handler opens the settings view (as `settings.open` does) and
  sets the pushed `section` field to `general`, `profiles`, or `history`
  respectively (§1), so the view reveals with that section selected whether it
  was closed or already open on another section. Dispatched through
  `executeCommand` like every registry command; `isCommandEnabled` treats all
  three as always enabled.
- Unit tests: the registry uniqueness and enablement suites cover the three
  new ids; each is in the always-enabled set with `activeTab === null`; none
  contributes a menu entry (`menu: null`).

### 8. Tests

- Unit (`packages/core`):
  - `settings.ts`: `SETTINGS_SECTIONS` order and titles; `nextSection`/
    `prevSection` order and end-clamping; `SEARCH_ENGINES` ids, names and
    templates; `searchEngine(id)` returns the entry for a catalog id and
    `undefined` otherwise; `searchUrl(id, q)` equals `urlTemplate +
    encodeURIComponent(q)` and round-trips a query with spaces and `&`.
  - `resolve-input`: with a non-default engine (e.g. `google`), a non-URL
    input resolves to a `search` target whose url starts with
    `https://www.google.com/search?q=` and whose query is URL-encoded; a URL
    input still resolves to a `url` target regardless of engine.
  - `suggest`: with `searchEngine: "google"`, the row-0 search label reads
    `Search Google for "<query>"` and the row url is the Google search url;
    the default engine reproduces the DuckDuckGo label.
  - Command registry: the three new ids are unique, always enabled, and
    `menu: null`.
  - `db.test.ts`: migration 6 → 7 adds the `searchEngine` column defaulting to
    `'duckduckgo'` on an existing row; `readSearchEngine`/`writeSearchEngine`
    round-trip a catalog id and `readSearchEngine` falls back to
    `duckduckgo` for a missing or non-catalog stored value; `historyStats()`
    returns the entry and visit counts and both are zero after `clearHistory`.
- e2e (`e2e/tests/settings.spec.ts`, loopback `http.createServer` fixture on
  an ephemeral port as in `blocking.spec.ts`, `ZEO_E2E=1`, offline, views
  located by testid, state read through `window.zeo`):
  - Open the settings view (`settings.open` / the section-open commands over
    the bridge); the four `settings-section-<id>` rows are present in registry
    order.
  - Switch sections by keyboard: from the general section, `ArrowDown` twice
    then `Enter` selects the profiles section; `ArrowUp` navigation returns
    toward general; the selected section's body is the one shown.
  - Pick Google in the general section (`settings-search-engine-google`), then
    open the command bar and type a non-URL query: the row-0 label reads
    `Search Google for "x"` and accepting it navigates the active tab to a url
    beginning `https://www.google.com/search?q=` (assert the tab url only, no
    network).
  - Relaunch with the same `--user-data-dir`: `settings.get()` still reports
    `searchEngine: "google"` and the command bar's search row still names
    Google.
  - `settings.setSearchEngine("not-an-engine")` over the bridge rejects with a
    `TypeError` and `settings.get()` still reports the prior engine (the
    unknown-id failure path changes nothing).
  - Profiles section: `settings-profile-create` with a name creates a profile
    that appears in the list; `settings-profile-rename-<id>` renames it and the
    new name is reflected in `TabsState`. With a space pointed at that profile
    (`spaces.setProfile`), its `settings-profile-delete-<id>` control is
    disabled and a `profiles.delete(id)` bridge call for it rejects, leaving it
    in `TabsState.profiles`; once no space uses it, the delete succeeds.
  - History section: `settings-history-retention` shows the 90-day retention
    and `settings-history-stats` reflects the current entry and visit counts; a
    single click of `settings-history-clear` does not clear history; the clear
    only happens after `settings-history-clear-confirm`, after which
    `history.stats()` and `settings-history-stats` report zero entries and zero
    visits.

## Constraints

- `packages/core` stays Electron-free and holds the sections registry, the
  search-engine catalog, the `Settings`/`SettingsApi` types, the channel
  constants, the command ids, and the `resolveInput`/`suggest` threading. All
  SQL — the `searchEngine` column, its migration step and read/write helpers,
  and `historyStats()` — stays in `apps/desktop/src/main/db.ts`.
- Extend PRD 5.2's settings view; do not redefine the `settingsView`
  `WebContentsView`, `settingsBounds()`, the `?view=settings` mount, the
  section list plumbing, or the `settings.open` command. This PRD adds only the
  general/profiles/history section bodies, the three section-open commands, the
  search engine, and the settings bridge.
- Schema version 7 assumes the versions already claimed by open PRDs — 3
  (5.2), 4 (6.1), 5 (6.2), and 6 (a lower-numbered Epic-6 PRD) — are on `main`
  first. If this PRD lands before a lower-numbered PRD,
  take the next free version at rebase and renumber the migration step so
  `SCHEMA_VERSION` equals `main`'s value plus one.
- No theme, no keybinding editor, no sync. No new profiles bridge method (reuse
  `create`/`rename`/`delete`); the only new bridge surface is `SettingsApi` and
  `HistoryApi.stats()`.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged; CI stays offline-deterministic (no test depends on the
  network).
- Version bump to 0.0.20 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: the settings view lists General, Blocking, Profiles and
  History and is navigable by keyboard; choosing a search engine changes the
  command bar's search row label and where a search navigates, and the choice
  survives a relaunch; profiles can be created and renamed and a profile a
  space still uses cannot be deleted; clearing history requires a confirm click
  and empties the visit summary.
- CI green on the merge request branch.
