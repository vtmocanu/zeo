# PRD 7.2 — Quick-browse window

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`, milestone 7 ("Split view and a
lightweight quick-browse window"). Feature (epic 7) #87.

A quick-browse window is a **throwaway** surface for a link opened from another
application through the macOS default-browser handoff (the `open-url` event). It
is out of scope for this PRD to handle `window.open` originating inside a space.
The link renders in a small, minimal window that is **not part of any space** and
is **never persisted**; the user either **promotes** it into a space — where it
becomes a normal tab in the chosen space, in the profile that space uses — or
**dismisses** it with Escape.

Two decisions this PRD makes and states up front, because the rest of the
contract depends on them:

- **At most one quick-browse window exists at a time** (a singleton). When a
  second external link arrives while one is already open, the existing window's
  URL is **replaced** in place (its page view navigates); a second window is never
  created.
- **The page renders in a dedicated ephemeral, in-memory session** — an Electron
  session partition named *without* the `persist:` prefix, in deliberate contrast
  to the space tab views, which use `partition: "persist:" +
  store.spaceProfileId(spaceId)` (`apps/desktop/src/main/index.ts:685`). The
  rejected alternative — rendering in the last active space's profile session —
  would let a link received from an untrusted application read and write that
  profile's cookies and storage. **Privacy consequence:** a quick-browse page is
  fully isolated in both directions — it cannot read any space profile's
  cookies/logins, and, because the session is in-memory, it writes nothing to
  disk; the trade-off is that such a link opens logged-out. On **promote** the URL
  is loaded afresh into the target space's `persist:` session (a new tab and view),
  so the promoted tab uses that profile's cookies from then on and does **not**
  inherit the ephemeral session's cookies.

Zeo already persists user settings through a narrow `meta`-column contract (the
`enabled` blocking flag and the `searchEngine` choice PRD 6.5 added), read and
written by dedicated helpers and deliberately kept **outside** the pure-core
`MetaRow`/`PersistedState` codec and the full-state `writeState` flush. This PRD
adds one persisted setting — a toggle — the same way; the quick-browse *window
state* above is a separate concern that is never persisted at all.

## Deliverables

### 1. Core model — `packages/core/src/quick-browse.ts`

- New pure module, Electron-free, exported from the barrel
  (`packages/core/src/index.ts`):

  ```ts
  export interface QuickBrowse {
    url: string;
    title: string;
  }
  /** `null` means no quick-browse window is open (the singleton is closed). */
  export type QuickBrowseState = QuickBrowse | null;
  ```

- Pure transitions, each returning a new value with the input never mutated (the
  convention every existing `packages/core` reducer follows). The title fallback
  reuses `titleForUrl` (`packages/core/src/tab-title.ts`, the port-less hostname
  or the raw string, already barrel-exported and used by the tab views):

  ```ts
  export function openQuickBrowse(url: string): QuickBrowse;
  export function replaceQuickBrowseUrl(state: QuickBrowseState, url: string): QuickBrowse;
  export function setQuickBrowseUrl(state: QuickBrowseState, url: string): QuickBrowse;
  export function setQuickBrowseTitle(
    state: QuickBrowseState,
    url: string,
    title: string,
  ): QuickBrowseState;
  export function promoteQuickBrowse(state: QuickBrowseState): QuickBrowse;
  export function dismissQuickBrowse(state: QuickBrowseState): null;
  ```

  - `openQuickBrowse(url)` returns `{ url, title: titleForUrl(url) }`. It ignores
    any prior state — there is only ever one window, so opening is always a fresh
    single entry. Main calls this on the first external link (no window open yet).
  - `replaceQuickBrowseUrl(state, url)` has the precondition that `state` is
    **non-null** — a replace only happens while a window is already open — and
    **throws** when `state` is `null`. It returns `{ url, title: titleForUrl(url)
    }`: the title is **reset** to the new URL's fallback, since the previous title
    belonged to the previous page. Main calls this for a second external link that
    arrives while a window is open.
  - `setQuickBrowseUrl(state, url)` is live-URL tracking for a navigation *inside*
    the quick-browse page (a link click, a cross-document or same-document
    navigation). It updates `url`, and while no real page title is known re-derives
    the `titleForUrl` fallback, so `state.url` always names the page the user is
    actually on — this is what promote and open-in-new-tab capture. Throws when
    `state` is `null` (there is no page to have navigated).
  - `setQuickBrowseTitle(state, url, title)` updates `title` **only** when
    `state !== null && state.url === url`; a title event that raced a navigation to
    a different URL (or arriving after dismissal) is dropped, returning the input
    state unchanged in value.
  - `promoteQuickBrowse(state)` returns the current `QuickBrowse` entry (the URL
    and title to hand to the target space) and **throws** when `state` is `null`.
    Promotion's *state* transition is then exactly `dismissQuickBrowse` (the window
    goes away); creating the tab in a space is a main-process side effect (§6), not
    part of the pure model. This keeps "promote" a distinct, unit-testable
    transition.
  - `dismissQuickBrowse(state)` returns `null` unconditionally (idempotent when
    already `null`).

- **Never persisted:** no `quick-browse` state — neither `QuickBrowse` nor the
  fact that a window is open — is written to disk or carried into `PersistedState`.

- Unit tests (`packages/core/src/quick-browse.test.ts`) cover **every** transition:
  `openQuickBrowse` builds url + fallback title; `replaceQuickBrowseUrl` updates
  the url and resets the title from an open state and throws from `null`;
  `setQuickBrowseUrl` tracks a new url (and re-derives the fallback title) and
  throws from `null`; `setQuickBrowseTitle` updates on a url match and is a no-op on
  a mismatch and on `null`; `promoteQuickBrowse` returns the entry and throws from
  `null`; `dismissQuickBrowse` returns `null` from both an open state and `null`;
  and every transition leaves its input object unmodified.

### 2. Core layout — `packages/core/src/layout.ts`

- Add the fixed geometry as pure constants and one pure function, mirroring the
  existing `settingsBounds` (`packages/core/src/layout.ts:50`):

  ```ts
  export const QUICK_BROWSE_WIDTH = 480;
  export const QUICK_BROWSE_HEIGHT = 640;
  /** Height of the quick-browse chrome bar above the page view. */
  export const QUICK_BROWSE_CHROME_HEIGHT = 44;
  /**
   * The quick-browse page WebContentsView's rectangle WITHIN the quick-browse
   * window's content area: full width, starting below the chrome bar, filling the
   * remaining height. Floored at 0 so a window shorter than the chrome bar never
   * yields a negative height.
   */
  export function quickBrowsePageBounds(
    contentWidth: number,
    contentHeight: number,
  ): { x: number; y: number; width: number; height: number };
  ```

  `quickBrowsePageBounds` returns `{ x: 0, y: QUICK_BROWSE_CHROME_HEIGHT, width:
  contentWidth, height: Math.max(0, contentHeight - QUICK_BROWSE_CHROME_HEIGHT) }`.
  The window's on-screen *placement* (which display, centered) is a main-side
  concern (§6) because it needs Electron's `screen`, which `packages/core` may not
  import.

- Barrel-export the constants and `quickBrowsePageBounds`. Unit tests
  (`packages/core/src/layout.test.ts`) cover a normal case and the too-short
  window (height floored at 0).

### 3. Bridge — `packages/core/src/ipc.ts` + preload

- `TabsState` gains `quickBrowse: QuickBrowse | null`, attached by main to every
  broadcast snapshot and riding the existing `IPC.stateChange` channel — **this is
  the quick-browse event stream; no new event channel is added** — exactly as
  `blocking` and `settings` ride it today (`packages/core/src/ipc.ts:63-69`;
  `fullSnapshot()` at `apps/desktop/src/main/index.ts:301-310`). `null` when no
  window is open.

- `QuickBrowseApi`, added to `ZeoApi` as `quickBrowse`, acting on the single
  quick-browse window:

  ```ts
  export interface QuickBrowseApi {
    /** The current quick-browse entry, or null when no window is open. */
    state(): Promise<QuickBrowse | null>;
    /** Promote the current link into the ACTIVE space, then tear the window down. */
    promote(): Promise<void>;
    /** Throw the current link away and tear the window down. */
    dismiss(): Promise<void>;
  }
  ```

- Channel constants added to `IPC`, following the `zeo:<domain>:<verb-kebab>`
  naming every existing entry uses:

  | constant | channel | request | response |
  |---|---|---|---|
  | `quickBrowseState` | `zeo:quick-browse:state` | none | `QuickBrowse \| null` |
  | `quickBrowsePromote` | `zeo:quick-browse:promote` | none | `void` |
  | `quickBrowseDismiss` | `zeo:quick-browse:dismiss` | none | `void` |

  Promote-to-a-chosen-space and open-in-a-new-tab are reached through the existing
  `window.zeo.commands.run(id)` bridge (§4), not new `QuickBrowseApi` methods, so
  the choose-a-space flow goes through the command bar rather than a bridge
  argument.

- `TabsState` also gains `isDefaultBrowser: boolean`, attached by main from
  `app.isDefaultProtocolClient("http")` — informational, non-persisted OS state,
  like `settingsOpen`, not a persisted setting — so the General-settings
  default-browser button (§7) can label itself. It rides the same `stateChange`
  broadcast (no new channel); main re-reads it and re-broadcasts after
  `browser.setDefault` runs (§6) so the label refreshes.

- The settings bridge is extended (§8): `Settings` gains `quickBrowseExternal:
  boolean`; `SettingsApi` gains `setQuickBrowseExternal(enabled: boolean):
  Promise<void>`; channel `settingsSetQuickBrowseExternal:
  "zeo:settings:set-quick-browse-external"` (payload `boolean`, response `void`).

- Preload (`apps/desktop/src/preload/index.ts`) exposes `window.zeo.quickBrowse`
  and `window.zeo.settings.setQuickBrowseExternal` via
  `contextBridge.exposeInMainWorld("zeo", api)`, matching every other domain, and
  never leaks `ipcRenderer`. Main, preload, and renderer use the `IPC` constants
  only — no inline channel strings.

### 4. Commands — `packages/core/src/commands.ts` + `packages/core/src/command-bar.ts`

- Four new registry rows, appended after the existing rows so registry order for
  prior ids is unchanged, each `menu: null` and `accelerator: null`:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `quickBrowse.promote` | Promote to Current Space | `promote`, `quick`, `browse`, `space`, `keep` | `null` | `null` |
  | `quickBrowse.promoteToSpace` | Promote to Space… | `promote`, `quick`, `browse`, `space`, `move` | `null` | `null` |
  | `quickBrowse.dismiss` | Dismiss Quick-Browse | `dismiss`, `quick`, `browse`, `close`, `discard` | `null` | `null` |
  | `quickBrowse.openInTab` | Open Link in New Tab | `open`, `tab`, `quick`, `browse`, `link` | `null` | `null` |

  Their effects:

  - `quickBrowse.promote` — create a new tab loading the current quick-browse URL
    in the **active** space, activate it, and tear the quick-browse window down
    (§6); focus returns to the main window.
  - `quickBrowse.promoteToSpace` — open the command bar in the new `promote` mode
    (below) so the user picks a target space; accepting a space row promotes the
    URL into that space.
  - `quickBrowse.dismiss` — tear the window down; no tab is created.
  - `quickBrowse.openInTab` — create a new tab loading the URL in the **active**
    space **while leaving the quick-browse window open**. This is the deliberate
    distinction from `quickBrowse.promote`: it grabs the link into normal browsing
    without giving up the throwaway window (whereas promote adopts the link and
    closes the window).

- `CommandId` gains these four ids **and** `browser.setDefault` (§6) — five new ids
  in total. `CommandContext` gains `quickBrowseOpen: boolean` alongside the existing
  `settingsOpen` (`packages/core/src/commands.ts:57-67`). `isCommandEnabled` adds a
  `case` for each new id: the four `quickBrowse.*` ids return `true` only when
  `context.quickBrowseOpen` (and `false` otherwise), and `browser.setDefault` is
  always enabled. Every new id needs its own `case` because `isCommandEnabled` ends
  in an exhaustive `default: const exhaustive: never = id`
  (`packages/core/src/commands.ts:156-158`) — a `CommandId` with no `case` fails
  `pnpm typecheck` (an acceptance criterion), so "no other rule changes" means no
  change to the enablement of *existing* commands, not that the switch is left
  untouched. `commandContextOf()` (`apps/desktop/src/main/index.ts:969-989`)
  populates `quickBrowseOpen` from whether the quick-browse window exists, and
  `refreshCommandState()` re-ranks the rows as it does for every command. Dispatch
  runs through the single checked boundary `executeCommand`
  (`apps/desktop/src/main/index.ts:1099-1109`), which throws for a command disabled
  in context.

- **Keys and accelerator collisions.** All four commands carry `accelerator: null`
  in the registry; the quick-browse window's keys are **window-local**: `Escape` →
  dismiss, `Return` → promote, `Cmd+Return` (`CmdOrCtrl+Return`) → promote-to-space,
  `Cmd+Shift+Return` (`CmdOrCtrl+Shift+Return`) → open-in-new-tab. Because the
  external page renders in a separate child `WebContentsView` (§6) that holds
  keyboard focus whenever the user interacts with it, a keydown listener in the
  chrome renderer alone would miss these keys while the page is focused — the
  settings view has no such focus-stealing child, so its in-renderer-Escape
  precedent (PRD 5.2 §5) does not transfer here. They are therefore handled in the
  **main process** via `webContents.on("before-input-event", …)` on **both** the
  quick-browse chrome view and its page view, dispatching the matching command
  through `executeCommand` (§6). This is a deliberate, window-scoped exception to the
  app's "menu accelerators, not `before-input-event`" convention (PRD 2.2; the
  `buildMenu` comment at `apps/desktop/src/main/index.ts:2317-2321`): that
  convention chose menu accelerators precisely because they fire app-wide, whereas
  these keys must be the opposite — window-local, never leaking `Escape`/`Return` to
  the main window — so `before-input-event` scoped to the quick-browse window's own
  two webContents is the right tool and touches no main-window accelerator. The
  registry `accelerator: null` mirrors `settings.close` (`packages/core/src/commands.ts:94`).
  The accelerators checked to confirm no collision, none of which uses `Return` or
  `Escape`:

  - Registry accelerators (`packages/core/src/commands.ts:76-99`): `CmdOrCtrl+T`,
    `CmdOrCtrl+W`, `CmdOrCtrl+Shift+P` (pin/unpin), `CmdOrCtrl+Shift+W`,
    `CmdOrCtrl+Shift+C`, `CmdOrCtrl+R`, `CmdOrCtrl+[`, `CmdOrCtrl+]`,
    `CmdOrCtrl+Shift+N`, `CmdOrCtrl+L`, `CmdOrCtrl+K`, `CmdOrCtrl+,`, `CmdOrCtrl+Y`.
  - Hidden application-menu accelerators (`apps/desktop/src/main/index.ts:2328,
    2366`): `CmdOrCtrl+Alt+1..9` (activate tab), `CmdOrCtrl+1..9` (activate space).
  - The `appMenu` and `editMenu` roles (`apps/desktop/src/main/index.ts:2391,
    2398`), which own `Cmd+Q`, `Cmd+C/V/X/A/Z`, etc.
  - Reserved by open PRDs: `Cmd+Shift+J` (downloads, PRD 6.2); `Cmd+=`, `Cmd+-`,
    `Cmd+0` (zoom, PRD 6.4).

  Because the quick-browse keys are window-local and none of them is an
  application-menu accelerator, they are delivered to the quick-browse renderer
  with no global conflict. The PRD states explicitly that the existing global
  application-menu accelerators (e.g. `Cmd+R`, `Cmd+W`, `Cmd+T`, `Cmd+L`) remain
  bound to the **main window's** context and keep acting on `store.activeTabId` and
  the active space regardless of which window has OS focus; the quick-browse window
  is not given, and does not remap, any global accelerator.

- **New command-bar mode.** `CommandBarMode` in `packages/core/src/command-bar.ts`
  gains `"promote"` (today it is `"navigate" | "new-tab" | "commands" |
  "history"`). In `promote` mode `suggest` (`packages/core/src/suggest.ts`) returns
  **only space rows**, drawn from the `catalog.spaces` the bar already carries
  (`packages/core/src/suggest.ts:283`; `buildCatalog` in main already supplies
  `spaces`), filtered by the query; there is no row-0 text action and no
  tab/command/history/archived rows — the `commands`-mode branch at
  `packages/core/src/suggest.ts:201` is the precedent for a mode with no row-0 text
  action. `promote` mode follows `commands` mode's submit/accept semantics: a
  free-text submit rejects (`submitCommandBar` throws for that mode,
  `apps/desktop/src/main/index.ts:1296`), and an accept with no row selected leaves
  the bar open (`acceptCommandBar` early-returns, `apps/desktop/src/main/index.ts:1442-1454`).
  `accept` of a space row runs the promote-into-that-space path in main (§6).

- Unit tests (`packages/core/src/commands.test.ts`): the four ids are unique,
  `menu: null`, and enabled only when `quickBrowseOpen` (disabled with
  `quickBrowseOpen: false`, including with `activeTab === null`); a `suggest` test
  asserts `promote` mode returns only space rows and no row-0 action.

### 5. Broadcast plumbing — `apps/desktop/src/main/index.ts`

`broadcast()` (`apps/desktop/src/main/index.ts:1706-1713`) and
`scheduleBlockingBroadcast()` (`apps/desktop/src/main/index.ts:317-330`) today push
`IPC.stateChange` to `win.webContents` and, while it exists,
`settingsView.webContents`. Both must **also** push to the quick-browse chrome
view's `webContents` while the quick-browse window exists, so the chrome renderer's
URL and title follow every change — the same pattern used for the settings view.
`fullSnapshot()` attaches `quickBrowse` (the in-memory `QuickBrowseState`) and
`isDefaultBrowser` (§3) to the snapshot alongside `blocking`/`settings`.

### 6. Main process — `apps/desktop/src/main/index.ts`

- **Default-browser registration (opt-in only).** A new registry command
  `browser.setDefault` — one more registry row appended after the four quick-browse
  rows (title "Set zeo as Default Browser", keywords `default`, `browser`, `open`,
  `links`; `accelerator: null`; `menu: null`), its `CommandId` and its
  always-enabled `isCommandEnabled` case added per §4 — whose handler calls
  `app.setAsDefaultProtocolClient("http")` and
  `app.setAsDefaultProtocolClient("https")`. It is **never** invoked at startup or
  unprompted. It is surfaced by a General-settings button (§7) that dispatches it
  via `window.zeo.commands.run("browser.setDefault")`; the button's label reflects
  `TabsState.isDefaultBrowser` (§3). After the handler runs, main re-reads
  `app.isDefaultProtocolClient("http")` into `isDefaultBrowser` and `broadcast()`s
  so the label refreshes; the field is also seeded at startup. Running it repeatedly
  is safe (idempotent). No such registration exists on `main` today — there is no
  `open-url` handler and no `setAsDefaultProtocolClient` call anywhere; the only
  `app.on(...)` registrations are `activate`, `window-all-closed`, and
  `before-quit` (`apps/desktop/src/main/index.ts:2593, 2602, 2610`). The PRD notes
  that full OS-level default-handler behavior additionally requires the macOS
  bundle to declare the `http`/`https` URL schemes (`CFBundleURLTypes` /
  `LSHandlerRank`), which is packaging configuration deferred to milestone 8;
  `setAsDefaultProtocolClient` and the `open-url` event still function for an
  unpackaged/dev run and for the e2e harness (§9).

- **The `open-url` event.** Register at module top level so it is bound before
  `app.whenReady()` resolves:

  ```ts
  app.on("open-url", (event, url) => {
    event.preventDefault();
    handleExternalLink(url);
  });
  ```

  `handleExternalLink(url)`:
  - ignores a URL whose `siteKeyForUrl(url)` is `null` (not `http:`/`https:`),
    logging it — the handoff is only for web links;
  - if the main window does not yet exist (`win === null`), first
    `createWindow(false)` so there is a window to fall back to (darwin keeps the
    process alive after `window-all-closed` with no window);
  - if `settings.quickBrowseExternal` is **on**, opens the quick-browse window with
    `url` when none is open (`openQuickBrowse`), or replaces the URL in the existing
    window when one is open (`replaceQuickBrowseUrl`, navigating its page view);
  - if the toggle is **off**, opens `url` as a normal new tab in the active space
    (`store.create` + activate), with no quick-browse window.

- **Cold launch.** A macOS `open-url` can be delivered before `whenReady()`
  finishes. URLs received before the main window is created and the persisted
  toggle is read are pushed onto a module-level queue and **drained in arrival
  order** at the end of the `whenReady` handler (`apps/desktop/src/main/index.ts:2404`
  onward), after `createWindow(...)` and after `settings` is seeded from
  `readQuickBrowseExternal()` (§8). Draining in order leaves the final state
  reflecting the last queued link (consistent with the singleton/replace rule).

- **Quick-browse window and views.** A small (`QUICK_BROWSE_WIDTH` ×
  `QUICK_BROWSE_HEIGHT`), frameless (`frame: false`) `BrowserWindow`, centered on
  the primary display via `screen.getPrimaryDisplay()`. Its top-level
  `webContents` loads the shared UI bundle with `?view=quick-browse` (the chrome),
  using the same preload and secure `webPreferences` as the sidebar, command-bar
  overlay, and settings view (`preload: ".../preload/index.cjs"`,
  `contextIsolation: true`, `sandbox: false`, `nodeIntegration: false` —
  `apps/desktop/src/main/index.ts:1938-1947, 1970-1977, 597-616`). The external
  page renders in a **child `WebContentsView`** added to the window's content view,
  positioned by `quickBrowsePageBounds` (§2) and repositioned on the window's
  `resize`, created on the **ephemeral session** (a `session.fromPartition` name
  without `persist:`) with the same tab-view web preferences —
  `nodeIntegrationInSubFrames: true` (`apps/desktop/src/main/index.ts:694`), so PRD
  5.3 cosmetic filtering still reaches child frames — and **no zeo preload** (it is
  untrusted web content, exactly like the space tab views, which "have no bridge
  and cannot dispatch", `apps/desktop/src/main/index.ts:2244`). The page view's
  `setWindowOpenHandler` **denies** new windows (a `window.open`/`target=_blank`
  from the page never spawns another window; a `_blank` link navigates in place),
  keeping quick-browse a single throwaway surface. The page view's `did-navigate`
  and `did-navigate-in-page` drive `setQuickBrowseUrl`, and `page-title-updated`
  drives `setQuickBrowseTitle`, so `quickBrowse.url`/`title` track the live page.

- **Focus.** On open, the quick-browse window is shown and focused. On replace (a
  second external link), the existing window is brought to the front and focused
  and its page view navigates. On dismiss, focus returns to the main window (its
  active tab view when present, else `win.webContents`). `promoteToSpace` moves
  focus to the main window's command-bar overlay to pick a space; `openInTab`
  creates a background tab in the active space and **leaves the quick-browse window
  focused**; `promote` tears the window down and focuses the main window on the new
  tab.

- **Content blocking.** The app blocker is attached to the ephemeral quick-browse
  session when the quick-browse window is created, gated on `blocking.enabled &&
  blocker` — the same condition the profile-session attach and the
  `IPC.profilesCreate` new-partition attach use (`apps/desktop/src/main/index.ts:2280-2282`).
  Note that `attachBlockerToAllSessions` iterates only `profileSessions()`
  (`apps/desktop/src/main/index.ts:363-367`), which does **not** include the
  ephemeral session; so in the startup cap-lost blocker swap
  (`apps/desktop/src/main/index.ts:2505-2513`) the implementer must **additionally**
  attach the newly-arrived blocker to the ephemeral session when a quick-browse
  window is open at that moment, rather than relying on `attachBlockerToAllSessions`
  to cover it. The installed
  bypass predicate is session-independent — it derives the host from the request
  URL and consults the live `allowlist` set (`installBypass`,
  `apps/desktop/src/main/index.ts:355-360`) — so the per-site allowlist ("Disable
  Blocking on This Site") applies to a quick-browse page with identical semantics.
  A quick-browse page's `webContents` is not registered in `webContentsToTab`, so a
  blocked request on it is counted as **unattributed** (`applyUnattributedBlock`),
  never mis-attributed to a real space tab.

- **Teardown ordering (dismiss, promote, and the quick-browse window's own
  `closed`), best-effort:**
  1. Remove the page `WebContentsView` from the window and `webContents.close()` it,
     guarded by an `isDestroyed()` check, matching the settings-view teardown at
     `apps/desktop/src/main/index.ts:2042-2045`.
  2. Close the quick-browse `BrowserWindow` (its chrome `webContents` with it).
  3. **Best-effort** clear the ephemeral session's storage and cache
     (`clearStorageData()` then `clearCache()`, matching the deleted-profile cleanup
     at `apps/desktop/src/main/index.ts:2300-2303`): awaited but non-fatal, any
     error logged, never blocking the dismissal. Because the session is in-memory,
     nothing was written to disk regardless, so this is defense-in-depth against a
     later unrelated link inheriting cookies within one app run; the "nothing
     survives relaunch" guarantee is structural.
  4. Set the in-memory `quickBrowse` to `null` and `broadcast()` (so
     `TabsState.quickBrowse` clears and the four `quickBrowse.*` commands become
     disabled).

  The view is destroyed **before** the session clear so no in-flight request can
  repopulate storage after it is cleared, and before the in-memory `quickBrowse` is
  nulled (step 4) so no late `did-navigate`/`page-title-updated` from the page can
  reach `setQuickBrowseUrl`/`setQuickBrowseTitle` after teardown — which is why
  `setQuickBrowseUrl` (§1) may safely throw on a `null` state.

- **Promote ordering and failure paths.** Capture the URL to promote with
  `promoteQuickBrowse(quickBrowse)`. For `promoteToSpace`, first
  `store.setActiveSpace(targetSpaceId)` (the space-switch pattern at
  `apps/desktop/src/main/index.ts:1390-1392`); for `promote`, the active space is
  the target. Then `store.create({ url })` in that space and activate it — the new
  tab's view is created on the target space's `persist:` profile partition via
  `createViewFor`'s `spaceProfileId` — and run the teardown above; `broadcast()`.
  - **If promotion targets a space that was deleted meanwhile** (the space picked
    in `promote` mode is no longer in `store.spaces()` when `accept` runs): a no-op
    that closes the command bar and leaves the quick-browse window open, so the URL
    stays promotable and nothing is lost.
  - **If the quick-browse window was dismissed while the picker was open**
    (`quickBrowse === null` at `accept` time): a no-op that closes the bar.
  - `quickBrowse.promote` (current space) always has a valid target, since at least
    one space always exists.

### 7. UI — `apps/ui`

### 8. Settings and persistence — `apps/desktop/src/main/db.ts`, `packages/core/src/persistence.ts`

- `Settings` (`packages/core/src/ipc.ts`) gains `quickBrowseExternal: boolean`,
  **default `true`** ("Open external links in quick-browse", on by default). It
  rides the `stateChange` broadcast on `TabsState.settings` like `searchEngine`,
  needing no separate change channel.

- Persistence follows PRD 6.5's `searchEngine` **helper** contract exactly — a
  db.ts-only `meta` column with dedicated read/write helpers, kept **out** of the
  pure-core `MetaRow`/`PersistedState` codec and the `writeState` full-state flush
  (the same way `enabled` and `searchEngine` are handled). Effective schema version
  `N` is main's `SCHEMA_VERSION` at rebase time (`packages/core/src/persistence.ts`;
  `5` today) **plus 1**, written illustratively as `6` below and substituted with
  the actually-allocated `N` everywhere at once (grep `SCHEMA_VERSION` live and add
  1). Note that the open PRD 6.4 (zoom) also illustratively claims schema version
  `6` for its `site_zoom` table; whichever of the two lands first takes `6` and the
  other takes the next free version at rebase — the same "next free version at
  rebase" rule PRD 6.5 used to reach `5`.

  ```sql
  ALTER TABLE meta ADD COLUMN quickBrowseExternal INTEGER NOT NULL DEFAULT 1;
  UPDATE meta SET schemaVersion = 6 WHERE id = 0;
  ```

  The `MIGRATION_STEPS[N]` step runs the two statements above; the fresh `DDL`'s
  `meta` table carries the `quickBrowseExternal` column too (so a brand-new
  database gets it, not only the migrate path); and `SCHEMA_VERSION`,
  `MIGRATION_STEPS[N]`, the fresh DDL, and the migration-runner tests all move to
  the one allocated `N` in lockstep.

- Helpers, kept outside `writeState`, mirroring
  `readSearchEngine`/`writeSearchEngine`:

  ```ts
  export function readQuickBrowseExternal(): boolean;
  export function writeQuickBrowseExternal(enabled: boolean): void;
  ```

  `readQuickBrowseExternal()` selects `quickBrowseExternal` from the `id = 0` row
  (mapping SQLite `0`/`1` to `boolean`) and returns `true` when the row or a value
  is absent. `writeQuickBrowseExternal(enabled)` runs `UPDATE meta SET
  quickBrowseExternal = ? WHERE id = 0`. Main seeds the in-memory `settings` slice
  from `readQuickBrowseExternal()` at startup alongside `readSearchEngine()`
  (`apps/desktop/src/main/index.ts:2449`).

- `settings.setQuickBrowseExternal(enabled)` runs on the main thread in this order,
  mirroring 6.5's `setSearchEngine` and 5.1's `setEnabled`: (1) if `enabled` equals
  the current value, resolve without side effects; (2) if `enabled` is not a
  boolean, reject with a `TypeError` and change nothing; (3) write it with
  `writeQuickBrowseExternal(enabled)` synchronously — on throw, reject with the
  persisted value and in-memory state unchanged and **no** `broadcast()`; (4) update
  the in-memory `settings.quickBrowseExternal` and `broadcast()`. `settings.get()`
  resolves the current in-memory `settings` (now including `quickBrowseExternal`).

## Constraints

- `packages/core` stays Electron-free (lint-enforced): `quick-browse.ts` and the
  new `layout.ts` additions are pure functions and types only; every
  `BrowserWindow`/`WebContentsView`/`session`/`app`/`screen` call lives in
  `apps/desktop/src/main`.
- Application state lives in the main process as the single source of truth; the
  quick-browse chrome renderer subscribes and dispatches over the bridge and never
  forks state.
- TypeScript strict mode; no `any` without a stated reason in review.
- Keep `apps/ui` components thin; reuse the existing renderer bundle
  (`?view=quick-browse`) rather than a separate app.
- Do not create or modify anything under `.github/workflows/`; root script names
  stay unchanged; CI stays offline-deterministic (no test depends on the network).
- Version bump: bump the root `package.json` **patch** to the next free version at
  rebase time and add a dated `CHANGELOG.md` (Keep a Changelog) section; the number
  is **not** fixed in this PRD.
