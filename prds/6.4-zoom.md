# PRD 6.4 — Zoom

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. `SCHEMA_VERSION` is 2 on
main, in `packages/core/src/persistence.ts`; all SQL lives in
`apps/desktop/src/main/db.ts` (`DDL`, `MIGRATION_STEPS` keyed by the version
each step produces, `migrate()`, the singleton `meta` row `id=0`).

This PRD claims schema version 6. PRDs 5.2 (site allowlist), 6.1 (history),
and 6.2 (downloads) are open on branches not reachable from this clone and
already claim versions 3, 4, and 5 respectively. If this PRD lands before a
lower-numbered one of those, the implementer takes the next free version at
rebase so `SCHEMA_VERSION` ends up one more than main's value at that time;
every version number in this PRD is written assuming no such collision.

Today every tab renders at the browser's default zoom with no way to change
it. This PRD adds per-site zoom: one factor per host, shared by every tab on
that host, set from the keyboard or the sidebar, snapped to the Chromium
zoom ladder, and persisted across relaunch. It reuses two contracts PRD 5.2
introduces — `siteKeyForUrl(url)` and `CommandContext.activeTab.siteHost` —
and restates each below with an add-if-absent clause: if the referenced
module or field does not exist at implementation time, the implementer adds
it with the stated contract rather than blocking on PRD 5.2. No settings
section is added by this PRD.

## Deliverables

### 1. Core `packages/core/src/zoom.ts`

- `ZOOM_FACTORS` is the Chromium zoom ladder, exactly:

  ```ts
  export const ZOOM_FACTORS: readonly number[] = [
    0.25, 0.33, 0.5, 0.67, 0.75, 0.8, 0.9, 1.0, 1.1, 1.25, 1.5, 1.75,
    2.0, 2.5, 3.0, 4.0, 5.0,
  ];
  export const DEFAULT_ZOOM_FACTOR = 1.0;
  ```

- Pure `zoomIn(factor)` returns the next rung strictly above `factor`,
  clamped at the ladder's top (`5.0`); when `factor` sits between two rungs
  or below the bottom rung, it snaps UP to the nearest rung on or above
  `factor` first (so `zoomIn(0.6)` is `0.67`, not `0.75`). Pure
  `zoomOut(factor)` is the mirror: the next rung strictly below `factor`,
  clamped at the bottom (`0.25`), snapping DOWN to the nearest rung on or
  below `factor` when off-ladder. Both are total functions: any finite
  input, on-ladder or not, returns a value on `ZOOM_FACTORS`.
- `formatZoomPercent(factor)` returns `Math.round(factor * 100) + "%"`
  (`1.5` → `"150%"`, `0.9` → `"90%"`).
- `siteKeyForUrl(url)` (PRD 5.2; add-if-absent: if `packages/core` has no
  such export at implementation time, this PRD adds it with this contract)
  returns the lowercased hostname — WHATWG `URL.hostname`, WITHOUT the
  port — for an `http:`/`https:` URL, and `null` for any other URL (including
  `about:`, `file:`, `chrome:`, and unparseable strings). The port is
  deliberately excluded, so two origins that differ only by port (e.g. a
  loopback fixture on any ephemeral port) share one host key and one zoom
  factor. Zoom keys off this function exclusively; see §2.
- `ZoomState { byHost: Record<string, number> }` is added to `TabsState` as
  `TabsState.zoom`:

  ```ts
  export interface ZoomState {
    byHost: Record<string, number>;
  }
  ```

  Pure reducers, both returning a new `ZoomState` (the input is never
  mutated, matching the existing reducers in `packages/core`):

  ```ts
  export function setHostZoom(
    state: ZoomState,
    host: string,
    factor: number,
  ): ZoomState;
  export function clearHostZoom(state: ZoomState, host: string): ZoomState;
  ```

  `setHostZoom` sets `byHost[host]` to `factor`, except that a `factor` of
  exactly `1.0` REMOVES the `host` key instead of storing `1.0` — the
  default factor is represented by absence, so `setHostZoom(state, host,
  1.0)` behaves exactly like `clearHostZoom(state, host)`. `clearHostZoom`
  removes the key unconditionally; removing an absent key returns a state
  equal in value to the input (a fresh object, same contents).
- Unit tests: `zoomIn`/`zoomOut` step correctly at both the top and bottom
  clamp; `zoomIn`/`zoomOut` snap up/down respectively from an off-ladder
  value in the interior and from below the bottom / above the top rung;
  `formatZoomPercent` on a representative set including a non-terminating
  decimal; `setHostZoom` adds and overwrites a host entry; `setHostZoom`
  with `1.0` removes an existing entry and is a no-op on an absent one;
  `clearHostZoom` removes an existing entry and is a no-op on an absent one;
  both reducers leave the input object unmodified.

### 2. Per-site semantics

- Zoom is keyed by host via `siteKeyForUrl`: one stored factor per host,
  shared by every tab whose current URL resolves to that host, across every
  space and every profile — zoom is not scoped to a profile's session
  partition.
- A tab applies its host's factor at two points: on every main-frame
  `did-navigate`, and immediately when the `byHost` map's entry for that
  tab's current host changes (a zoom command run from another tab on the
  same host takes effect on this tab without a navigation).
- A host with no `byHost` entry renders at `1.0`. Any tab whose current URL
  is not `http:`/`https:` (`siteKeyForUrl` returns `null`) always renders at
  `1.0`, is never given a `byHost` entry, and the three zoom commands (§6)
  are disabled while it is active.

### 3. Main process (`apps/desktop/src/main/index.ts`)

- `applyZoom(tabId, factor)` is the single write path: every place that
  changes a tab's on-screen zoom or its persisted host factor calls this
  function, and nothing else calls `webContents.setZoomFactor` directly.
  Given a `tabId`, it resolves the tab's `WebContentsView`, resolves its
  current host through `siteKeyForUrl`, and:
  - when the host is `null` (non-http(s)), it sets the view's zoom factor to
    `1.0` and touches no persisted state;
  - otherwise it calls `setHostZoom` on the in-memory `TabsState.zoom`,
    persists the change through `upsertSiteZoom`/`deleteSiteZoom` (§4),
    applies `webContents.setZoomFactor(factor)` to every open tab currently
    on that host (not just `tabId`), and broadcasts the updated `TabsState`.
  `applyZoom` is idempotent: calling it twice with the same host's current
  factor changes nothing further and broadcasts a `TabsState` equal in
  value to the last one.
- `createViewFor` applies the tab's host factor with
  `webContents.setZoomFactor` once the first navigation commits (not at
  view construction, before there is a committed host), and again on every
  later `did-navigate`, reading the then-current host's factor from
  `TabsState.zoom.byHost` (or `1.0` when absent or non-http(s)). This is the
  ordering: first-commit, then every subsequent `did-navigate`; a view
  never sits at the wrong factor between those two events because it starts
  at Chromium's own default (`1.0`) until the first commit applies the
  stored value.
- `webContents.setVisualZoomLevelLimits(1, 1)` is called on every tab view
  alongside the above, disabling pinch-to-zoom so the visual viewport never
  drifts from the applied factor.
- `webContents.on("zoom-changed", ...)` (fired by Ctrl+scroll-wheel) reads
  the requested direction and factor, snaps the result onto `ZOOM_FACTORS`
  with `zoomIn`/`zoomOut` as appropriate, and routes it through
  `applyZoom` for that tab's host — a wheel zoom is indistinguishable from
  a command-driven zoom once it reaches `applyZoom`.
- Failure path: `applyZoom` on a `tabId` with no live view, or on a tab
  whose view is already destroyed, is a no-op that changes no state and
  broadcasts nothing.

### 4. Persistence (`apps/desktop/src/main/db.ts`)

- Schema version 6 (subject to the rebase caveat in Context). A
  `MIGRATION_STEPS` step keyed at `6` creates the table and bumps
  `meta.schemaVersion`:

  ```sql
  CREATE TABLE site_zoom (
    host TEXT PRIMARY KEY,
    factor REAL NOT NULL,
    updatedAt INTEGER NOT NULL
  );
  UPDATE meta SET schemaVersion = 6 WHERE id = 0;
  ```

- Helpers, kept OUTSIDE `writeState` — the same precedent
  `readBlockingEnabled`/`writeBlockingEnabled` set for the blocking `enabled`
  flag:

  ```ts
  export function readSiteZoom(): Record<string, number>;
  export function upsertSiteZoom(
    host: string,
    factor: number,
    updatedAt: number,
  ): void;
  export function deleteSiteZoom(host: string): void;
  ```

  `readSiteZoom()` returns the full host-to-factor map from `site_zoom`.
  `upsertSiteZoom` inserts or replaces the row for `host`. `deleteSiteZoom`
  removes the row for `host`, a no-op when absent. The map is loaded via
  `readSiteZoom()` before the first window is created and seeds
  `TabsState.zoom.byHost`; every later change goes through `applyZoom`
  (§3), which calls `upsertSiteZoom` for a non-default factor and
  `deleteSiteZoom` when the reducer removes the host entry (the `1.0`-means-
  absent rule from §1 applies here too: `site_zoom` never carries a row for
  a host at the default factor).
- Migration-runner test covers 5 → 6: a version-5 database gains the
  `site_zoom` table with no rows, `meta.schemaVersion` reads `6`, and a
  version-2 (pre-5.2) database run through the full chain ends at 6 with
  the table present.

### 5. Bridge (`packages/core/src/ipc.ts` + preload)

- `ZoomApi`, added to `ZeoApi` as `zoom`, acting on the ACTIVE tab of the
  active space:

  ```ts
  export interface ZoomApi {
    zoomIn(): Promise<void>;
    zoomOut(): Promise<void>;
    reset(): Promise<void>;
    state(): Promise<ZoomState>;
  }
  ```

- Channel constants added to `IPC`, following the `zeo:<domain>:<verb-
  kebab>` naming every existing entry uses:

  | constant | channel | request | response |
  |---|---|---|---|
  | `zoomIn` | `zeo:zoom:in` | none | `void` |
  | `zoomOut` | `zeo:zoom:out` | none | `void` |
  | `zoomReset` | `zeo:zoom:reset` | none | `void` |
  | `zoomState` | `zeo:zoom:state` | none | `ZoomState` |

  No dedicated change channel: `ZoomState` rides `TabsState.zoom` on the
  existing `IPC.stateChange` broadcast, exactly as `BlockingState` does.
- `zoomIn`, `zoomOut`, and `reset` share one failure path: each REJECTS and
  changes nothing when there is no active tab, or when the active tab's
  current URL yields `siteKeyForUrl(url) === null` (non-http(s)). `reset`
  on a host with no `byHost` entry (already at `1.0`) resolves without
  side effects. On success, `zoomIn`/`zoomOut` call `applyZoom` with the
  ladder-stepped factor for the active tab's host; `reset` calls
  `applyZoom` with `1.0`, which removes the host's persisted entry per the
  §1 rule.
- Preload (`apps/desktop/src/preload/index.ts`) exposes `window.zeo.zoom`
  via `contextBridge.exposeInMainWorld("zeo", api)`, matching every other
  domain. Main, preload, and renderer use the four `IPC` constants above
  only — no inline channel strings.

### 6. Commands (`packages/core/src/commands.ts`, `menu: "view"`)

- Three new registry rows, appended after the existing rows so registry
  order for prior ids is unchanged:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `zoom.in` | Zoom In | `zoom`, `in`, `larger`, `bigger` | `CmdOrCtrl+=` | view |
  | `zoom.out` | Zoom Out | `zoom`, `out`, `smaller` | `CmdOrCtrl+-` | view |
  | `zoom.reset` | Actual Size | `zoom`, `reset`, `actual`, `default`, `100` | `CmdOrCtrl+0` | view |

  All three accelerators are unassigned in `COMMANDS` on main today, and
  none collide with the accelerators the open PRDs reserve (`Cmd+,` settings
  in PRD 5.2, `Cmd+Y` history in PRD 6.1, `Cmd+Shift+J` downloads in
  PRD 6.2).
- `CommandId` gains `"zoom.in" | "zoom.out" | "zoom.reset"`.
- Enablement, read from `CommandContext.activeTab.siteHost` (PRD 5.2;
  add-if-absent: if `CommandContext.activeTab` has no `siteHost` field at
  implementation time, this PRD adds it with this contract — `siteHost` is
  exactly `siteKeyForUrl(activeTab.url)`: the same port-less hostname §1
  defines, or `null` for no active tab or a non-http(s) URL, so an enablement
  lookup into `byHost` uses the identical key the write path stored):
  `zoom.in` and `zoom.out` are enabled only when `siteHost` is non-null;
  `zoom.reset` is enabled only when `siteHost` is non-null AND that host's
  current factor (read from `TabsState.zoom.byHost`, default `1.0`) is not
  `1.0`. `commandContextOf()` in `apps/desktop/src/main/index.ts` populates
  `siteHost`, and `refreshCommandState()` re-ranks the three rows exactly as
  it does for every other command whenever the active tab or its zoom
  changes.
- `isCommandEnabled`, `menuEntries`, and the View menu need no rule changes
  beyond the three new rows and the enablement above; dispatch runs through
  `executeCommand` exactly like every other command.
- Unit tests: the registry's uniqueness and enablement checks cover
  `zoom.in`, `zoom.out`, and `zoom.reset`, including `zoom.reset` toggling
  enabled/disabled as the active host's factor crosses `1.0`.

### 7. Sidebar (`apps/ui/src/App.tsx` + `apps/ui/src/App.css`)

- The active tab's row shows a zoom badge, `data-testid="tab-zoom"`,
  displaying `formatZoomPercent(factor)` for that tab's host key
  (`siteKeyForUrl` of its URL, the port-less hostname §1 defines, so the
  badge reads the same `byHost` key the write path stored) — the sibling
  of the existing `data-testid="tab-shield"` blocked-count badge. It is
  hidden entirely when the factor is `1.0` (including when the tab has no
  `byHost` entry or is on a non-http(s) page). Clicking the badge runs
  `zoom.reset` through the same command dispatch the command bar uses.
- A new BEM-ish class is added to the single stylesheet
  (`apps/ui/src/App.css`), matching the dark palette and the existing
  `tab-shield`-style rules; no CSS tooling is introduced.

### 8. Tests

- Unit: the ladder and reducer tests in §1, the migration and helper tests
  in §4, and the registry tests in §6.
- e2e (`e2e/tests/zoom.spec.ts`), a loopback `http.createServer` fixture
  page on an ephemeral port, following the `e2e/tests/blocking.spec.ts`
  pattern:
  - Loading the fixture page, then running `zoom.in` twice over
    `window.zeo.zoom.zoomIn()`: `zoom.state().byHost["127.0.0.1"]` equals
    the ladder value two rungs above `1.0` (`1.25`), and the page's
    `window.devicePixelRatio` reflects that factor. `devicePixelRatio`,
    not `visualViewport.scale`, is the observable asserted here: pinch-zoom
    is disabled (§3), so `visualViewport.scale` stays `1` regardless of the
    applied `setZoomFactor`, while `devicePixelRatio` scales with it.
  - Opening a second tab on the same host and loading the same fixture
    page: it loads at the same factor from its first commit, with no
    separate zoom command run against it.
  - Running `zoom.reset`: `byHost` loses the host's entry and the sidebar's
    `data-testid="tab-zoom"` badge disappears from that tab's row.
  - Relaunching the app after setting a non-default factor: the factor is
    unchanged on the first tab opened against that host, read from
    `site_zoom` with no user interaction.
  - The suite serves only from loopback and reads no network resource, so
    CI stays offline-deterministic.

## Constraints

- No per-tab temporary zoom: zoom is always keyed by host, never by tab id,
  and there is no UI or API to zoom one tab independently of its host's
  other tabs.
- No zoom for the sidebar or any overlay (command bar, context menus); only
  tab `WebContentsView`s are zoomed.
- No settings section is added by this PRD.
- `packages/core` stays Electron-free (lint-enforced): `zoom.ts` holds only
  pure functions and types; `apps/desktop/src/main/index.ts` owns every
  `WebContents` call (`setZoomFactor`, `setVisualZoomLevelLimits`, the
  `zoom-changed` listener).
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.
- Version bump to `0.0.19` with a dated `CHANGELOG.md` section.
- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e`
  green.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e`
  green.
- In the running app: `Cmd+=`, `Cmd+-`, and `Cmd+0` zoom the active tab's
  site in, out, and back to actual size, with the sidebar badge tracking
  the current factor; a second tab opened on the same host inherits the
  factor immediately; the factor survives a full relaunch.
- CI green on the merge request branch.
