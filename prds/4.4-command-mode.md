# PRD 4.4 — Command mode

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 4.3
(`prds/done/4.3-command-registry.md`) merged: the command registry exists,
the bar lists matching commands among tab and space rows, and every dispatch
goes through `executeCommand`.

Today the bar has two modes, `navigate` (`Cmd+L`) and `new-tab` (`Cmd+T`),
and both treat the typed text as a URL or search first. There is no way to
open the bar to run an action: `Cmd+K`, the palette shortcut users know from
Raycast, Linear, and VS Code, does nothing, and a query like `pin` competes
with tabs whose titles contain the same letters. This PRD adds a third bar
mode restricted to registry commands, bound to `Cmd+K`. It is the last PRD
of epic 4 (feature #84).

## Deliverables

### 1. Mode and registry entry (core)

- `CommandBarMode` becomes `"navigate" | "new-tab" | "commands"`. In
  `commands` mode the bar opens with `initialText: ""`, the typed text is a
  command query only, and there is no text action: `suggestions` never
  contains a `navigate` or `search` row, and `submit` is not a valid action
  (see 3).
- `CommandId` gains `"bar.open-commands"` with this registry row, appended
  after `bar.open-location` so registry order is unchanged for existing ids:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `bar.open-commands` | Run Command | `run`, `command`, `palette`, `actions` | `CmdOrCtrl+K` | view |

  It is always enabled. `isCommandEnabled`, `menuEntries`, and the View
  menu need no rule changes beyond the new row.
- Unit tests: the registry test suite's uniqueness and enablement checks
  cover the new id; `bar.open-commands` is enabled with `activeTab === null`
  and is part of the always-enabled set asserted there.

### 2. Suggestions in commands mode (core)

- `suggest(query, catalog, options)` with `options.mode === "commands"`:
  - Only `command` rows are produced. Spaces, tabs, and archived tabs are
    never consulted, even when they would match.
  - The catalog entry for `bar.open-commands` is excluded (the bar is
    already open in that mode), as are disabled commands.
  - Empty or whitespace query: every remaining enabled command in registry
    order, uncapped (the registry has fewer than `MAX_MATCHES` rows today;
    if it grows past it, the cap applies).
  - Non-empty query: the PRD 4.2 matching and tier rules over
    `title + " " + keywords`, ranked by score then registry order, capped at
    `MAX_MATCHES`. No row 0.
  - `selectedIndex` starts at `0` when the list is non-empty and `-1`
    otherwise, matching the existing rule.
- `navigate` and `new-tab` modes are unchanged: commands stay mixed in per
  PRD 4.3, and `bar.open-commands` matches there like any command (typing
  `command` in `new-tab` mode lists it).
- Unit tests: empty query lists all enabled commands minus
  `bar.open-commands` in registry order; a query that matches a tab title
  and a command yields only the command row; no `navigate`/`search` row
  ever appears in `commands` mode; disabled commands are excluded; the cap
  applies when the catalog carries more than `MAX_MATCHES` matching
  commands.

### 3. Opening, toggling, and dispatch (main)

- `openCommandBar("commands")` opens the bar with empty `initialText`, empty
  `query`, and the empty-query suggestion list from 2. It never falls back
  to another mode (the `navigate`-without-active-tab fallback does not apply).
- Handler for `bar.open-commands`: when the bar is closed or open in
  `navigate`/`new-tab` mode, open it in `commands` mode (switching mode
  resets the query and selection); when the bar is already open in
  `commands` mode, close it. So `Cmd+K` toggles the palette and switches
  into it from the other modes.
- Accepting a `command` row in `commands` mode runs `executeCommand(id)` and
  then closes the bar, with the same exceptions as PRD 4.3 (`tab.new` and
  `bar.open-location` re-open the bar in their own mode and are left open).
  `bar.open-commands` is never a row in this mode, so the toggle branch is
  not reachable from accept.
- `submitCommandBar(text, mode)`: when the effective mode (explicit `mode`
  argument, else the open bar's mode, else `navigate`) is `commands`, the
  call rejects with an error and changes nothing; the bar stays open. The
  renderer never calls `submit` (Enter is `accept`), so this only guards
  the bridge.
- `refreshCommandState()` re-runs suggestions while the bar is open in
  `commands` mode exactly as it does for the other modes, so a command whose
  enablement changed appears or disappears without retyping.
- Escape closes the bar in `commands` mode like in the other modes. All
  bridge methods and channel constants are unchanged; `commandBar.open`
  accepts the new mode value.

### 4. Bar renderer (ui)

- Placeholder text per mode: `Run a command` in `commands` mode, the
  existing `Search or enter address` otherwise.
- Command rows keep the PRD 4.3 layout (title, `Command` label, accelerator
  glyphs). No other renderer changes; the row kinds the renderer draws are
  unchanged.

### 5. Tests

- Core: registry and suggestion tests above.
- e2e:
  - `commandBar.open("commands")` over the bridge: the overlay shows,
    `state().mode` is `commands`, the input is empty with placeholder
    `Run a command`, and `suggestions` lists every enabled command except
    `bar.open-commands` in registry order with no `navigate`/`search` row.
  - Type `pin`: exactly one row, the `tab.pin` command; accept it and the
    active tab is pinned and the bar is closed.
  - With an open tab titled `pinboard`, type `pin` in `commands` mode and
    assert no `tab` row; open in `new-tab` mode, type `pin`, and assert the
    tab row is back (modes stay independent).
  - `commands.run("bar.open-commands")` opens the bar in `commands` mode; a
    second call closes it; with the bar open in `navigate` mode, the call
    switches it to `commands` with an empty query.
  - `commandBar.submit("example.org", "commands")` rejects and the bar
    state is unchanged; `submit("example.org")` with the bar open in
    `commands` mode rejects the same way.
  - The View menu binds `CmdOrCtrl+K` to `Run Command` (extend the
    registry-driven accelerator assertion, which picks the new row up from
    `COMMANDS`).
  - Enablement refresh: open `commands` mode on a fresh tab, assert no
    `tab.back` row; navigate the tab in place; assert the row appears
    without retyping.

## Constraints

- Mode and suggestion logic in `packages/core`; main owns open/toggle and
  dispatch; the renderer only changes its placeholder.
- No new commands beyond `bar.open-commands`; every PRD 4.1–4.3 behavior in
  `navigate` and `new-tab` mode is unchanged.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.
- Version bump to 0.0.13 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: `Cmd+K` opens the bar listing every available action;
  typing filters to actions only and never shows tabs or a search row;
  `Enter` runs the highlighted action; `Cmd+K` again closes it; `Cmd+T` and
  `Cmd+L` behave exactly as before.
- CI green on the merge request branch.
