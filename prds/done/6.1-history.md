# PRD 6.1 — History

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 4.4
(`prds/done/4.4-command-mode.md`) merged: the command bar has modes
(`navigate`, `new-tab`, `commands`), main recomputes `CommandBarState`
from a `SuggestCatalog` on every query change and pushes it to the overlay,
and tab views report navigations through `did-navigate`,
`did-navigate-in-page` and `page-title-updated` in `createViewFor`.

Nothing a tab visits is remembered once the tab closes. Epic 6 starts with
history: every top-level http(s) navigation is persisted in SQLite, the
command bar suggests matching history entries next to open tabs, a history
mode of the bar lists and filters recent history entries (one row per
url), and history can be deleted per url or cleared. Feature #86.

## Deliverables

### 1. History model (core)

- New module `packages/core/src/history.ts`, pure, exported from the barrel:

  ```ts
  interface HistoryEntry { url: string; title: string; visitCount: number; lastVisitedAt: number }
  interface HistoryVisit { id: number; url: string; title: string; visitedAt: number }
  /** True for http(s) urls up to 2048 characters with no credentials. */
  function isHistoryUrl(url: string): boolean;
  /** Storage key: the url without its fragment. */
  function historyKey(url: string): string;
  /** Query terms for a search: lowercased, whitespace-split, empty dropped. */
  function historyTerms(query: string): string[];
  const HISTORY_RETENTION_MS: number; // 90 days
  ```

- `isHistoryUrl` rejects everything but `http:`/`https:`, any url with
  `username` or `password`, and any url longer than 2048 characters.
  `historyKey` strips the `#fragment` only; query strings are kept because
  they distinguish pages. Both are unit-tested.
- Full query strings are retained by design, matching standard browser
  history (which stores the full url so query-distinguished pages stay
  searchable and re-openable); potentially-sensitive params such as
  `?code=` or `?token=` are therefore stored, not redacted. The exposure
  this allows is bounded: history lives only in the local per-user
  userData SQLite database and is reachable solely through the in-process
  IPC bridge to the app's own renderers (settings and the command bar),
  queried on demand — it is never part of `TabsState` or broadcast (see
  Bridge, below) and is never transmitted off the device.

### 2. Persistence

- Schema version 4 (PRD 5.2 takes 3). `MIGRATION_STEPS[4]` and the fresh
  `DDL` create:

  ```sql
  CREATE TABLE history_entries (
    url TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    visitCount INTEGER NOT NULL,
    lastVisitedAt INTEGER NOT NULL
  );
  CREATE TABLE history_visits (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    url TEXT NOT NULL REFERENCES history_entries(url) ON DELETE CASCADE,
    title TEXT NOT NULL,
    visitedAt INTEGER NOT NULL
  );
  CREATE INDEX history_visits_visitedAt ON history_visits(visitedAt);
  CREATE INDEX history_entries_lastVisitedAt ON history_entries(lastVisitedAt);
  ```

- `db.ts` helpers, synchronous, each one statement or one transaction:
  - `recordVisit(url, title, visitedAt): number` inserts the visit and
    upserts the entry in one transaction, returning the visit id. The
    visit row always inserts and `visitCount` always increments by 1, but
    `lastVisitedAt` is set to the new `visitedAt` and `title` replaced
    (only when the new title is non-empty) under the same `(visitedAt,
    id)` newest-visit rule as `updateVisitTitle`: they change only when
    the inserted visit is the newest for the url (its `visitedAt`, ties
    broken by the new `id`, is the maximum among the url's visits).
    Otherwise the entry keeps its `lastVisitedAt` and `title` while still
    counting the visit. This stops an out-of-order (older) visit from
    moving `lastVisitedAt` backward or replacing the entry title with an
    older one.
  - `updateVisitTitle(visitId, title): void` sets the title on that visit
    row, and on its entry only when that visit is still the newest visit
    for the entry's url (its `visitedAt`, ties broken by `id`, is the
    maximum among the url's visits), both in one transaction. This
    last-write rule stops a delayed title update for an older visit from
    overwriting a newer visit's title on the shared entry row.
  - `searchHistory(terms: string[], limit): HistoryEntry[]`: every term
    must be a case-insensitive substring of `url` or `title` (`LIKE` with
    `%`/`_` escaped through `ESCAPE '\'`), ordered by `visitCount DESC,
    lastVisitedAt DESC`. An empty `terms` array returns the entries ordered
    by `lastVisitedAt DESC` alone.
  - `recentVisits(limit): HistoryVisit[]` ordered by `visitedAt DESC`.
  - `deleteHistoryUrl(url): void` deletes the entry (visits cascade).
  - `clearHistory(): void` deletes both tables in one transaction.
  - `pruneHistory(now): void` deletes visits older than
    `HISTORY_RETENTION_MS` and then entries left with no visits, in one
    transaction. `visitCount` is a lifetime counter: `recordVisit`
    increments it and nothing decrements it, so pruning does not adjust
    the `visitCount` of surviving entries. The count can therefore exceed
    the number of retained visits, and `visitCount DESC` ranking
    intentionally ranks by lifetime visits.
- History tables are outside `writeState` and `readState`; the history
  writes above happen directly from the navigation handlers, never through
  the debounced state save. `db.test.ts` covers the migration 3 → 4, each
  helper, the `updateVisitTitle` last-write rule (a title update for an
  older visit updates only that visit row and leaves the entry title set
  by the newest visit), the `recordVisit` newest-visit rule (an older
  visit recorded after a newer one increments `visitCount` but leaves
  `lastVisitedAt` and the entry `title` at the newer visit's values),
  `LIKE` escaping (`%` in a term matches a literal `%`), and prune
  (including that a surviving entry keeps its lifetime `visitCount` after
  its old visits are deleted).

### 3. Recording (main)

- In `createViewFor`, a single `did-navigate` listener (the same one that
  resets blocked counts, or a sibling registered right after it) and the
  `did-navigate-in-page` listener call `recordNavigation(tabId)`. The
  `did-navigate` listener first removes the tab from `hasRealTitle` and
  then calls `recordNavigation` (a new document has committed, so the tab
  has not yet emitted its own title); the `did-navigate-in-page` listener
  calls `recordNavigation` without touching `hasRealTitle` (a same-document
  navigation keeps the document's title). `recordNavigation`
  reads `view.webContents.getURL()` live, and when `isHistoryUrl` is false
  clears the tab's `lastHistoryKey`, `lastVisitId` and `hasRealTitle`
  entries before returning (so navigating away to `about:blank` or `data:`
  and back to a recorded url records the return as a fresh visit with a
  fresh title). When the url is a history url it computes `historyKey`, and
  skips when the key equals the tab's last recorded key
  (`lastHistoryKey: Map<string, string>`), so hash and `pushState` churn on
  one page records once. Otherwise it calls
  `recordVisit(key, currentTitle, Date.now())` where `currentTitle` is
  `webContents.getTitle()` when the tab is in `hasRealTitle`, else
  `titleForUrl(key)`, and stores the returned visit id in `lastVisitId:
  Map<string, number>` together with the `lastHistoryKey` entry written in
  the same call, so the tab's recorded key and visit id are always the pair
  from one navigation.
- `hasRealTitle: Set<string>` (tab ids) tracks whether the tab's current
  document has emitted its own title. The tab is added when
  `page-title-updated` fires with a non-empty title (next bullet) and
  removed by the `did-navigate` handler before it calls `recordNavigation`
  (a new document commits) and on the non-history clear path above;
  `did-navigate-in-page` leaves it set because a same-document navigation
  keeps the document's title. Because the removal precedes the
  `recordNavigation` read, a history-to-history navigation to a page that
  emits no title of its own records `titleForUrl(key)` rather than the
  previous document's stale title.
- `page-title-updated` fires only for the tab's current document, whose
  visit is the tab's `lastVisitId`. The handler adds the tab to
  `hasRealTitle` and, when the live url's `historyKey` still equals the key
  recorded alongside `lastVisitId`, calls
  `updateVisitTitle(lastVisitId.get(tabId), title)`, so the title updates the
  visit the current load created. The key check drops a title event that
  races a navigation to a different key (the tab has already left that
  visit's url). A title event from an earlier same-url visit cannot reach a
  newer visit's row: a navigation tears down the previous document, so its
  renderer emits no further titles, and the `updateVisitTitle` last-write
  rule (section 2) additionally guards the shared entry row against any
  update carrying an older visit id.
- The `lastHistoryKey`, `lastVisitId` and `hasRealTitle` entries are deleted
  in the same paths that delete `tabOrigin` (`closeTab`, `removeTab`,
  `deleteSpace`); `destroyView` keeps them.
- `pruneHistory(Date.now())` runs once on launch after `migrate` and then
  every 24 h on the same interval that refreshes filter lists (a separate
  timer is fine).
- Recording failures (a database error) are logged once per launch and
  never break navigation.

### 4. Bridge

- `packages/core/src/ipc.ts`:

  ```ts
  interface HistoryApi {
    search(query: string, limit?: number): Promise<HistoryEntry[]>;
    recent(limit?: number): Promise<HistoryVisit[]>;
    deleteUrl(url: string): Promise<void>;
    clear(): Promise<void>;
  }
  interface ZeoApi { history: HistoryApi }
  ```

  Channels `historySearch: "zeo:history:search"` (payload `{ query:
  string; limit: number }`, response `HistoryEntry[]`), `historyRecent:
  "zeo:history:recent"` (payload `{ limit: number }`, response
  `HistoryVisit[]`), `historyDeleteUrl: "zeo:history:delete-url"` (payload
  `string`, response `void`), `historyClear: "zeo:history:clear"` (no
  payload, response `void`). `limit` defaults to 50 and is clamped to
  `[1, 500]` in main; a non-string url rejects with `TypeError`. History
  is not part of `TabsState` and is never broadcast; the settings and
  command-bar surfaces query it on demand.

### 5. Suggestions

- `Suggestion` gains `{ kind: "history"; url: string; title: string;
  visitCount: number; lastVisitedAt: number }`. `SuggestCatalog` gains
  `history: HistoryEntry[]`, already filtered by the database for the
  query: main's `recomputeSuggestions` calls
  `searchHistory(historyTerms(query), HISTORY_CANDIDATES)` with
  `HISTORY_CANDIDATES = 20` whenever the query is non-empty and the mode is
  `navigate`, `new-tab` or `history`; for an empty query in `history` mode
  it passes the 20 entries ordered by `lastVisitedAt`; otherwise
  `history` is `[]`.
- Inside `suggest()`, history candidates are scored with the same
  `termTier` rules over `title` and host as tabs, skipped when an open
  tab's url has the same `historyKey` (the tab row wins), and get
  `kindRank` 2 with the ranks re-numbered: tab 0, space 1, history 2,
  command 3, archived 4. `recency` for a history row is `lastVisitedAt`.
  `commands` mode ignores history.
- `CommandBarMode` gains `"history"`. In that mode row 0 (navigate/search)
  is omitted, `suggest()` returns only history rows (up to `MAX_MATCHES`)
  and the input placeholder reads "Search history". Accepting a history
  row in any mode navigates the active tab (`navigateTab`) in `navigate`
  and `history` modes and creates a tab in `new-tab` mode, through
  `performSuggestion`, then closes the bar.
- Overlay row rendering: `data-kind="history"`, title on the first line,
  host on the second, a clock glyph in place of the favicon.
- In `history` mode, `Cmd+Backspace` on the selected row calls
  `history.deleteUrl(row.url)` then `setQuery(query)` to recompute;
  the bar stays open. Wired in `CommandBar.tsx` next to the existing key
  handling.
- Commands, `menu: "view"`, dispatched through `executeCommand`:
  - `history.open`, "Show History", keywords `history`, `recent`,
    `visited`, accelerator `CmdOrCtrl+Y`, always enabled; opens the bar in
    `history` mode (the bar stays open after accepting this command, like
    `bar.open-commands`).
  - `history.clear`, "Clear Browsing History", keywords `history`,
    `clear`, `delete`, always enabled; calls `clearHistory()` and, when
    the bar is open in `history` mode, recomputes it.
- Unit tests in `suggest.test.ts`: history rows rank between spaces and
  commands, dedupe against open tabs, `history` mode returns no row 0 and
  no commands, empty query in `history` mode lists the catalog order.

### 6. Tests

- Unit: history module, db helpers and migration, suggest changes, command
  registry (`history.open` accelerator and mode behavior).
- e2e (`e2e/tests/history.spec.ts`, loopback server serving `/a.html` with
  `<title>Alpha page</title>` and `/b.html` with `<title>Beta page</title>`,
  plus `/a.html#x` and `/notitle.html` (a history url with no `<title>`)):
  - Navigate the active tab to `/a.html`, then `/b.html`, then `/a.html#x`:
    `history.recent()` has three visits, `history.search("alpha")` returns
    one entry with `visitCount` 2, `title` "Alpha page", and the url without
    the fragment; `search("%")` returns nothing.
  - Close the tab; open the command bar in `navigate` mode and type
    `alpha`: a row with `data-kind="history"` appears and accepting it
    navigates the active tab to `/a.html`. With `/a.html` open in a tab,
    the same query shows the `tab` row and no `history` row for that url.
  - `Cmd+Y` opens the bar in `history` mode showing the recent entries with
    no `navigate` row; `Cmd+Backspace` on the selected row removes it and
    `history.search` no longer returns it.
  - Relaunch: `history.recent()` still returns the remaining visits.
  - `history.clear()` empties `recent()` and `search("")`.
  - `about:blank` and `data:` navigations record nothing; navigating
    `/a.html` → `about:blank` → `/a.html` records the return as a new
    visit (the non-history navigation reset the tab's last-key state).
  - After `/a.html` → `/b.html` → `/a.html`, `history.search("alpha")`
    returns the `/a.html` entry with `visitCount` 2 and the current
    document's title — a re-visit updates its own visit, never an older one.
  - A history-to-history navigation from a titled page to a page that emits
    no title records `titleForUrl(key)` for the second page, not the first
    page's title: after `/a.html` ("Alpha page", which sets `hasRealTitle`),
    navigate the same tab to `/notitle.html`; `history.search` returns the
    `/notitle.html` entry with its url-derived title, confirming
    `did-navigate` cleared `hasRealTitle` before `recordNavigation` read it.
    An `about:blank`/`data:` hop likewise does not leave `hasRealTitle` set
    so as to corrupt a subsequently recorded visit's title.

## Constraints

- `packages/core` stays Electron-free and holds types, url rules, suggest
  changes and mode logic; SQL stays in `apps/desktop/src/main/db.ts`.
- No history page or settings section in this PRD (a settings section is
  PRD 6.5); no sync; no per-space history.
- Schema version 4 assumes PRD 5.2 (version 3) is on `main` first; if this
  PRD lands first, take the next free version at rebase and renumber the
  migration step so `SCHEMA_VERSION` equals `main`'s value plus one.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged; CI stays offline-deterministic.
- Version bump to 0.0.16 with a dated `CHANGELOG.md` section.
