# PRD 5.1 — Content blocking engine

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 4.3
(`prds/done/4.3-command-registry.md`) merged: epic 4 (command bar) is
complete and every profile maps to an Electron session partition
`persist:<profileId>`.

Epic 5 delivers built-in, filter-list based content blocking. This PRD lands
the engine and its wiring: the `packages/adblock` workspace the design doc
reserves, a blocker built from the standard uBlock Origin ad and tracking
lists through `@ghostery/adblocker-electron`, attached to every profile
session, with an on-disk engine cache so the app blocks from the first
request after a cold start and keeps working offline. A global on/off switch
and per-tab blocked-request counts are exposed over the bridge and shown in
the sidebar. Per-site allowlisting, the command-bar commands for it, and a
blocking settings surface arrive in PRD 5.2.

## Deliverables

### 1. `packages/adblock` workspace

- New workspace package `@zeo/adblock` (`packages/adblock`), TypeScript,
  built like `@zeo/core`, depending on `@ghostery/adblocker-electron` (pin
  the current stable major). It is the only package that imports the
  adblocker library. This package is Electron-aware by design: it may import
  `electron` (the session hook needs it), so the "no Electron" lint rule
  stays scoped to `packages/core` exactly as today, and its unit tests run
  under plain Vitest with a hand-written fake `Session` (`webRequest` stub)
  instead of Electron.
- Exports:

  ```ts
  interface BlockedEvent { webContentsId: number; url: string }
  interface Blocker {
    /** Enables blocking on `session`; idempotent per session. */
    attach(session: Electron.Session): void;
    /** Disables blocking on `session`; idempotent. */
    detach(session: Electron.Session): void;
    /** Sessions currently attached. */
    attachedSessions(): readonly Electron.Session[];
    onBlocked(listener: (event: BlockedEvent) => void): () => void;
    /** Rebuilds the engine from the lists and swaps it in; resolves true on success. */
    refresh(): Promise<boolean>;
    listVersion: string;
  }
  function createBlocker(options: {
    cacheFile: string;
    fetch: typeof fetch;
    lists?: string[];
    fs?: { readFile; writeFile };
  }): Promise<Blocker>;
  function createBlockerFromFilters(filters: string): Blocker;
  ```

- One `Blocker` object lives for the whole app lifetime; it owns exactly one
  engine at a time plus the set of attached sessions and the listener list.
  `refresh()` builds the new engine off to the side and then swaps the
  engine reference in a single synchronous step while the session hooks and
  listeners stay registered, so there is never a detached window, never two
  engines answering for one session, no listener re-subscription, and the
  attached/detached state of every session is preserved across a refresh.
  A failed refresh leaves the current engine untouched and resolves `false`.
- `createBlocker()` startup order: read the serialized engine from
  `cacheFile` when it exists and deserializes with the installed library
  version (local, fast); otherwise use the library's bundled fallback lists
  when it ships any, else an empty engine that blocks nothing. It resolves
  as soon as that local step is done, then starts one background
  `refresh()` from the remote lists (`lists` defaults to the library's
  prebuilt ads and tracking set) bounded by a 15 s fetch timeout; on success
  the engine is swapped in and serialized to `cacheFile`. `listVersion`
  reports the active engine's origin (`"cache"`, `"remote"`, `"bundled"`,
  `"none"`, or `"fixture"` prefix plus a date or hash) and changes on swap.
- `createBlockerFromFilters(text)` builds a `Blocker` from raw filter text
  synchronously with no cache, no remote, and a no-op `refresh()`; used by
  tests and by the e2e fixture.
- `attach` calls the library's session hook (`enableBlockingInSession`);
  `detach` its inverse; both are idempotent so repeated calls for one
  session never double-register. `onBlocked` adapts the library's
  `request-blocked` event to the requesting `webContents.id` and the url.
- Unit tests (Vitest, no Electron, fake session and injected `fetch`/`fs`):
  `createBlockerFromFilters` matches a request that a filter targets and
  passes one it does not; `createBlocker` prefers the cache, degrades to
  bundled/none when there is no cache, writes the cache after a successful
  refresh, keeps the old engine on a failed refresh, keeps every attached
  session attached across a refresh, and delivers blocked events to a
  listener registered before the refresh.

### 2. Blocking state (core)

- `BlockingState` type in `packages/core`: `{ enabled: boolean; listVersion:
  string; blockedByTab: Record<string, number>; blockedUnattributed: number }`
  where the `blockedByTab` key is the tab id and the value the count of blocked
  requests since the tab was created or last navigated to a new origin, and
  `blockedUnattributed` counts blocked requests that mapped to no tab (see §3).
- `TabsState` gains `blocking: BlockingState`. A pure reducer
  `applyBlockedRequest(state, tabId)` and `resetBlockedCount(state, tabId)`
  with unit tests; counts reset on a top-level navigation to a different
  origin and are dropped when the tab is removed.
- Persisted setting: `enabled` is stored in the SQLite meta table (schema
  version 2 migration adds the key, default `true`); the migration runner
  test covers 1 to 2.
- Bridge, in `packages/core/src/ipc.ts` next to the existing APIs:

  ```ts
  interface BlockingApi {
    setEnabled(enabled: boolean): Promise<void>;
    state(): Promise<BlockingState>;
  }
  interface ZeoApi { blocking: BlockingApi }
  ```

  Channel constants `blockingSetEnabled: "zeo:blocking:set-enabled"`
  (request payload `boolean`, response `void`) and `blockingState:
  "zeo:blocking:state"` (no payload, response `BlockingState`). Updates need
  no new channel: `BlockingState` is part of `TabsState`, so every change
  rides the existing `stateChange` broadcast. Main, preload, and renderer use
  these constants only.
- `setEnabled` contract, executed on the main thread in this order: (1) if
  the value equals the current one, resolve without side effects; (2) write
  the new value to the SQLite meta table synchronously; on failure reject
  and change nothing; (3) attach or detach the blocker on every profile
  session; if any session call throws, revert the sessions already changed
  and the persisted value, then reject; (4) update the in-memory state and
  broadcast. Profile creation reads the in-memory `enabled` when it creates
  the new partition, and because both paths run on the main thread with no
  await between reading and applying, a profile created during `setEnabled`
  always ends in the final state.
- Command registry gains `blocking.toggle` ("Toggle Content Blocking",
  keywords `block`, `ads`, `tracking`, `adblock`, no accelerator, menu
  `view`), always enabled, dispatched through `executeCommand`.

### 3. Main process wiring

- Startup gate: on app ready, before the first window is created, main
  awaits `createBlocker({ cacheFile: app.getPath("userData") +
  "/adblock-engine.bin", fetch })`. That await covers only the local step
  (cache or bundled/none), so it is bounded by disk speed and additionally
  capped at 3 s; past the cap the window opens with the empty engine and the
  cache load result is swapped in when it arrives. The blocker is attached
  to every existing profile session before any tab view is created (when
  the persisted `enabled` is true), and to every profile created later
  (`profiles.create` and the partition-migration path). Guarantee: with a
  warm cache the very first request of a launch is filtered; on a first-ever
  launch requests are filtered by the bundled lists (or not at all when the
  library ships none) until the background remote refresh lands, and the
  sidebar shows no shield until then.
- Attribution: main keeps a reverse index `webContents.id -> tabId`,
  registered in `createViewFor` right after the view is constructed and
  removed in every view-destroy path (close, remove, archive teardown, space
  delete, profile remap recreate). `onBlocked` looks the id up; a hit applies
  `applyBlockedRequest` for that tab, a miss (a view already torn down, or
  the sidebar/overlay renderer) is dropped and counted in a
  `blockedUnattributed` number on `BlockingState` so a wrong mapping is
  visible in tests. Broadcasts are coalesced (at most one per 250 ms) so a
  page loading many blocked resources does not flood the renderer.
- Test hook: when `ZEO_ADBLOCK_FILTERS` names a file, main builds the
  blocker with `createBlockerFromFilters` from that file and nothing else:
  no cache read or write, no remote fetch, no daily refresh; `listVersion`
  reads `fixture:<basename>`. This is checked before any other source.
- Refresh: once a day while running, and on launch when the cache is older
  than a day, main calls `blocker.refresh()`; the swap is atomic as defined
  in section 1, so attached sessions and the disabled state are untouched.
  Failures keep the current engine and log once per launch.

### 4. Sidebar (ui)

- Each tab row shows a small shield glyph with the blocked count when the
  count is above zero; the glyph is dimmed when blocking is disabled. No
  other renderer changes; the toggle is reachable through the command bar
  and the View menu.

### 5. Tests

- Unit: package tests above; core reducers and migration.
- e2e: the suite starts a loopback `http.createServer` in the Playwright
  process on an ephemeral port serving `/page.html` (an `<img>` for
  `/blocked/pixel.png` and one for `/allowed/ok.png`, each 1×1 PNG) and
  recording every request path it receives; `ZEO_ADBLOCK_FILTERS` points to
  a fixture list containing the path filter `/blocked/*$image`. Both hosts
  are the same loopback origin, so a missing request can only mean the
  blocker dropped it, never a DNS or network failure.
  - After loading `/page.html`: the server saw `/allowed/ok.png` and did not
    see `/blocked/pixel.png`, the allowed image's `naturalWidth` is 1, the
    blocked image fired `error`, `blockedByTab` for the tab is 1, and
    `blockedUnattributed` is 0.
  - Close the tab, then load `/page.html` in a new tab: the closed tab's id
    has no entry, `blockedUnattributed` stays 0.
  - `blocking.setEnabled(false)` then reload the same origin: both requests
    now load, and because a same-origin reload does not reset the count, no
    new block is added and the tab's existing `blockedByTab` count is
    preserved (stays 1); `setEnabled(true)` then restores blocking on the same
    session without relaunch, and the next load increments the count.
  - Two spaces on distinct profiles both block (the second profile's session
    is attached).
  - Relaunch with `enabled` set to false persists the setting.
  - The `blocking.toggle` command row appears for the query `ads` and
    accepting it flips `enabled`.

## Constraints

- Only `packages/adblock` imports the adblocker library; `packages/adblock`
  and `apps/desktop` may import Electron; `packages/core` stays Electron-free
  and holds types, reducers, and the schema change.
- No per-site allowlist, no cosmetic-filter UI, no filter-list management
  UI in this PRD.
- Engine cache and list downloads live under `userData`; nothing is written
  into the repository or the app bundle at runtime.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged. CI must stay offline-deterministic: no test may
  depend on downloading filter lists.
- Version bump to 0.0.12 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: ad-heavy sites show blocked counts on their sidebar
  rows within seconds of loading; toggling content blocking from the command
  bar stops and resumes blocking without relaunch; the second launch starts
  blocking immediately from the cached engine with no network.
- CI green on the merge request branch.
