# PRD 4.3 — Command registry and action suggestions

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 4.2
(`prds/done/4.2-command-bar-suggestions.md`) merged: the command bar lists
ranked tab, archived-tab, and space suggestions and acts on them.

Actions today live in two disconnected places: hard-coded application-menu
items with accelerators in `apps/desktop/src/main/index.ts`, and sidebar
context menus. Neither is reachable from the bar. This PRD introduces the
command registry the design doc calls for: one declarative list of commands
in `packages/core` with ids, titles, keywords, accelerators, and an
enablement rule. The application menu is generated from it, the bar offers
matching commands as suggestions, and both dispatch through one handler map
in main. This closes epic 4.

## Deliverables

### 1. Command registry (core)

- Types in `packages/core`:

  ```ts
  type CommandId =
    | "tab.new" | "tab.close" | "tab.pin" | "tab.unpin" | "tab.archive"
    | "tab.copy-url" | "tab.reload" | "tab.back" | "tab.forward"
    | "space.new" | "space.rename" | "space.delete" | "bar.open-location";
  interface CommandDescriptor {
    id: CommandId;
    title: string;
    keywords: string[];
    accelerator: string | null;
    menu: "tabs" | "spaces" | "view" | null;
  }
  interface CommandContext {
    activeTab: { pinned: boolean; canGoBack: boolean; canGoForward: boolean } | null;
    spaceCount: number;
  }
  ```

- `COMMANDS: readonly CommandDescriptor[]` in registry order, one entry per
  id above. Titles, keywords, and accelerators:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `tab.new` | New Tab | `new`, `tab`, `create` | `CmdOrCtrl+T` | tabs |
  | `tab.close` | Close Tab | `close`, `tab` | `CmdOrCtrl+W` | tabs |
  | `tab.pin` | Pin Tab | `pin`, `tab`, `favorite` | `CmdOrCtrl+Shift+P` | tabs |
  | `tab.unpin` | Unpin Tab | `unpin`, `pin`, `tab` | `CmdOrCtrl+Shift+P` | tabs |
  | `tab.archive` | Archive Tab | `archive`, `tab`, `hide` | `CmdOrCtrl+Shift+W` | tabs |
  | `tab.copy-url` | Copy URL | `copy`, `url`, `link`, `address` | `CmdOrCtrl+Shift+C` | tabs |
  | `tab.reload` | Reload Page | `reload`, `refresh`, `page` | `CmdOrCtrl+R` | view |
  | `tab.back` | Go Back | `back`, `history`, `previous` | `CmdOrCtrl+[` | view |
  | `tab.forward` | Go Forward | `forward`, `history`, `next` | `CmdOrCtrl+]` | view |
  | `space.new` | New Space | `new`, `space`, `workspace`, `create` | `CmdOrCtrl+Shift+N` | spaces |
  | `space.rename` | Rename Space | `rename`, `space`, `workspace` | null | spaces |
  | `space.delete` | Delete Space | `delete`, `remove`, `space`, `workspace` | null | spaces |
  | `bar.open-location` | Open Location | `open`, `location`, `url`, `address`, `go` | `CmdOrCtrl+L` | view |

  `tab.pin` and `tab.unpin` share one accelerator; at most one of them is
  enabled at a time (exactly one while a tab is active, neither without),
  and the generated menu carries a single "Pin Tab" / "Unpin Tab" item whose
  label and handler follow the enabled one ("Pin Tab", disabled, when no tab
  is active). The existing hidden `Activate Tab N` / `Activate Space N` items stay
  as they are, outside the registry.
- `isCommandEnabled(id, context): boolean`, pure. Always enabled: `tab.new`,
  `space.new`, `space.rename`, `bar.open-location`. Every other `tab.*`
  command needs `activeTab !== null`; on top of that `tab.pin` needs it
  unpinned, `tab.unpin` pinned, `tab.archive` unpinned, and `tab.back` /
  `tab.forward` the matching flag. `space.delete` needs `spaceCount > 1`.
  With `activeTab === null` the only enabled commands are the four
  always-enabled ones plus `space.delete` when more than one space exists.
- `commandContextOf(store, viewFlags)` is not in core; main builds the
  `CommandContext` from the store and the active view's `canGoBack` /
  `canGoForward`.
- Unit tests: every id appears exactly once, accelerators are unique except
  the pin/unpin pair, each enablement rule has a positive and a negative
  case, and the `activeTab === null` context yields exactly the set stated
  above.

### 2. Command suggestions (core)

- `Suggestion` gains `{ kind: "command"; id: CommandId; title: string;
  accelerator: string | null }`. `SuggestCatalog` gains `commands:
  { id, title, keywords, accelerator, enabled }[]`; main passes every
  registry entry (its `CommandDescriptor` fields verbatim) with its current
  enablement, and `suggest` copies `accelerator` from the catalog entry into
  the row.
- Matching uses the PRD 4.2 rules with haystack `title + " " + keywords`.
  Disabled commands are excluded from results. In the kind order commands sit
  after spaces and before archived tabs. Empty-query behavior is unchanged
  (no commands listed without a query).
- Unit tests: a command matches on a keyword, a disabled command never
  appears, kind ordering with commands present, and a command row carries
  the catalog entry's accelerator (including `null`).

### 3. Dispatch and menu generation (main)

- One checked boundary in main, `executeCommand(id)`: it builds the current
  `CommandContext`, rejects (throws for menu callers, rejects the invoke for
  bridge callers) when `isCommandEnabled` is false or the id is unknown, and
  only then runs the handler. Every dispatch path goes through it: generated
  menu items, `commands.run`, and command-suggestion acceptance. A stale menu
  click or a stale accepted row therefore never runs `space.delete`,
  `tab.close`, or a navigation command after the context changed; the e2e
  below covers one such case.
- One handler map in main keyed by `CommandId`, called only by
  `executeCommand`; each handler runs the same store and view operations the
  current menu items and context menus use.
  `space.rename` pushes the existing `spaceMenuAction` `rename` for the
  active space so the sidebar's inline editor opens; `space.delete` runs the
  existing delete path for the active space; `tab.copy-url` writes the
  active tab's url to the clipboard; `tab.reload` / `tab.back` /
  `tab.forward` act on the active view's `webContents`; `bar.open-location`
  opens the bar in `navigate` mode.
- The application menu's Tabs, Spaces, and a new View submenu are generated
  from `COMMANDS` filtered by `menu`, in registry order, using each entry's
  accelerator and dispatching through `executeCommand`; hand-written items
  for the same actions are removed. Merge rule for shared accelerators: a
  pure `menuEntries(commands, context)` in core groups registry entries that
  share a non-null accelerator into one menu entry placed at the first
  member's position; the entry's label, id, and `enabled` come from the
  first member that is enabled in `context`, or from the first member
  (disabled) when none is. Only the pin/unpin pair qualifies today, so the
  Tabs menu has exactly one `CmdOrCtrl+Shift+P` item reading "Pin Tab" or
  "Unpin Tab". Because the label changes with context, `refreshCommandState()`
  rebuilds the application menu with `Menu.setApplicationMenu` rather than
  toggling `enabled` in place. Unit test: `menuEntries` yields one entry for
  the pair with the right label per context and no duplicate accelerators. Menu items' `enabled` is recomputed from
  `isCommandEnabled` on every state broadcast and, for the history flags, on
  the active view's `did-navigate`, `did-navigate-in-page`, and
  `did-finish-load` events plus every active-tab or active-space change; a
  single `refreshCommandState()` in main is the one place that recomputes the
  context, updates the menu, and re-runs the bar's suggestions when the bar
  is open. macOS app menu and edit menu stay as today.
- Accepting a `command` suggestion runs the handler, then closes the bar.
  Accepting `bar.open-location` from an open bar re-seeds the bar in
  `navigate` mode instead of closing.
- Bridge: `CommandsApi { list(): Promise<CommandDescriptor[]>; run(id:
  CommandId): Promise<void> }` on `ZeoApi.commands`, with channel constants.
  `run` rejects for an unknown id or a command disabled in the current
  context. The sidebar's existing new-tab button and tab context-menu actions
  keep their current paths; migrating them is not required.

### 4. Bar renderer (ui)

- Command rows show the title, a `Command` secondary label, and the
  accelerator rendered with macOS glyphs (`⌘⇧P`) right-aligned when present.
  No other renderer changes.

### 5. Tests

- Core: registry and enablement tests above; suggestion tests above.
- e2e:
  - Type `pin`, assert a `command` row for `tab.pin` appears and accepting
    it pins the active tab; type `pin` again and assert the row is now
    `tab.unpin`.
  - Type `new space`, accept, assert the space count grew and the new space
    is active.
  - With one space, type `delete space`, assert no `space.delete` row.
  - `commands.run("tab.close")` closes the active tab;
    `commands.run("tab.back")` with no history rejects.
  - History refresh: with the bar open and `back` typed, no `tab.back` row
    exists on a fresh tab; navigate the tab in place, assert the row appears
    without retyping; the Tabs/View menu item for Go Back reports `enabled`
    accordingly via `Menu.getApplicationMenu()`.
  - Stale dispatch: open the bar, type `delete space` with two spaces, then
    delete the other space over the bridge before accepting; `accept` on the
    `space.delete` row rejects and the remaining space survives.
  - The Tabs, Spaces, and View menus bind the registry accelerators (extend
    the existing accelerator assertions to read expectations from `COMMANDS`
    rather than literals); the Tabs menu contains exactly one item with
    `CmdOrCtrl+Shift+P`, labelled "Pin Tab" on an unpinned active tab and
    "Unpin Tab" after pinning it.
  - `tab.reload` via the bar reloads the active view (assert a page-side
    marker set before the reload is gone after it).

## Constraints

- Registry, enablement, and suggestion logic in `packages/core`; main owns
  handlers and menu construction; the renderer stays thin.
- No new commands beyond the table; settings, history, downloads, find,
  and zoom commands arrive with epic 6.
- `submit(text, mode?)` and every PRD 4.2 behavior are unchanged.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.
- Version bump to 0.0.11 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: typing an action name in the bar lists it with its
  shortcut and `Enter` runs it; the Tabs, Spaces, and View menus show the
  same commands with the same shortcuts; `Cmd+R`, `Cmd+[`, `Cmd+]`,
  `Cmd+Shift+P`, `Cmd+Shift+W`, and `Cmd+Shift+C` work from inside a page.
- CI green on the merge request branch.
