# PRD 4.1 — Command bar shell and URL entry

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 3.4
(`prds/done/3.4-sqlite-persistence.md`) merged: spaces, profiles, and tabs
work end to end and persist across relaunches.

The browser still has no way to type a URL. Tabs are created against a
hard-coded default URL and navigation happens only by following links. Epic 4
delivers the command bar, the single keyboard entry point for URLs, search,
tab switching, and actions. This PRD lands the bar itself and URL/search
entry: an overlay that opens over the page with `Cmd+L` / `Cmd+T`, takes a
line of text, and either navigates the active tab or opens a new one.
Suggestions (open tabs, archived tabs, spaces) arrive in PRD 4.2 and the
command registry with action items in PRD 4.3; both extend this shell without
replacing it.

## Deliverables

### 1. Input resolution (core)

- A pure module in `packages/core` that turns the typed text into a
  navigation target:
  `resolveInput(text): NavigationTarget | null` with
  `NavigationTarget = { kind: "url" | "search"; url: string }`. The text is
  trimmed first; empty text returns `null`. Rules, in order, on the trimmed
  text; the first matching rule wins:
  - Scheme rule: text matching `^[a-z][a-z0-9+.-]*:` (case-insensitive)
    whose scheme is `http` or `https` is a URL. Any other scheme (`file`,
    `about`, `zeo`, `javascript`, `data`, …) is not a URL and falls through to
    the search rule; the bar never navigates to a non-HTTP scheme. Tab views
    keep the navigation surface they have today (no preload, no privileged
    scheme); a `zeo:` protocol is not introduced in this epic.
  - Host rule: text containing no whitespace is split into `authority` (up to
    the first `/`, `?`, or `#`) and the remainder (path, query, fragment kept
    verbatim). `authority` must be `host` or `host:port` with `port` all
    digits. `host` must be one of: `localhost`; an IPv4 literal (four
    dot-separated decimal octets, each 0–255); a dotted hostname of two or
    more labels, each `[a-z0-9-]+` (case-insensitive, no leading or trailing
    hyphen), whose last label is alphabetic and at least two characters. A
    match is a URL with `https://` prepended, or `http://` when `host` is
    `localhost` or an IPv4 literal.
  - Search rule: everything else. The text is percent-encoded into the
    default search engine's query URL. The default engine is a single exported
    constant (DuckDuckGo, `https://duckduckgo.com/?q=`); making it a setting is
    epic 6.
- Canonical output: every `url` result is passed through the WHATWG `URL`
  parser and serialized (`new URL(candidate).href`), so schemes and hosts are
  lower-cased, a bare origin gains its trailing slash, and the path, query, and
  fragment are percent-encoded the way the browser would. A candidate the
  parser rejects falls through to the search rule. Core and e2e assert the
  serialized form, never the raw input.
- Unit tests cover each rule, including edge cases: a bare word (`zeo`) is a
  search; a word with a trailing dot (`done.`) is a search; a
  space-containing string with a dot (`what is example.com`) is a search;
  `example.com:8080/path?q=1#frag` is `https://example.com:8080/path?q=1#frag`;
  `localhost:3000` is `http://localhost:3000/`; `HTTPS://Example.COM` is
  `https://example.com/`; `file:///etc/hosts` and `about:blank` are searches;
  `192.168.1.10` is `http://192.168.1.10/` while `999.1.1.1` is a search;
  leading and trailing whitespace is ignored; empty and whitespace-only text
  returns `null`.

### 2. Command bar state and bridge contract (core)

- A `CommandBarState` type: `{ open: boolean; mode: "navigate" | "new-tab";
  initialText: string }`. `navigate` mode acts on the active tab and opens
  prefilled with its current URL, selected; `new-tab` mode opens empty and
  creates a tab on submit.
- Bridge surface, all in `packages/core/src/ipc.ts` next to the existing
  APIs:

  ```ts
  type CommandBarMode = "navigate" | "new-tab";
  interface CommandBarState { open: boolean; mode: CommandBarMode; initialText: string }
  interface CommandBarApi {
    open(mode: CommandBarMode): Promise<void>;
    close(): Promise<void>;
    submit(text: string, mode?: CommandBarMode): Promise<void>;
    state(): Promise<CommandBarState>;
  }
  interface ZeoApi {
    commandBar: CommandBarApi;
    onCommandBarChange(listener: (state: CommandBarState) => void): () => void;
  }
  ```

  Every method is an `ipcRenderer.invoke` round trip (`state()` included; the
  renderer never caches it). `onCommandBarChange` mirrors `onStateChange`: the
  push channel carries the full `CommandBarState` and the listener returns an
  unsubscribe function. Channel constants: `commandBarOpen`, `commandBarClose`,
  `commandBarSubmit`, `commandBarState`, `commandBarChange`. `submit` resolves
  the text in main via `resolveInput`. A `null` result closes the bar (when open) and
  resolves without navigating or creating anything. Otherwise the effective
  mode decides the action: `navigate` calls `tabs.navigate` on the active tab;
  `new-tab` creates a tab with the resolved url and activates it. The
  effective mode is the explicit `mode` argument when given, else the open
  bar's mode, else `navigate`; `navigate` with no active tab falls back to
  `new-tab`. `submit` then closes the bar if it was open and resolves once the
  store mutation and broadcast are done; it does not wait for the page load.
  Submitting while the bar is closed is the headless seam e2e drives and must
  not depend on overlay visibility.
- `TabsApi` gains `navigate(id, url): Promise<void>`. Main updates the stored
  url and the title fallback synchronously, broadcasts, then calls `loadURL`
  on the tab's view; the promise resolves once the load has been initiated,
  not settled, matching how `tabs.create` behaves today. A failed load keeps
  the stored url (the tab shows where the user asked to go) and follows the
  existing `failedLoads` retry-on-activation path. Unknown ids and ids outside
  the active space reject, as the other tab commands do.
- Concurrent navigations are last-request-wins. Each tab carries a
  navigation sequence number in main, incremented per `navigate` call; a
  newer `loadURL` aborts the older one (Electron rejects the older promise
  with `ERR_ABORTED`), and the older call's rejection is ignored when its
  sequence is no longer current, so it never marks `failedLoads` or logs an
  error. The stored url is the last requested url until the first
  `did-navigate` for the current sequence, after which it follows the
  webContents. `did-navigate` handlers read the webContents url, never a
  captured value, so a late event from an aborted load cannot overwrite a
  newer one.
- IPC channel constants for every new method and for the state push.

### 3. Overlay view (main)

- The bar renders in its own `WebContentsView` loading the same renderer
  bundle with a `?view=command-bar` query (the renderer picks the component
  from the query). The overlay is created once per window, hidden by default,
  and kept as the topmost child: whenever a tab view is added, main re-adds
  the overlay so it stays above every tab view. It never receives a partition
  (default session, like the sidebar renderer) and shares the sidebar's
  preload.
- Bounds: horizontally centered over the page region (right of the sidebar),
  top at 12% of the content height, width `max(0, min(640, pageWidth - 48))`,
  height fixed for this PRD (a single input row); recomputed on window resize
  and on every open. A zero-width page region yields a zero-width, zero-height
  rectangle; the bounds function never returns a negative dimension. A pure bounds function in `packages/core` (next to
  `SIDEBAR_WIDTH`) computes the rectangle from the content size and is unit
  tested.
- Open: main sets the state, shows the overlay, focuses its webContents, and
  pushes the state so the renderer seeds the input. In `navigate` mode with no
  active tab, the bar opens in `new-tab` mode instead.
- Close: hides the overlay, resets state, pushes it, and returns focus to the
  active tab's webContents (or the sidebar when there is none). The bar also
  closes when its webContents loses focus (click on the page or sidebar) and
  when the window loses focus.
- Menu accelerators, in the existing application-menu pattern: `Cmd+L` opens
  in `navigate` mode; `Cmd+T` now opens in `new-tab` mode instead of creating
  a tab directly, so a new tab appears only when the user submits. The
  sidebar's new-tab button does the same through `commandBar.open("new-tab")`.
- Live URL tracking: `did-navigate` and `did-navigate-in-page` on a tab's
  webContents update the stored url (and the title fallback when no page title
  has arrived yet) and broadcast, so the sidebar and the `navigate` prefill
  always reflect where the tab actually is. This resolves the url half of
  issue #29; favicon staleness stays open.

### 4. Bar renderer (ui)

- A thin component: one text input, seeded from `initialText` on every open
  (text selected in `navigate` mode), `Enter` calls `commandBar.submit`,
  `Escape` calls `commandBar.close`. No local state beyond the input value; no
  resolution logic in the renderer.
- Visual style follows the sidebar conventions in `App.css`: same font, a
  rounded panel with a subtle border and shadow, no backdrop dimming.

### 5. Tests

- Core: `resolveInput` rules above; overlay bounds function.
- e2e:
  - Open the bar over the bridge in `navigate` mode, assert the overlay
    webContents becomes visible and the input holds the active tab's URL;
    type a URL, press Enter, assert the active tab's stored url updates and
    the bar closes.
  - Open in `new-tab` mode, submit `example.org`, assert a new active tab
    exists with url `https://example.org/` (or the resolved form) and the tab
    count grew by one; assert opening the bar alone did not create a tab.
  - Submit a bare word, assert the active tab's url starts with the default
    search engine query URL and carries the encoded term.
  - `Escape` closes without navigating or creating a tab.
  - Headless: with the bar closed, `commandBar.submit("example.net")`
    navigates the active tab and leaves the bar closed;
    `commandBar.submit("example.net", "new-tab")` creates a tab; submitting
    whitespace-only text changes nothing.
  - Core-level scheme rejection surfaces end to end: submitting
    `file:///etc/hosts` leaves the active tab on a search-engine url, never a
    `file:` url.
  - Menu accelerators `Cmd+L` and `Cmd+T` are registered on the expected
    items (same assertion style as the existing accelerator tests).
  - Two rapid `commandBar.submit` calls on the same tab without awaiting the
    first load: the stored url ends on the second target, the tab is not in
    the failed-load set (activating it does not reload the first target), and
    the page's final `location.href` is the second target.
  - In-tab navigation (a link click or `location.assign` inside the tab
    page) updates the tab's url in the broadcast state.

## Constraints

- Input resolution, state types, and bounds math live in `packages/core`;
  main only wires views, focus, and IPC; the renderer stays thin.
- No suggestions, history, or fuzzy matching of any kind in this PRD.
- Fresh-launch seed behavior is unchanged: a database with no data still
  seeds one default tab.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.
- Version bump to 0.0.9 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: `Cmd+L` opens the bar prefilled with the current URL,
  typing a URL or a search term and pressing Enter navigates the active tab;
  `Cmd+T` and the sidebar new-tab button open an empty bar, and submitting
  opens a new tab; `Escape` or clicking the page dismisses it; the sidebar's
  tab entries follow in-page navigation.
- CI green on the merge request branch.
