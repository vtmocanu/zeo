# PRD 5.2 — Per-site allowlist and blocking settings

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 5.3
(`prds/done/5.3-csp-cosmetic-filtering.md`) merged: `@zeo/adblock` owns one
long-lived `Blocker` whose `attach` installs `onBeforeRequest`,
`onHeadersReceived`, the cosmetic preload and the two cosmetic IPC handlers
on a profile session, every callback delegating to the current engine.

Blocking today is all-or-nothing per launch: the only switch is the global
`enabled` flag. A site that breaks under filtering can only be fixed by
turning blocking off everywhere. This PRD adds a per-site allowlist that
bypasses all three layers (network, CSP, cosmetic) for documents on
allowlisted hosts, exposes it over the bridge and the command bar, and
lands the first settings surface of the app with a content-blocking
section (global toggle, filter-list version and manual refresh, allowlist
management). PRD 6.5 extends that surface with search engine and profile
settings. Feature #85.

## Deliverables

### 1. Allowlist model (core)

- New module `packages/core/src/allowlist.ts`, pure, exported from the
  barrel:

  ```ts
  /** Hostname for http(s) urls, null for every other scheme. */
  function siteKeyForUrl(url: string): string | null;
  /** Canonical allowlist entry for user input, null when unusable. */
  function normalizeAllowlistHost(input: string): string | null;
  /**
   * True when host equals an entry or is a subdomain of a non-IP entry;
   * an IP-literal entry or host matches only an identical host.
   */
  function hostMatchesAllowlist(host: string, entries: Iterable<string>): boolean;
  ```

- `siteKeyForUrl` parses with `URL`; it returns the lowercased `hostname`
  for `http:` and `https:` only and `null` for anything else (`about:`,
  `file:`, `data:`, `chrome:`, an unparsable string).
- `normalizeAllowlistHost` trims, lowercases, strips one leading `*.`,
  strips a leading scheme and everything from the first `/`, `?` or `#`,
  strips a trailing `.`, then validates by parsing `"http://" + value` and
  requiring the parsed `hostname` to equal the value with no userinfo and
  no port. IPv4 and bracketed IPv6 literals pass; an empty result, an
  embedded space, or a value the parser rewrites returns `null`.
- `hostMatchesAllowlist(host, entries)` first detects IP literals — an IPv4
  dotted-quad or a bracketed IPv6 literal — on the entry or the host: when
  either side is an IP literal the only match is exact equality
  (`host === entry`), and the suffix rule below is skipped so an
  attacker-controlled host such as `foo.127.0.0.1` can never match the entry
  `127.0.0.1`. For every other entry it is true when `host === entry` or
  `host.endsWith("." + entry)`; `example.com` matches `www.example.com` and
  `a.b.example.com`, never `notexample.com`. An IP literal matches only
  itself: `127.0.0.1` matches `127.0.0.1` alone, never `foo.127.0.0.1`, and
  `[::1]` matches only `[::1]`.
- `BlockingState` gains `allowlist: readonly string[]`, sorted with
  `localeCompare`, no duplicates. `initialBlockingState` takes it as a
  third parameter defaulting to `[]`. Pure reducers with unit tests:
  `addAllowlistHost(state, host)` (returns the same reference when
  present) and `removeAllowlistHost(state, host)` (same reference when
  absent). Blocked counts are untouched by both: `blockedByTab` keeps
  counting until the tab's next origin change as in PRD 5.1, so a user who
  allowlists a site sees the old count until they reload.

### 2. Persistence

- Schema version 3. `SCHEMA_VERSION` in `packages/core/src/persistence.ts`
  becomes 3; `MIGRATION_STEPS[3]` in `apps/desktop/src/main/db.ts` creates
  `blocking_allowlist (host TEXT PRIMARY KEY, createdAt INTEGER NOT NULL)`
  and the `DDL` for a fresh database includes the same table.
  `migrationAction` and the runner are unchanged; `db.test.ts` covers
  2 → 3 on a database seeded at version 2 and a fresh create at 3.
- `db.ts` helpers, each a single prepared statement: `readAllowlist():
  string[]` (ordered by host), `insertAllowlistHost(host: string, createdAt:
  number): void` (`INSERT OR IGNORE`), `deleteAllowlistHost(host: string):
  void`. The table is outside `writeState` and `readState`, exactly like
  `meta.enabled`.

### 3. Bypass hook (`packages/adblock`)

- `Blocker` gains `setBypass(predicate: BypassPredicate | null): void` where
  `type BypassPredicate = (documentUrl: string) => boolean`. The predicate is
  stored on the blocker, survives `refresh()`, `attach` and `detach`, and is
  cleared by `dispose()`. `null` restores full filtering. The library never
  sees it; every check happens in the wrapper's own callbacks.
- Document url resolution, one function `documentUrlOf(details)` used by
  the network and CSP callbacks: for a main-frame request
  (`resourceType === "mainFrame"`) the request url itself (`details.url`),
  resolved before reading `details.frame` — during a provisional navigation
  `frame.url` still names the source document, so a blocked destination
  reached from an allowlisted source must key on the destination, not the
  frame; otherwise, when `details.frame` is non-null and not destroyed, the
  url of its top frame (`frame.top?.url ?? frame.url`); otherwise `""`. An
  empty document url never consults the predicate and
  the request is filtered normally, so a request whose owning frame Electron
  cannot name is never silently exempted.
- `onBeforeRequest`: when a predicate is set and returns true for the
  document url, the callback answers `callback({})` at once; the engine is
  not consulted, no `request-blocked` event fires, so allowlisted pages
  never increment `blockedByTab`. Otherwise the engine handles the request
  exactly as today.
- `onHeadersReceived`: same check; a bypassed frame response passes
  `{ responseHeaders: details.responseHeaders, statusLine:
  details.statusLine }` through unchanged, with no CSP appended.
- Cosmetic handlers: after the existing sender checks pass, both handlers
  compute the document url from `event.senderFrame.top?.url ??
  event.senderFrame.url`. For a bypassed document,
  `inject-cosmetic-filters` resolves without injecting anything and
  `is-mutation-observer-enabled` resolves `false`, so the preload stops
  observing that document.
- A predicate that throws counts as `false` for that call; the error is
  logged at most once per blocker instance.
- Unit tests with the fake session: bypass true skips the engine and calls
  `callback({})`; bypass false reaches the engine; a `mainFrame` request
  with no frame uses its own url; a `mainFrame` request whose frame url is an
  allowlisted source but whose `details.url` destination is not allowlisted is
  filtered (keys on `details.url`, not the frame url — an Electron 44
  navigation regression); a sub-resource with no frame is filtered
  even when the predicate would say true; `refresh()` keeps the predicate;
  `setBypass(null)` restores blocking; the CSP callback passes headers
  through for a bypassed frame; the inject handler resolves without calling
  `getCosmeticsFilters` for a bypassed frame; a throwing predicate filters
  normally and logs once.

### 4. Bridge and main wiring

- `packages/core/src/ipc.ts`:

  ```ts
  interface BlockingApi {
    setEnabled(enabled: boolean): Promise<void>;
    state(): Promise<BlockingState>;
    allowSite(host: string): Promise<void>;
    disallowSite(host: string): Promise<void>;
    refreshLists(): Promise<boolean>;
  }
  ```

  Channel constants `blockingAllowSite: "zeo:blocking:allow-site"` (payload
  `string`, response `void`), `blockingDisallowSite:
  "zeo:blocking:disallow-site"` (payload `string`, response `void`),
  `blockingRefresh: "zeo:blocking:refresh"` (no payload, response
  `boolean`). Allowlist changes ride the existing `stateChange` broadcast.
- Main holds `allowlist: Set<string>` loaded from `readAllowlist()` before
  the blocker is created, and installs one predicate at blocker creation
  (both the fixture and the production path): `(url) => { const host =
  siteKeyForUrl(url); return host !== null && hostMatchesAllowlist(host,
  allowlist); }`. The predicate reads the live set, so allowlist edits need
  no further wrapper calls.
- `allowSite(host)` runs on the main thread in this order: (1) normalize;
  a `null` result rejects with `TypeError` and changes nothing; (2) if the
  set has the host, resolve; (3) `insertAllowlistHost` synchronously; on
  throw reject and change nothing; (4) add to the set and to
  `blocking.allowlist` through the reducer; (5) broadcast.
  `disallowSite(host)` mirrors it with `deleteAllowlistHost` and the remove
  reducer; an absent host resolves without side effects.
- `refreshLists()`: rejects when `blocker === null`; otherwise returns
  `blocker.refresh()`. While a refresh is in flight every further call
  returns the same promise. A manual refresh runs whether or not blocking
  is enabled; the daily timer keeps skipping while disabled.
- `CommandContext.activeTab` gains `siteHost: string | null` (from
  `siteKeyForUrl(tab.url)`) and `siteAllowlisted: boolean`
  (`hostMatchesAllowlist(siteHost, allowlist)` when `siteHost` is set).
  `commandContextOf()` fills both; `refreshCommandState()` runs after every
  allowlist change so the menu and command rows follow.
- Commands, all `menu: "view"`, dispatched through `executeCommand`:
  - `blocking.allowSite`, "Disable Blocking on This Site", keywords
    `allow`, `whitelist`, `allowlist`, `site`, `ads`; enabled when
    `activeTab.siteHost !== null && !activeTab.siteAllowlisted`; handler
    calls `allowSite(activeTab.siteHost)`.
  - `blocking.disallowSite`, "Enable Blocking on This Site", keywords
    `block`, `allowlist`, `site`, `ads`; enabled when
    `activeTab.siteAllowlisted`; handler removes the longest allowlist
    entry that `activeTab.siteHost` matches.
  - `settings.open`, "Open Settings", keywords `settings`, `preferences`,
    `options`, accelerator `CmdOrCtrl+,`, always enabled.
  - `settings.close`, "Close Settings", no keywords beyond `settings`,
    accelerator `null`, enabled while the settings view is open; hidden from
    menus (`menu: null`).
- Unit tests in `commands.test.ts` cover the four enablement rules.

### 5. Settings view

- Third render mode of the `apps/ui` bundle: `?view=settings` mounts
  `<Settings />`. Main hosts it in a dedicated `WebContentsView`
  (`settingsView`), default session, same preload as the sidebar, created
  lazily on the first `settings.open` and kept for the window's lifetime.
  While open it sits above every tab view and below the command-bar overlay
  (main re-adds the overlay after adding the settings view) and covers the
  content area: `settingsBounds(contentWidth, contentHeight)` in
  `packages/core/src/layout.ts` returns `{ x: SIDEBAR_WIDTH, y: 0, width:
  contentWidth - SIDEBAR_WIDTH, height: contentHeight }`, applied on open
  and on every window resize. Closing removes the view from the window and
  focuses the active tab view.
- `TabsState` gains `settingsOpen: boolean`. `broadcast()` sends
  `stateChange` to the settings view as well as to the sidebar while the
  view exists. The settings renderer subscribes with `onStateChange` and
  reads the initial snapshot with `blocking.state()`; it never keeps its own
  copy of blocking data.
- Keyboard: `Escape` inside the settings view dispatches `settings.close`
  through the `commands` bridge. `Cmd+,` toggles: `settings.open` while open
  is a no-op that focuses the view.
- Content, one column with a left section list holding a single entry
  "Content blocking" (6.5 adds more), all controls reachable with Tab and
  operable with Space or Enter:
  - Global toggle: checkbox `data-testid="settings-blocking-enabled"`
    bound to `blocking.enabled`; change calls `blocking.setEnabled`. A
    rejected call re-renders from state and shows the error text in
    `data-testid="settings-blocking-error"`.
  - Filter lists: `data-testid="settings-blocking-version"` shows
    `listVersion`; button `data-testid="settings-blocking-refresh"` calls
    `refreshLists()`, is disabled while pending, and afterwards shows
    "Updated" or "Update failed" in `data-testid="settings-blocking-refresh-result"`.
  - Allowlist: text input `data-testid="settings-allowlist-input"` plus
    button `data-testid="settings-allowlist-add"` (Enter in the input
    submits too) calling `allowSite`; a rejected call shows "Enter a host
    name such as example.com" in `data-testid="settings-allowlist-error"`
    and keeps the input. Rows `data-testid="settings-allowlist-row"` with
    `data-host` render `blocking.allowlist` in state order, each with a
    button `data-testid="settings-allowlist-remove"` calling `disallowSite`.
    An empty list shows `data-testid="settings-allowlist-empty"`.
- Styling follows `App.css` conventions (BEM-ish classes, existing dark
  palette); no new CSS tooling.

### 6. Sidebar

- `TabRow` renders the shield whenever `blockedCount > 0` or the tab's site
  is allowlisted. For an allowlisted site the glyph gets
  `tab-item__shield--allowlisted`, `data-allowlisted="true"`, and the
  title/aria-label "Blocking disabled on <host>"; the count is omitted.
  The renderer computes "allowlisted" with `siteKeyForUrl` and
  `hostMatchesAllowlist` imported from `@zeo/core` over `state.blocking.allowlist`.

### 7. Tests

- Unit: allowlist module (normalization table, matching rules including
  IPv4 and IPv6 near-misses — entry `127.0.0.1` does not match
  `foo.127.0.0.1`, and a bracketed IPv6 entry matches only itself), reducers,
  wrapper bypass tests (§3), db helpers and migration, command enablement,
  `settingsBounds`.
- e2e (`e2e/tests/blocking.spec.ts`, loopback fixture server and
  `ZEO_ADBLOCK_FILTERS` from PRD 5.1, cosmetic fixture from PRD 5.3):
  - Load `/page.html`: the blocked pixel is dropped. `allowSite("127.0.0.1")`
    then reload: the server sees `/blocked/pixel.png`, `blockedByTab` for
    the tab is unchanged from before the reload, `state().allowlist` equals
    `["127.0.0.1"]`, and the sidebar shield for the tab has
    `data-allowlisted="true"`.
  - On the 5.3 cosmetic fixture page, the element hidden by the cosmetic
    filter is visible after allowlisting and reloading, and the CSP fixture
    response carries no injected `Content-Security-Policy`.
  - `disallowSite("127.0.0.1")` then reload: the pixel is dropped again and
    the count increments.
  - `allowSite("not a host")` rejects; `allowSite("HTTP://Example.COM/x")`
    stores `example.com`.
  - Command bar: with the fixture tab active, query `allow` lists
    `blocking.allowSite`; accepting it adds `127.0.0.1`; query `block` then
    lists `blocking.disallowSite` and not `blocking.allowSite`.
  - Relaunch: the allowlist persists and the first load of `/page.html`
    after relaunch is not filtered.
  - `settings.open` via the commands bridge: a page with
    `data-testid="settings"` appears, `settingsOpen` is true, the allowlist
    row for `127.0.0.1` is present, clicking its remove button empties the
    list, typing `example.org` and pressing Enter adds a row, `Escape`
    closes the view and `settingsOpen` is false.
  - `refreshLists()` on the fixture blocker resolves `false` (the fixture
    engine has no remote source, so `refresh()` is a no-op that never swaps the
    engine) and `listVersion` still starts with `fixture:`.

## Constraints

- `packages/core` stays Electron-free; only `packages/adblock` imports the
  adblocker library; the wrapper never calls the library's own allowlist
  or `$document` exception machinery for this feature.
- No settings beyond content blocking, no filter-list selection, no
  import/export of the allowlist in this PRD.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged; CI stays offline-deterministic.
- Version bump to 0.0.15 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: on a site with blocked requests, "Disable Blocking on
  This Site" from the command bar makes the next reload load the page
  unfiltered with the shield showing the allowlisted state; `Cmd+,` opens
  the settings view with the host listed; removing it there re-enables
  blocking on the next reload; both survive a relaunch.
- CI green on the merge request branch.
