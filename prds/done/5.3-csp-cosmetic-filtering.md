# PRD 5.3 — CSP injection and cosmetic filtering

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 5.1
(`prds/done/5.1-content-blocking-engine.md`) merged: `@zeo/adblock` owns
one long-lived `Blocker` whose `attach` registers `onBeforeRequest` on a
profile session and delegates every callback to the current engine, so a
list refresh swaps the engine without re-registering session hooks.

Network blocking is the only layer wired today. Two layers that the uBlock
Origin lists rely on are parsed by the engine but never applied: `$csp`
rules, which need an `onHeadersReceived` handler adding a
`Content-Security-Policy` to the response, and cosmetic filters
(`##.selector` element hiding and `##+js(...)` scriptlets), which need a
preload script in every browsing frame and an IPC round trip so the engine
can push CSS and scriptlets into the page. Without them, sites whose ads
are hidden rather than blocked show empty ad slots and anti-adblock scripts
run unopposed. This PRD wires both layers inside `packages/adblock` with
the same current-engine delegation as `onBeforeRequest`. Per-site
allowlisting and the blocking settings surface remain PRD 5.2. Feature
#85, follow-up to issue #83.

## Deliverables

### 1. Session hooks (`packages/adblock`)

- Session ownership is process-wide: a module-level map records which
  blocker owns each session, and a module-level slot records which blocker
  holds the IPC handlers. `attach` throws, before registering anything, when
  the session is owned by another blocker that has not been disposed, or
  when the IPC handlers are held by another such blocker. Ownership is
  taken as the first step of attach and released by detach and by
  dispose, so at most one blocker ever holds a session's hooks and preload
  and at most one holds the handlers; resources are never shared between
  blockers, only handed over after a dispose.
- `attach(session)` registers, on an unattached session, in this order:
  (0) ownership of the session, as above; (1) the wrapper's IPC handlers if
  this is the blocker's first attach ever (see §2); (2) `session.webRequest.onBeforeRequest({ urls:
  ["<all_urls>"] }, ...)` as today; (3) `session.webRequest
  .onHeadersReceived({ urls: ["<all_urls>"] }, ...)` with the wrapper's CSP
  callback below; (4) the preload: a module-level registry shared by every
  blocker in the process maps a session to the id returned by
  `session.registerPreloadScript({ type: "frame", filePath: preloadPath
  })`; attach registers only when the registry has no id for the session
  and otherwise reuses the existing one, so a session carries at most one
  adblocker preload for the life of the process no matter how many
  blockers attach it; (5) the session joins the attached set. Every callback reads `this.engine` at
  call time, so a refresh keeps working for all of them without touching
  the session. Attach stays idempotent per session: a second call is a
  no-op and never registers a second preload script.
- Attach is failure-atomic. If any step throws, the steps already done for
  that session are undone in reverse order (`unregisterPreloadScript`,
  `onHeadersReceived(null)`, `onBeforeRequest(null)`; the IPC handlers stay
  once registered, see §2), the session is not added to the attached set,
  and the error is rethrown. `attachedSessions()` therefore never lists a
  session with partial hooks, which keeps main's rollback loop in
  `setEnabled` and the drop-old-blocker cleanup correct.
- `detach(session)` removes exactly what attach installed, in reverse
  order: unregisters the session's preload id and deletes the registry
  entry, passes `null` to `onHeadersReceived`, then `null` to
  `onBeforeRequest`, and releases ownership of the session. It is
  best-effort: every removal is attempted even when an earlier one throws,
  the session leaves the attached set and ownership either way, and the
  first error is rethrown at the end. A failed preload
  unregister keeps the registry entry, so the preload is reused rather
  than duplicated by the next attach of that session (by this blocker or
  a replacement); a failed hook removal is retried by the next attach's
  own registration, which replaces the listener under Electron's
  single-listener rule. `attachedSessions()` therefore lists exactly the
  sessions with complete hooks, and main's `setEnabled(false)` rollback
  re-attaches the sessions already detached and the failing session
  itself, which reconciles it. Detaching an unattached session is a
  no-op, and detaching one session leaves every other attached session's
  hooks and preload in place.
- Electron allows one listener per `webRequest` event per session. The
  wrapper is the sole owner of `onBeforeRequest` and `onHeadersReceived`
  on every attached session; that ownership is documented on `attach`, and
  `apps/desktop` registers no other listener for those events on profile
  sessions. There is no Electron API to detect a foreign listener, so this
  is a contract, not a runtime check.
- CSP callback, owned by the wrapper (the library's `onHeadersReceived` is
  not used because it folds the filter directives into the page's own
  policy, where a later duplicate directive is ignored and a filter could
  loosen a stricter site policy). For a `mainFrame` or `subFrame` response,
  the callback asks the current engine for `getCSPDirectives(request)`;
  when it returns directives, the callback appends them as one additional
  value to the response's `Content-Security-Policy` header array (creating
  the header when absent) and passes every other header, including
  `Content-Security-Policy-Report-Only` and every existing
  `Content-Security-Policy` value, through unchanged. Browsers enforce each
  policy independently, so the result is the intersection: a filter can
  only tighten, never loosen. Any other resource type, and any frame
  response with no matching directives, passes through: the callback
  receives `{ responseHeaders: details.responseHeaders, statusLine:
  details.statusLine }` unchanged, never an empty object, so the original
  headers are never dropped.
- No `BlockingState` counter changes: neither a CSP addition nor a hidden
  element is a blocked request, so `blockedByTab` and
  `blockedUnattributed` count network blocks only, exactly as in PRD 5.1.

### 2. Cosmetic injection channel

- The preload script is a small, self-contained CommonJS file
  (`packages/adblock/preload/cosmetic-preload.cjs`) that the wrapper ships
  itself rather than the library's `@ghostery/adblocker-electron-preload`
  entry. The library preload gates its whole injection behind
  `window === window.top`, so it never fires in a cross-origin child frame —
  incompatible with the per-frame injection this PRD requires — so `@zeo/adblock`
  ships its own frame-agnostic preload that runs in every frame (only the
  `devtools://` exclusion is kept) and imports no library code (just
  `require("electron").ipcRenderer` and DOM APIs), so it works under the default
  `sandbox: true`. Because `@zeo/adblock` is bundled into `apps/desktop`'s main
  bundle, in-wrapper path resolution is unreliable; instead the file is copied to
  `out/preload/cosmetic-preload.cjs` by the desktop build and its path is passed
  to attach through the `internals.preloadPath` seam. It runs in the frame's
  isolated world under the default `sandbox: true` and `contextIsolation: true`
  of tab views, and exposes nothing to page scripts.
- The preload talks to main over the library's two channels,
  `@ghostery/adblocker/inject-cosmetic-filters` (`(url, dom?) =>
  Promise<void>`; the first call per document carries no `dom`, later calls
  carry observed classes, ids, and hrefs) and
  `@ghostery/adblocker/is-mutation-observer-enabled` (`() =>
  Promise<boolean>`). The wrapper's handlers are registered with
  `ipcMain.handle` once, during the blocker's first `attach`, and stay
  registered for the blocker's lifetime, across every later detach, so an
  invoke that Electron dispatches after the last session detached still
  reaches a handler and resolves instead of rejecting in the preload.
- `dispose()` is the blocker's terminal transition. It detaches every
  attached session, then removes both handlers; every step is attempted
  even when an earlier one throws, and the first error is rethrown at the
  end, so a detach failure can never leave a handler registered or block
  a replacement blocker's first attach. Whatever a failed detach leaves
  behind is safe for a replacement: a preload still registered is reused
  through the registry (never duplicated, so a frame sends one invoke),
  and a hook still installed is overwritten by the replacement's attach.
  After `dispose`, `attach` throws and `attachedSessions()` is empty. An
  invoke Electron dispatches after `dispose` finds no handler and rejects
  inside the sending frame's preload, which the library preload reports on
  the frame's console and otherwise ignores; this is accepted because main
  disposes only during startup cleanup, before any tab view exists, and
  never while frames are live. At most one blocker
  may hold the handlers at a time, so main disposes the outgoing blocker
  before creating a replacement (§3).
- Handler contract. Both handlers first check the sender: the event's
  `senderFrame` must be non-null and not destroyed, `event.sender.session`
  must be in the attached set, and for `inject-cosmetic-filters` the `url`
  argument must equal `event.senderFrame.url`. When any check fails (a
  frame in the sidebar or overlay renderer, a session detached after the
  preload's send, a frame that navigated since it sent, or a url the frame
  does not own), `inject-cosmetic-filters` resolves with `undefined`
  having injected nothing and `is-mutation-observer-enabled` resolves with
  `false`. For an accepted sender the wrapper performs the injection
  itself, targeting the sending frame: it parses the url with the
  library's URL parser, calls `this.engine.getCosmeticsFilters(...)` with
  the same argument set the library uses (base, injection, and hostname
  rules on the first call, DOM rules on update calls, caller context from
  the event), and when the result is active applies `styles` to that
  frame and runs each script with
  `event.senderFrame.executeJavaScript(script)` with no user-gesture
  argument, so a scriptlet cannot reach gesture-gated APIs such as
  fullscreen or popups. Styles reach the frame two ways: when
  `senderFrame` is the top frame (`senderFrame === sender.mainFrame`),
  `event.sender.insertCSS(styles, { cssOrigin: "user" })`; for a child
  frame, which has no `insertCSS`, a `<style>` element carrying the rules
  is appended to that frame's document head through
  `senderFrame.executeJavaScript`, marked with a fixed `data-zeo-cosmetic`
  attribute and replaced rather than duplicated on later update calls.
  Each frame of a page, including cross-origin child frames, gets its own
  preload instance and its own invoke, so each is filtered by its own
  url. `is-mutation-observer-enabled` returns
  `this.engine.config.enableMutationObserver`. Scriptlets are trusted to
  the same degree as network filters: they come from the same lists and
  the engine's bundled resources, never from page content, and the sending
  frame is the only frame they run in.
- Ordering is documented, not changed: a frame loaded before attach (or
  before a refresh) keeps the CSS and scriptlets it already received until
  its next navigation; a frame loaded after detach receives nothing; a
  frame loaded while attached receives the first injection during document
  start and DOM-driven updates as the page mutates.
- Electron is reached through a seam so the package's unit tests still run
  under plain Vitest: `BlockerIpc { handle(channel, listener): void;
  removeHandler(channel): void }`. Production resolves it lazily from
  Electron's `ipcMain` on the first attach (never at module load).
  `CreateBlockerOptions` and `createBlockerFromFilters` accept it under an
  optional `internals?: { ipc?: BlockerIpc; preloadPath?: string;
  resources?: string }` argument, where `resources` is scriptlet resource
  text in the library's resources format applied to the parsed engine with
  `updateResources`; `createBlockerFromFilters(filters, listVersion?,
  internals?)` keeps its two existing positional parameters unchanged.

### 3. Main process (`apps/desktop`)

- Every existing attach and detach call site (startup gate, `setEnabled`,
  profile creation, profile remap, the cap-lost swap) gets CSP and
  cosmetic filtering through the wrapper with no change. `setEnabled(false)`
  therefore also stops injection for frames loaded afterwards, and
  `setEnabled(true)` restores it, with the same ordering and rollback
  contract as PRD 5.1 §2.
- The startup cleanup path, where main today detaches every session of a
  blocker it is about to drop, calls `dispose()` instead, so the IPC
  handlers are released before any replacement blocker's first attach; a
  thrown error is caught and logged once, and startup continues.
- Failure state, defined for the case that path already has (blocking
  set-up failed, `blocker` stays `null`): the in-memory `BlockingState`
  reports `enabled: false` for the rest of the launch while the persisted
  value is left untouched, so the next launch retries, and
  `setEnabled(true)` while `blocker` is `null` rejects with an error and
  changes nothing (persisted value, sessions, and state unchanged). The
  app never reports blocking enabled with no engine attached. The cap-lost path never holds two blockers at once (the fixture
  path and the real path are exclusive), so no other site changes.
- The `ZEO_ADBLOCK_FILTERS` fixture path builds the engine with
  `ElectronBlocker.parse` as today; cosmetic and `$csp` filters in the
  fixture file are honoured because the library's default config loads
  cosmetic filters. When `ZEO_ADBLOCK_RESOURCES` also names a file, its
  text is passed as `internals.resources` so fixture scriptlets resolve.
  Both variables are read only on the fixture path.

### 4. Tests

- Unit (`packages/adblock`, fake session extended with
  `onHeadersReceived`, `registerPreloadScript` returning a fresh id, and
  `unregisterPreloadScript`; fake `BlockerIpc` recording handled channels;
  fake IPC event with a `sender` recording `insertCSS` and
  `executeJavaScript` calls and exposing a `session`):
  - attach registers both request hooks, one preload script, and both IPC
    handlers; a second attach registers nothing more; attaching a second
    session registers its hooks and preload but no second IPC handler;
    detaching one of two sessions removes only its hooks and preload;
    detaching the last session keeps both handlers; a second blocker
    attaching a session the first still owns throws before touching the
    fake session or the fake IPC, and the first blocker's hooks, preload,
    handlers, and `attachedSessions()` are unchanged; a second blocker
    attaching a different, unowned session while the first holds the IPC
    handlers throws before touching that session or the fake IPC, leaving
    that session with no hooks and no preload and the handler set
    unchanged; after the first blocker disposes successfully (its preload
    unregistered and the registry entry deleted), the second attaches
    that session, registers one new preload, and registers its own
    handlers; `dispose` detaches the
    remaining sessions and removes both handlers, and a later attach
    throws; `dispose` where one session's detach throws still detaches
    the others, removes both handlers, and rethrows the first error;
    after a `dispose` whose preload unregister threw, a replacement
    blocker attaching the same fake session registers no second preload
    (the fake session reports one registered script) and, on a fake IPC
    invoke from a frame of that session, the fake sender records exactly
    one `insertCSS` call; detaching an unattached session is a no-op.
  - attach where `registerPreloadScript` throws leaves both request hooks
    cleared, the session unattached, and rethrows; detach where
    `unregisterPreloadScript` throws still clears both request hooks,
    drops the session from `attachedSessions()`, and rethrows; a following
    attach of that session reuses the registered preload id, registers no
    new preload, and lists the session again.
  - the CSP callback, for a `mainFrame` response matching a `$csp` filter:
    with no existing header, the header holds exactly the filter
    directives; with two existing `Content-Security-Policy` values and a
    `Content-Security-Policy-Report-Only` header, the result holds the two
    original values unchanged, the filter directives as a third value, and
    the report-only header untouched; a filter `script-src 'self'` on a
    response already carrying `script-src 'none'` keeps `'none'` as its
    own value (the intersection still forbids scripts); a matching
    `subFrame` response is treated like a main frame; an unmatched frame
    response and a matched `image` response, each carrying non-empty
    headers and a status line, pass through with those exact headers and
    status line in the callback.
  - after `refresh`, the same registered callbacks use the new engine: a
    `$csp` rule and an element-hiding rule present only in the new lists
    take effect through the CSP callback and the `inject-cosmetic-filters`
    handler with no re-attach.
  - the IPC handlers, for an accepted top-frame sender, insert the
    engine's styles with `cssOrigin: "user"` on the sender and run each
    scriptlet through the sender frame's one-argument `executeJavaScript`
    (no user-gesture flag); for an accepted child-frame sender they run
    the style element script and the scriptlets through that frame's
    `executeJavaScript` and never call `insertCSS`; for a sender whose
    session is not attached, whose `senderFrame` is null, or whose `url`
    differs from `senderFrame.url`, `inject-cosmetic-filters` calls
    nothing and resolves `undefined` and `is-mutation-observer-enabled`
    resolves `false`; after the last detach an invoke still resolves this
    way; after `dispose` the fake IPC holds no handlers.
- e2e (`e2e/tests/blocking.spec.ts`, same loopback fixture server, offline):
  the server also serves `/cosmetic.html`, whose body holds
  `<div class="zeo-ad-slot">` above a visible `<p id="marker">`, and
  `/csp.html`, whose body holds an inline `<script>` that sets
  `document.title` to `scripted` and a `<p id="marker">`; the server sends
  no `Content-Security-Policy` header of its own. The fixture list gains
  the generic element-hiding rule `##.zeo-ad-slot`, the rule
  `/csp.html$csp=script-src 'none'`, and the scriptlet rule
  `##+js(zeo-mark)` scoped to the fixture host, with a fixture resources
  file (`ZEO_ADBLOCK_RESOURCES`) defining `zeo-mark.js` as a script that
  sets `document.documentElement.dataset.zeoScriptlet = "ran"`.
  Assertions:
  - After loading `/cosmetic.html` in a tab: the ad slot's computed
    `display` becomes `none` (polled, since injection follows document
    start), the marker stays visible, and
    `document.documentElement.dataset.zeoScriptlet` becomes `"ran"`;
    `blockedByTab` for the tab has no entry and `blockedUnattributed` is
    0.
  - After loading `/csp.html`: `document.title` is not `scripted` and the
    marker rendered.
  - `blocking.setEnabled(false)`, then load both pages in new tabs: the ad
    slot is displayed, the scriptlet marker is absent, and the title reads
    `scripted`. `setEnabled(true)` and load again in new tabs: all three
    effects return without a relaunch.
  - A second space on a distinct profile loading `/cosmetic.html` hides
    the slot and runs the scriptlet.
  - Cross-origin child frame: the server is reachable as both
    `127.0.0.1` and `localhost`, two origins on one port. `/frame.html`
    on the first origin embeds `<iframe src="http://localhost:<port>
    /cosmetic.html">` next to its own visible `<p id="marker">`. After
    loading it in a tab, inside the child frame the ad slot's computed
    `display` is `none` and the scriptlet marker is `"ran"`, while the
    top document's marker stays visible and its `dataset.zeoScriptlet`
    is unset (the scriptlet rule is scoped to the frame's host only).
  - Failure state: launched with `ZEO_ADBLOCK_FILTERS` naming a missing
    file and a persisted `enabled` of true, the app starts, `state()`
    reports `enabled: false`, `setEnabled(true)` rejects, and a relaunch
    with a valid fixture file reports `enabled: true` and blocks again.
  - Default-session isolation, checked directly in the main process
    through Playwright's `electronApp.evaluate`: while blocking is enabled,
    `session.defaultSession.getPreloadScripts()` contains no script whose
    path includes `cosmetic-preload`, and each profile
    partition's session contains exactly one; after `setEnabled(false)`
    the profile sessions contain none. In addition, the sidebar renderer
    appends a sentinel `<div class="zeo-ad-slot">` to its own document
    from the test and asserts its computed `display` is not `none` while
    the profile tab's element with the same class is hidden.

## Constraints

- Only `packages/adblock` imports the adblocker library and its preload
  package; `packages/core` stays Electron-free and is untouched by this
  PRD except where a shared type is needed (none expected).
- No per-site allowlist, no settings UI, no filter-list management UI.
- No new IPC channel in `packages/core/src/ipc.ts`: the cosmetic channels
  are the library's own, spoken only between its preload and the wrapper.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged. CI stays offline-deterministic.
- Version bump to 0.0.14 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app with the default lists: a news site that reserves ad
  slots shows no empty placeholders where the list hides them; toggling
  content blocking off and reloading brings the placeholders back.
- CI green on the merge request branch.
