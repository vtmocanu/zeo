# PRD 3.4 — SQLite persistence for spaces, profiles, and tabs

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 3.3
(`prds/3.3-spaces-ui.md`) merged: the full space/profile/tab model works in
memory and vanishes on quit.

Persistence lives in the main process using SQLite via `better-sqlite3`;
schemas and (de)serialization logic live in `packages/core`.

## Deliverables

### 1. Persistence schema and codec (core)

- A versioned schema module in `packages/core`: tables for profiles, spaces,
  tabs (open and archived, with pin state, order, `lastActiveAt`,
  `archivedAt`), and a meta table carrying the schema version plus the
  nullable `activeSpaceId`. Each space row carries its own nullable
  `activeTabId`; both selection columns must reference an existing row of the
  right scope or be null.
- Pure functions that serialize the store to row sets and rebuild a store
  from row sets, with unit tests round-tripping every field, order, active
  space, and each space's active tab.
- A migration runner keyed on the schema version: version 1 creates the
  tables; unknown newer versions abort the load rather than destroying data.

### 2. Database wiring (main)

- `better-sqlite3` database at `app.getPath("userData") + "/zeo.db"`, opened
  before the first window; WAL mode.
- Load on launch: rebuild the store from the database when it has data,
  otherwise seed as today. "Has data" means any persisted space, open tab, or
  archived tab — a database whose only tabs are archived is restored, not
  re-seeded (the current `store.list().length === 0` seed check is
  insufficient and must be replaced). A corrupt or unreadably-new database is
  moved aside to `zeo.db.bak-<timestamp>` and the app starts fresh.
- Save: full snapshot replacement inside one transaction — delete rows absent
  from the snapshot, then upsert the rest — debounced (~1s) after any state
  mutation, plus a final synchronous write on `before-quit`. Tests cover
  removal (a deleted tab/space/profile stays gone after relaunch), not only
  round-trip preservation.
- Restored tabs recreate their views lazily: only the active tab of the
  active space gets a view at startup (the current rebuild loop creating a
  view per open tab changes accordingly); every other tab gets its view on
  first activation. The e2e asserts a non-active restored tab has no view
  until activated.

### 3. Tests

- Unit: schema round-trip, migration runner behavior on empty, current, and
  too-new versions.
- e2e: create a second space with a named tab, pin one tab, archive another,
  relaunch the app in the same test (new Electron launch against the same
  `userData` dir), assert spaces, tab order, pin state, archived list, and
  active ids all survive. A second relaunch case: archive every tab, relaunch,
  assert no new default tab is seeded and the archived list is intact.

## Constraints

- SQL statements and the `better-sqlite3` dependency only in `apps/desktop`;
  `packages/core` stays free of Electron and node-specific imports.
- Native module note: `better-sqlite3` must be rebuilt for Electron's ABI
  (`electron-rebuild` or the electron-vite equivalent) and CI must cover it on
  both Linux and macOS jobs without touching `.github/workflows/` — if the
  existing workflow cannot build it, stop and report instead of editing
  workflows.
- History and downloads tables are out of scope (epic 6).
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: quit and relaunch restores spaces, profiles, tabs,
  order, pins, archived tabs, and the active space/tab.
- CI green on the merge request branch.
