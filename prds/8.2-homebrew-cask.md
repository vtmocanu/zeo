# PRD 8.2 — Homebrew cask and tap publish

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md` (Distribution section). This
PRD is feature 8.2 of epic 8 (issue #88, "Packaging and release"), whose
done-when is: `brew install --cask vtmocanu/tap/zeo --no-quarantine` on a clean
Mac produces a launchable zeo at the tagged version.

Blocked by #20 (release prerequisites): the `HOMEBREW_TAP_TOKEN` fine-grained
PAT (contents:write, scoped to `vtmocanu/homebrew-tap` only) exists as an
Actions secret; workflow files under `.github/workflows/` are committed by a
human, never by the automation token or a uzi run; and the open question
whether the shared taskfile at github.com/vtmocanu/task needs a cask variant is
tracked there, not resolved here. This PRD carries the "blocked by #20" marker.

Depends on sibling PRD 8.1 (packaging), written in parallel. PRD 8.1 owns the
ad-hoc signed app bundle, the dmg/zip artifacts, the GitHub Release, and the
base `release.yml` with its build-and-release job; it publishes the artifact
names. This PRD does NOT redefine packaging. It consumes exactly two of 8.1's
release assets: the arm64 dmg (the cask `url` target) and the `SHA256SUMS`
release asset (the source of the cask `sha256`). The exact artifact filenames
are owned by 8.1; this PRD's assumed names — the arm64 dmg
`zeo-<version>-arm64.dmg` and the aggregate `SHA256SUMS` file — match PRD 8.1's
published `artifactName: ${productName}-${version}-${arch}.${ext}` (which yields
exactly `zeo-<version>-arm64.dmg`) and the `SHA256SUMS` asset 8.1 generates over
those artifacts. The implementing run re-confirms both against 8.1's published
names at rebase time rather than hard-coding a name 8.1 might change.

The distribution model, restated from the design doc: the tap repository is
`vtmocanu/homebrew-tap` (users add it as `vtmocanu/tap`); a cask template in
THIS repo is the source of truth; a `v*` tag triggers a release workflow that
builds the artifacts, creates the GitHub Release, renders the template
(version, url, sha256), and pushes the rendered cask to the tap using the
`HOMEBREW_TAP_TOKEN` secret; Homebrew-managed installs are told to run
`brew upgrade`.

This is a run-sized packaging feature. It adds no schema change, no `apps/ui`
or `packages/core` behavior, and no e2e coverage: the deliverables are a cask
template, a render script and its unit test, a release-workflow template, a
README section, and a `pnpm cask:check` verification script.

## Deliverables

### 1. Cask template (`packaging/homebrew/zeo.rb.tmpl`)

- A new file `packaging/homebrew/zeo.rb.tmpl`: the Ruby cask body with three
  render placeholders, exactly:

  ```ruby
  cask "zeo" do
    version "{{VERSION}}"
    sha256 "{{SHA256}}"

    url "{{URL}}"
    name "zeo"
    desc "Keyboard-first, workspace-centric browser for macOS"
    homepage "https://github.com/vtmocanu/zeo"

    depends_on arch: :arm64

    app "zeo.app"

    zap trash: [
      "~/Library/Application Support/zeo",
      "~/Library/Caches/zeo",
      "~/Library/Logs/zeo",
      "~/Library/Preferences/com.zeo.browser.plist",
      "~/Library/Saved Application State/com.zeo.browser.savedState",
    ]

    caveats <<~EOS
      zeo is distributed as an ad-hoc signed build — it carries no Apple
      Developer ID signature and is not notarized. Install it with
      --no-quarantine so macOS Gatekeeper does not block the first launch:

        brew install --cask vtmocanu/tap/zeo --no-quarantine

      If zeo was installed without --no-quarantine, the first launch is
      blocked with "zeo can't be opened because Apple cannot check it for
      malicious software." Open it once via Finder (right-click zeo.app →
      Open), or clear the quarantine attribute:

        xattr -dr com.apple.quarantine "/Applications/zeo.app"

      zeo is Homebrew-managed here, so update it with:

        brew upgrade --cask zeo
    EOS
  end
  ```

- Placeholders and their exact substitution rules:
  - The template contains exactly three placeholder tokens, each the literal
    ASCII sequence `{{VERSION}}`, `{{SHA256}}`, and `{{URL}}`, and each appears
    only inside the double-quoted `version`, `sha256`, and `url` string
    literals respectively.
  - Before substitution, each of the three tokens must appear exactly once in
    the template — no expected token missing and none duplicated. §2's
    validation enforces this on the template text (a missing token that a stale
    hard-coded literal has silently replaced would otherwise survive the
    leftover-`{{` check below and ship the wrong version, url, or checksum).
  - Rendering replaces every occurrence of each token with the corresponding
    input value by literal string substitution (the input is inserted verbatim,
    not treated as a regular expression or interpolation).
  - After rendering, no `{{` substring may remain anywhere in the output (§2's
    validation enforces this; a leftover token is a render failure, never a
    silently shipped cask).
- The `zap trash:` paths are derived from the app's real on-disk footprint,
  not guessed:
  - `~/Library/Application Support/zeo` holds the SQLite database
    (`zeo.db`, `zeo.db-wal`, `zeo.db-shm`) written to `app.getPath("userData")`
    in `apps/desktop/src/main/db.ts` (`dbPath()`), the cached adblock engine
    `adblock-engine.bin` written to the same `userData` directory in
    `apps/desktop/src/main/index.ts`, and Chromium's per-`persist:` partition
    session storage (cookies, local/IndexedDB storage, caches) that Electron
    keeps under `userData`.
  - `~/Library/Caches/zeo` and `~/Library/Logs/zeo` are the macOS
    per-application cache and log directories Electron/Chromium create for the
    app.
  - `~/Library/Preferences/com.zeo.browser.plist` and
    `~/Library/Saved Application State/com.zeo.browser.savedState` are keyed by
    the app's `CFBundleIdentifier`.
  - The app-name segment `zeo` derives from `app "zeo.app"` (the staged bundle
    name), which fixes `app.getName()` / `CFBundleName` to `zeo`. The bundle
    identifier `com.zeo.browser` is a static string in this template (not a
    render placeholder — it does not change per version); it is the
    `CFBundleIdentifier` that PRD 8.1's packaging config sets (`appId:
    com.zeo.browser`), and the value PRD 8.1's macOS build job verifies on the
    packaged bundle (its CI smoke asserts `CFBundleIdentifier == com.zeo.browser`
    and that the staged bundle is `zeo.app`). 8.2 consumes this bundle identity
    as a named contract from 8.1 rather than re-verifying the dmg here: the
    `publish-cask` job (§3) runs on `ubuntu-latest` and only downloads
    `SHA256SUMS`, so it cannot mount the macOS dmg to read its `Info.plist`
    (`hdiutil`/`PlistBuddy` are macOS-only). The implementing run re-confirms
    `com.zeo.browser` against 8.1's packaging config at rebase and keeps these
    two identifier-keyed `zap` entries in step with it.

### 2. Render script (`packaging/homebrew/render.mjs`) and its unit test

- A new file `packaging/homebrew/render.mjs`, a plain Node ESM (`.mjs`) script in
  the style of the existing `apps/desktop/scripts/copy-renderer.mjs` (a
  standalone `.mjs` that uses only `node:*` built-ins and needs no TypeScript
  build). It uses `node:fs`, `node:path`, `node:url`, and `node:process`, runs
  standalone in the release workflow with only Node on PATH (no `pnpm install`,
  no monorepo build), and does NOT import from `@zeo/core` or any workspace
  package.
- The module exports pure functions and, when invoked as a CLI (guarded by the
  standard `import.meta.url` main check), runs `main()`:

  ```js
  // Pure: substitute the three tokens into the template text.
  export function renderCask(template, { version, url, sha256 });
  // Pure: throw a RenderError with a numeric `code` when an input, the template
  // shape, or the rendered text is invalid; return normally when everything is
  // valid.
  export function validate({ version, url, sha256, expectedVersion, template, rendered });
  ```

- CLI usage:

  ```
  node packaging/homebrew/render.mjs \
    --version <version> --url <url> --sha256 <sha256> [--out <path>]
  ```

  - Inputs: `--version` (the release version, e.g. `0.0.20`, no leading `v`),
    `--url` (the full GitHub Release asset download URL for the arm64 dmg), and
    `--sha256` (the dmg's SHA-256 digest). `--out` is the output file path; when
    omitted the rendered cask is written to stdout.
  - The template is read from `packaging/homebrew/zeo.rb.tmpl` resolved relative
    to the script's own location (via `import.meta.url`), so the CWD does not
    matter. The expected version for validation is read from the root
    `package.json` `version` field, resolved relative to the script location.
  - Output: on success the rendered cask is written to `--out` (or stdout) and
    the process exits `0`. On any validation failure nothing is written to the
    `--out` path (no partial or invalid file is ever produced) and a
    human-readable message is printed to stderr.
- Validation and exit codes. Argument parsing is the CLI `main()`'s job: a
  missing or unknown flag exits `1`. Given the parsed inputs, the template text,
  and the rendered text, the pure `validate` throws a `RenderError` carrying the
  matching `code`, and `main()` exits with it. The template-shape check (code
  `6`) runs first, on the template before substitution; the remaining checks run
  in the order listed:
  - `1` — usage error: a required argument (`--version`, `--url`, `--sha256`) is
    missing or blank, or an unknown flag is given.
  - `2` — `--sha256` is not exactly 64 lowercase hexadecimal characters
    (`/^[0-9a-f]{64}$/`).
  - `3` — `--version` does not equal the root `package.json` `version` (the tag
    and the committed version have drifted).
  - `4` — `--url` does not contain `--version` as a delimited token: the version
    must appear in the URL followed by a non-`[0-9.]` boundary character (e.g.
    the release-tag segment `/v<version>/`), so a stale URL whose embedded
    version merely shares the new version as a prefix is rejected (`--version
    0.0.2` does not match inside `.../zeo-0.0.20-arm64.dmg`).
  - `5` — after substitution the rendered text still contains a `{{` sequence (a
    placeholder was not replaced — template drift).
  - `6` — the template is missing one of the three placeholder tokens
    (`{{VERSION}}`, `{{SHA256}}`, `{{URL}}`), or contains one more than once —
    checked against the template text before substitution, so a stale literal
    that has displaced a placeholder cannot pass validation (code `5` only
    catches a token left unreplaced after substitution, not one absent from the
    template).
  - `0` — success.
- A new file `packaging/homebrew/render.test.mjs` using Node's built-in test
  runner (`node:test` + `node:assert`) — no new dependency and no lockfile or
  workspace change. It drives the exported pure functions directly against a
  committed fixture template (a minimal `zeo.rb.tmpl`-shaped string carrying the
  three placeholders, checked in under `packaging/homebrew/__fixtures__/` or
  inlined in the test), passing `expectedVersion` explicitly so the test is
  independent of the repo's current `package.json` version. Cases:
  - a valid `{version, url, sha256}` renders text that contains each substituted
    value and no remaining `{{`;
  - a `sha256` that is too short, too long, uppercase, or non-hex is rejected
    with code `2`;
  - a `version` that does not match `expectedVersion` is rejected with code `3`;
  - a `url` that omits the version, or embeds it only as a prefix of a longer
    version (e.g. `0.0.2` inside `0.0.20`), is rejected with code `4`;
  - a template with an extra unreplaced placeholder is rejected with code `5`;
  - a template with `{{VERSION}}` (respectively `{{SHA256}}`, `{{URL}}`) removed
    — a stale literal in its place — is rejected with code `6`, and a template
    that repeats an expected token is likewise rejected with code `6`;
  - a missing required input is rejected with code `1`.

### 3. Tap publish job (`docs/release/release.yml.template`)

- The tap-publish job is delivered as part of `docs/release/release.yml.template`
  — a template file under `docs/`, NOT a workflow under `.github/workflows/`.
  Per #20 a human commits the real `.github/workflows/release.yml` from this
  template; the implementing run writes nothing under `.github/workflows/`.
- PRD 8.1 introduces `docs/release/release.yml.template` with the tag trigger
  and the build-and-release job. This PRD appends a `publish-cask` job to that
  same template (creating the template with a documented placeholder for 8.1's
  build job if 8.1 has not landed at rebase). The job `needs:` 8.1's
  build-and-release job so it runs only after the GitHub Release exists:

  ```yaml
  publish-cask:
    needs: build-and-release # PRD 8.1's job: builds artifacts, creates the Release
    runs-on: ubuntu-latest
    steps:
      - name: Check out zeo (cask template + render script only)
        uses: actions/checkout@v7
        with:
          persist-credentials: false

      - uses: actions/setup-node@v7
        with:
          node-version: 24

      - name: Fail fast when the tap token is absent
        env:
          HOMEBREW_TAP_TOKEN: ${{ secrets.HOMEBREW_TAP_TOKEN }}
        run: |
          if [ -z "$HOMEBREW_TAP_TOKEN" ]; then
            echo "HOMEBREW_TAP_TOKEN is not set; cannot publish the cask." >&2
            exit 1
          fi

      - name: Download SHA256SUMS from the release
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release download "${GITHUB_REF_NAME}" \
            --repo "${GITHUB_REPOSITORY}" --pattern SHA256SUMS --dir .

      - name: Render the cask
        run: |
          version="${GITHUB_REF_NAME#v}"
          dmg="zeo-${version}-arm64.dmg"
          sha256="$(awk -v f="$dmg" '$2 == f || $2 == "*"f {print $1}' SHA256SUMS)"
          if [ -z "$sha256" ]; then
            echo "no SHA256SUMS entry for ${dmg}" >&2
            exit 1
          fi
          url="https://github.com/${GITHUB_REPOSITORY}/releases/download/${GITHUB_REF_NAME}/${dmg}"
          mkdir -p out
          node packaging/homebrew/render.mjs \
            --version "$version" --url "$url" --sha256 "$sha256" --out out/zeo.rb

      - name: Publish to the tap
        env:
          HOMEBREW_TAP_TOKEN: ${{ secrets.HOMEBREW_TAP_TOKEN }}
        run: |
          version="${GITHUB_REF_NAME#v}"
          git clone --depth 1 \
            "https://x-access-token:${HOMEBREW_TAP_TOKEN}@github.com/vtmocanu/homebrew-tap.git" tap
          mkdir -p tap/Casks
          cp out/zeo.rb tap/Casks/zeo.rb
          cd tap
          git config user.name "zeo-release-bot"
          git config user.email "zeo-release-bot@users.noreply.github.com"
          git add Casks/zeo.rb
          if git diff --cached --quiet; then
            echo "tap already carries zeo ${version}; nothing to publish."
            exit 0
          fi
          git commit -m "zeo ${version}"
          git push origin HEAD
  ```

- Contract, made explicit for each path:
  - Ordering: `publish-cask` runs after `build-and-release` (via `needs:`), i.e.
    after the Release and its `SHA256SUMS` and dmg assets exist.
  - Input: the arm64 dmg's digest is read from the downloaded `SHA256SUMS` by
    filename `zeo-<version>-arm64.dmg` (PRD 8.1's `artifactName` output),
    tolerating the leading `*` binary marker `shasum` emits; a missing entry
    fails the job (no cask is pushed against an unknown digest).
  - Idempotency: after staging `Casks/zeo.rb`, `git diff --cached --quiet`
    detects that the tap already carries an identical cask for this version, in
    which case the job commits and pushes nothing and exits `0` — re-running a
    tag, or a workflow retry, does not create an empty commit or fail.
  - Failure semantics: a missing `HOMEBREW_TAP_TOKEN` fails the job fast with a
    clear message (never a silent skip); a rejected push (non-fast-forward,
    e.g. the tap advanced concurrently) fails the job because `git push` is
    never forced.
  - Isolation: the job clones and pushes ONLY the tap repository; it makes no
    commit, tag, or push to this repository. Its only interaction with this repo
    is the read-only `checkout` (template + render script) and the read-only
    `gh release download`.
  - Identity: commits are authored by the named bot identity `zeo-release-bot`
    (`zeo-release-bot@users.noreply.github.com`) with the message `zeo <version>`.
- The template file carries a header comment stating that it is the source for a
  human-committed `.github/workflows/release.yml` (#20) and that the automation
  token cannot write workflow files.

### 4. Install and upgrade story (README)

### 6. Verification (`pnpm cask:check`)

- A new root `package.json` script, `cask:check`, mapped to
  `node packaging/homebrew/cask-check.mjs` (a new Node ESM helper alongside the
  render script). Adding this script leaves every existing root script name and
  behavior unchanged. `cask:check` performs, in order:
  1. runs the render unit tests (`node --test` over
     `packaging/homebrew/render.test.mjs`), failing `cask:check` if any fail;
  2. renders `packaging/homebrew/zeo.rb.tmpl` against a committed fixture — the
     root `package.json` version for `--version`, a fixture arm64-dmg release
     URL that contains that version, and a fixture 64-hex `sha256` — to a
     gitignored temporary path, asserting the render exits `0` and the output
     contains no `{{`;
  3. if `brew` is on PATH (`command -v brew`), runs `brew audit --cask` (and/or
     `brew style --cask`) against the rendered fixture cask and fails
     `cask:check` on a non-zero result; if `brew` is absent, prints a clear
     message (e.g. "Homebrew not found; skipping brew audit/style") and exits
     `0`.
- A CI-only cask job in `.github/workflows/ci.yml` is out of scope (the
  workflow-file rule): `cask:check` is a local/manual gate and is also exercised
  by the release workflow's render step (§3). Consequently the render script's
  unit tests run under `pnpm cask:check`, not under the standard `pnpm test`
  (`pnpm -r`) gate, which is left unchanged; this trade-off is accepted so the
  release-time renderer stays a dependency-free standalone script and the run
  adds no new pnpm workspace or lockfile entry.

### 7. Tests

- The render-script unit tests in §2 (placeholder substitution and each
  validation failure) are the only tests this PRD adds. There is no schema
  change, so no `packages/core` or `apps/desktop` unit test changes. The
  Playwright e2e suite is unaffected — no e2e test is added or changed.

### 8. Versioning

- The implementing run bumps the root `package.json` version by one patch to the
  next free version at rebase time and adds a matching dated section to
  `CHANGELOG.md` (Keep a Changelog). The exact number is deliberately NOT fixed
  in this PRD: it is `main`'s current patch plus one at the moment 8.2 rebases
  (e.g. if `main` is at `0.0.19`, 8.2 lands `0.0.20`; if a sibling milestone
  merged first, take the next free patch). The changelog entry summarizes the
  Homebrew cask distribution (tap, `brew install --cask ... --no-quarantine`,
  `brew upgrade`, ad-hoc signed / `--no-quarantine` note).

## Constraints

- `packages/core` must not import `electron` (lint-enforced) — unaffected: all
  new code lives under `packaging/`, never in `packages/core`, and there is no
  new core module.
- No Apple Developer ID signing and no notarization: the build is ad-hoc signed
  and the cask installs with `--no-quarantine`.
- TypeScript strict mode is unaffected: the new scripts are plain Node ESM
  (`.mjs`), like the existing `apps/desktop/scripts/copy-renderer.mjs`; any
  TypeScript touched stays strict with no unexplained `any`.
- Nothing under `.github/workflows/` is created or modified by the run; the
  release workflow is delivered as `docs/release/release.yml.template` for a
  human to commit (#20).
- The tap repository `vtmocanu/homebrew-tap` is never modified by a uzi run;
  only the release workflow, running with `HOMEBREW_TAP_TOKEN`, writes to it.
- Conventional Commits; no AI attribution in any commit, file, or message.
- Only the arm64 artifact is consumed (`depends_on arch: :arm64`); the dmg name
  `zeo-<version>-arm64.dmg` and the `SHA256SUMS` layout match PRD 8.1's
  `artifactName: ${productName}-${version}-${arch}.${ext}` and its aggregate
  `SHA256SUMS`, re-confirmed against 8.1 at rebase.

## Acceptance criteria

- `brew install --cask vtmocanu/tap/zeo --no-quarantine` on a clean Apple
  Silicon Mac produces a launchable zeo at the tagged version, and
  `brew upgrade --cask zeo` moves it to a newer tagged version (epic 8
  done-when).
- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` stays
  green (this PRD adds only packaging scripts, docs, and a version bump — no
  product-behavior or schema change — and the new `.mjs` scripts pass
  `eslint .`), and `pnpm cask:check` is green — it
  renders the template against the fixture and either runs `brew audit --cask`
  successfully or prints a clear skip message when Homebrew is absent, exiting
  `0` in both cases.
- `packaging/homebrew/render.mjs` renders the cask from `version`, `url`, and
  `sha256`, and fails closed with the documented non-zero exit code on an
  invalid sha256, a version/`package.json` mismatch, a url that omits the
  version, a template missing (or duplicating) an expected placeholder token, an
  unreplaced placeholder, or a missing argument.
- The `publish-cask` job in `docs/release/release.yml.template` renders and
  pushes `Casks/zeo.rb` to `vtmocanu/homebrew-tap` after the Release is created,
  is idempotent when the tap already carries that version, fails fast on a
  missing token or a rejected push, and never writes to this repository.
- CI green on the merge request branch.
