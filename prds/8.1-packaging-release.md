# PRD 8.1 — Packaging and release workflow

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`, milestone 8 (packaging and
Homebrew release). Feature epic 8, issue #88 ("ship zeo to other Macs").

This PRD delivers 8.1: an ad-hoc signed macOS app bundle, `dmg` and `zip`
artifacts, a local `pnpm package` command, and a tag-driven release workflow
that creates the GitHub Release. The Homebrew cask template and the tap push
are **PRD 8.2** and are out of scope here — but the release workflow this PRD
specifies leaves a clearly named job boundary (a `cask` job with
`needs: [release]`) where 8.2 appends its render-and-push job, and 8.1's
workflow itself reads only the built-in `GITHUB_TOKEN`, never
`HOMEBREW_TAP_TOKEN`.

Blocked by #20 (release prerequisites): the `HOMEBREW_TAP_TOKEN` actions secret
(a fine-grained PAT scoped to `vtmocanu/homebrew-tap`, needed by 8.2) and the
rule that **workflow files are committed by a human, never by an automation
run**. Because of that rule, the implementing run **does not** create or modify
anything under `.github/workflows/`. Instead it delivers the full workflow
contents as `docs/release/release.yml.template` plus a `docs/release/README.md`
step for a human to copy the template to `.github/workflows/release.yml` and
commit it (§6).

Packager choice — **electron-builder**, justified against the existing build:
`apps/desktop` already builds with electron-vite (`electron-vite build && node
scripts/copy-renderer.mjs`), which emits `apps/desktop/out/{main,preload}` and
copies the separately-built `@zeo/ui` renderer into `apps/desktop/out/renderer`
(and the `@zeo/adblock` cosmetic frame preload into `out/preload`). electron-
builder *consumes a pre-built directory* — it never owns the transpile/bundle
step — so it slots in as a pure post-build packaging stage over `out/`, leaving
the electron-vite pipeline and the bespoke `copy-renderer.mjs` step untouched.
Electron Forge, by contrast, wants to own the build through its own Vite/Webpack
plugins and a `forge.config`, which would duplicate or replace electron-vite and
the copy-renderer step. electron-builder also gives first-class `dmg` + `zip`
mac targets, ad-hoc signing via `identity: null`, and automatic detection,
unpacking, and Electron-ABI rebuild of the native `better-sqlite3` module — so
it is the lower-friction choice and the one electron-vite's own docs recommend.

Non-goals (design doc): builds are ad-hoc signed only — no Developer ID
signing, no notarization, no hardened runtime, no auto-update, and no Windows or
Linux. v1 ships **arm64 only** (§1).

Versioning is deliberately not fixed here. At rebase the implementing run bumps
root `package.json` to the next free patch version (illustratively `0.0.20` if
no other 8.x PRD lands first — substitute the actually-allocated value) and adds
a dated `CHANGELOG.md` section; the version number is not hard-coded in this
PRD. `apps/desktop/package.json` stays at `0.0.0`; §3 explains how the root
version reaches the packaged bundle.

## Deliverables

### 1. Packager config (`apps/desktop/electron-builder.yml`)

- A new `apps/desktop/electron-builder.yml`, read by electron-builder run with
  `apps/desktop` as its project directory. Contract:

  ```yaml
  appId: com.zeo.browser
  productName: zeo
  directories:
    output: ../../release
    buildResources: build
  files:
    - out/**/*
    - package.json
  asar: true
  asarUnpack:
    - "**/*.node"
  npmRebuild: true
  mac:
    category: public.app-category.productivity
    icon: build/icon.png
    identity: null
    hardenedRuntime: false
    target:
      - target: dmg
        arch: [arm64]
      - target: zip
        arch: [arm64]
  artifactName: ${productName}-${version}-${arch}.${ext}
  ```

- `appId` is `com.zeo.browser` and `productName` is `zeo` (the `.app` is
  `zeo.app`). These two are load-bearing: the CI smoke (§8) asserts the
  packaged bundle's `CFBundleIdentifier` equals `com.zeo.browser`.
- `directories.output: ../../release` resolves to a repo-root `release/`
  directory (relative to `apps/desktop`); `buildResources: build` is
  `apps/desktop/build/`.
- `files: [out/**/*, package.json]` ships only the electron-vite output tree
  and the app manifest. `@zeo/core`, `@zeo/adblock`, and `@zeo/ui` are bundled
  into `out/` by electron-vite / copied by `copy-renderer.mjs`, so they are
  **not** shipped again from `node_modules`; only the runtime-externalized
  `better-sqlite3` and `@ghostery/adblocker-electron` are collected from the app
  `dependencies` by electron-builder's production-dependency walk. The cosmetic
  frame preload already lives at `out/preload/cosmetic-preload.cjs`, so it is
  inside `out/**/*` and needs no separate entry.
- `asar: true`. Native binaries (`**/*.node`, i.e. `better-sqlite3`'s binding)
  are unpacked via `asarUnpack` so they load as real files. `npmRebuild: true`
  (electron-builder's default) rebuilds `better-sqlite3` against Electron 44's
  ABI at package time — required because `pnpm-workspace.yaml` sets
  `allowBuilds.better-sqlite3: false`, so pnpm never builds the module on
  install. If the cosmetic frame preload cannot be resolved through the asar
  layer by `session.registerPreloadScript`, `out/preload/cosmetic-preload.cjs`
  is added to `asarUnpack` too; the acceptance smoke (§8) plus a manual launch
  on macOS confirm the packaged app opens a page and blocks (no ABI/asar break).
- Artifacts: `artifactName: ${productName}-${version}-${arch}.${ext}` produces
  exactly `zeo-<version>-arm64.dmg` and `zeo-<version>-arm64.zip`, where
  `<version>` is the root version threaded in by §3. The unpacked app is at
  `release/mac-arm64/zeo.app`.
- **arm64 only for v1**, recommended and stated: Apple Silicon is the current
  Mac baseline; producing ad-hoc-unsigned x64 or universal builds doubles build
  time and artifact size to serve a shrinking, Rosetta-covered Intel base.
  Adding x64 or universal later is a one-line `mac.target[].arch` change and
  does not reshape the workflow or the artifact-name contract.

### 2. Ad-hoc signing (`apps/desktop/electron-builder.yml`, mac)

- `mac.identity: null` disables Developer ID signing; `hardenedRuntime: false`;
  there is no notarization step and no `afterSign` notarize hook. This is the
  `codesign --sign -` (ad-hoc) equivalent the design doc calls for.
- Contract: the produced `zeo.app` **must carry an ad-hoc signature** — arm64
  apps do not launch unsigned — verifiable with `codesign -dv zeo.app` reporting
  `Signature=adhoc`. If electron-builder's `identity: null` path leaves the
  arm64 app unsigned, the implementing run adds an `afterPack` hook (referenced
  from the config as `afterPack: build/after-pack.cjs`) that runs
  `codesign --force --deep --sign - "<app path>"`; no Developer ID, no hardened
  runtime, no notarization is introduced by the hook.
- Gatekeeper behavior on first launch: a `dmg`/`zip` downloaded through a
  browser carries the `com.apple.quarantine` extended attribute, so an ad-hoc
  signed, un-notarized zeo is blocked on first open ("zeo cannot be opened
  because the developer cannot be verified" / "is damaged"), requiring a manual
  right-click → Open or `xattr -dr com.apple.quarantine`. The **intended**
  install path is PRD 8.2's `brew install --cask … --no-quarantine`, which
  installs the app without the quarantine attribute so Gatekeeper does not block
  it. The artifacts themselves are not quarantined at creation time; quarantine
  is applied by the downloading agent.

### 3. Local packaging (`scripts/package.mjs`, root `package` script, `.gitignore`)

- Root `package.json` gains `"package": "pnpm build && node scripts/package.mjs"`.
- New root ESM script `scripts/package.mjs` (styled after the existing
  `apps/desktop/scripts/copy-renderer.mjs`), whose contract is:
  - **Requires the built renderer and main.** It hard-checks that
    `apps/desktop/out/main/index.js` and `apps/desktop/out/renderer/index.html`
    exist; if either is missing it prints a clear message ("Missing build
    output … run `pnpm build` first") and exits non-zero **without** invoking
    electron-builder.
  - **Threads the root version in.** It reads the version from the root
    `package.json` and invokes electron-builder in `apps/desktop` with
    `--mac --arm64 --publish never -c.extraMetadata.version=<root version>`.
    `extraMetadata.version` overrides `apps/desktop/package.json`'s `0.0.0`, so
    the bundled app manifest, the Info.plist `CFBundleShortVersionString` /
    `CFBundleVersion`, the `${version}` in `artifactName`, and `app.getVersion()`
    at runtime all equal the single source of truth — the root version. This is
    why `apps/desktop/package.json` can stay at `0.0.0`.
  - **Exit status.** The script exits with electron-builder's exit code; any
    packaging failure (config error, native rebuild failure, signing failure)
    is a non-zero exit that fails `pnpm package`.
- Output directory: `release/` at the repo root (from §1's
  `directories.output`). The run adds `/release/` to `.gitignore` so artifacts
  are never committed. `pnpm package` is a macOS operation (a mac `.app`/`dmg`
  cannot be produced on Linux); §"Constraints" states where it runs.

### 4. Version/changelog logic (`packages/core/src/release.ts` + test)

- New Electron-free pure module `packages/core/src/release.ts`, exported from
  the `@zeo/core` barrel (`packages/core/src/index.ts`). Domain-pure release
  helpers, unit-testable in the existing `packages/core` Vitest runner:

  ```ts
  export interface ChangelogSection {
    version: string;
    date: string; // ISO date, "YYYY-MM-DD"
    body: string; // section markdown below the heading, trimmed, non-empty
  }

  /**
   * The `## [<version>] - <YYYY-MM-DD>` section for `version` from CHANGELOG
   * markdown, or null when that version has no section, the date is not a
   * valid ISO `YYYY-MM-DD`, or the body (up to the next `## ` heading) is
   * empty/whitespace. The `## [Unreleased]` heading (no date) never matches.
   */
  export function parseChangelogSection(
    markdown: string,
    version: string,
  ): ChangelogSection | null;
  ```

- `parseChangelogSection` reads only the requested version's section: it starts
  at that version's heading and stops at the next `## ` heading (or end of
  file), so a later version's notes never leak into the body. The body is the
  release-notes text used verbatim as the GitHub Release body (§6).
- Unit tests (`packages/core/src/release.test.ts`): a well-formed changelog
  returns the section with its date and trimmed body; a version with no section
  returns `null`; `## [Unreleased]` (no date) is never returned; a section whose
  date is not `YYYY-MM-DD` returns `null`; a section with an empty body returns
  `null`; the body for one version excludes the next version's notes.

### 5. Release-check tooling (`scripts/release-check.mjs`, `scripts/changelog-section.mjs`, root scripts)

- Root `package.json` gains
  `"release:check": "pnpm --filter @zeo/core run build && node scripts/release-check.mjs"`
  (it self-builds `@zeo/core` so the pure helper is available without a full
  `pnpm build`) and `@zeo/core: "workspace:*"` in `devDependencies` so the root
  scripts can `import { parseChangelogSection } from "@zeo/core"`. The
  `pnpm-lock.yaml` update from adding that dependency is committed.
- `scripts/release-check.mjs` (root ESM) verifies, in order, and exits non-zero
  with a specific message on the first failure (it never pushes anything):
  1. reads the root `package.json` `version`;
  2. `parseChangelogSection(CHANGELOG.md, version)` is non-null — i.e. a
     `## [<version>] - <YYYY-MM-DD>` section with a valid date and a non-empty
     body exists (message names the missing/invalid piece);
  3. the working tree is clean — `git status --porcelain` is empty (message
     lists the dirty paths).
  It is the local pre-flight a maintainer runs before pushing a tag; the
  authoritative tag-equals-version gate lives in the workflow (§6).
- `scripts/changelog-section.mjs <version>` (root ESM) prints the changelog
  body for `<version>` to stdout via `parseChangelogSection`, exiting non-zero
  if absent. The release workflow uses it to build the GitHub Release body.

### 6. Release workflow (delivered as `docs/release/release.yml.template` + `docs/release/README.md`)

- The run **does not** create or modify anything under `.github/workflows/`. It
  writes the **full** workflow contents to `docs/release/release.yml.template`
  and a `docs/release/README.md` telling a human to copy it to
  `.github/workflows/release.yml` and commit it (issue #20), to confirm the
  `HOMEBREW_TAP_TOKEN` secret exists for 8.2 (8.1 does not use it), and how a
  release is cut (§7).
- `docs/release/release.yml.template` contents:

  ```yaml
  name: release

  on:
    push:
      tags:
        - "v*"

  permissions:
    contents: write

  concurrency:
    group: release-${{ github.ref }}
    cancel-in-progress: false

  jobs:
    release:
      runs-on: macos-latest
      outputs:
        version: ${{ steps.version.outputs.version }}
      steps:
        - uses: actions/checkout@v7
          with:
            persist-credentials: false

        - uses: pnpm/action-setup@v6

        - uses: actions/setup-node@v7
          with:
            node-version: 24
            cache: pnpm

        - run: pnpm install --frozen-lockfile

        - id: version
          name: Verify tag matches package.json version
          run: |
            TAG_VERSION="${GITHUB_REF_NAME#v}"
            PKG_VERSION="$(node -p "require('./package.json').version")"
            if [ "$TAG_VERSION" != "$PKG_VERSION" ]; then
              echo "Tag $GITHUB_REF_NAME (version $TAG_VERSION) != package.json version $PKG_VERSION" >&2
              exit 1
            fi
            echo "version=$PKG_VERSION" >> "$GITHUB_OUTPUT"

        - run: pnpm lint
        - run: pnpm typecheck
        - run: pnpm build
        - run: pnpm test
        - run: pnpm package

        - name: Generate SHA256SUMS
          working-directory: release
          run: |
            shasum -a 256 \
              "zeo-${{ steps.version.outputs.version }}-arm64.dmg" \
              "zeo-${{ steps.version.outputs.version }}-arm64.zip" > SHA256SUMS

        - name: Smoke-test the packaged bundle
          env:
            VERSION: ${{ steps.version.outputs.version }}
          run: |
            APP="release/mac-arm64/zeo.app"
            PLIST="$APP/Contents/Info.plist"
            test -d "$APP" || { echo "Packaged app not found at $APP" >&2; exit 1; }
            BUNDLE_ID="$(/usr/libexec/PlistBuddy -c 'Print :CFBundleIdentifier' "$PLIST")"
            SHORT="$(/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "$PLIST")"
            [ "$BUNDLE_ID" = "com.zeo.browser" ] || { echo "CFBundleIdentifier $BUNDLE_ID != com.zeo.browser" >&2; exit 1; }
            [ "$SHORT" = "$VERSION" ] || { echo "CFBundleShortVersionString $SHORT != $VERSION" >&2; exit 1; }

        - name: Build release notes from CHANGELOG
          env:
            VERSION: ${{ steps.version.outputs.version }}
          run: node scripts/changelog-section.mjs "$VERSION" > release/RELEASE_NOTES.md

        - uses: actions/upload-artifact@v4
          with:
            name: zeo-${{ steps.version.outputs.version }}-arm64
            path: |
              release/zeo-${{ steps.version.outputs.version }}-arm64.dmg
              release/zeo-${{ steps.version.outputs.version }}-arm64.zip
              release/SHA256SUMS

        - name: Create GitHub Release
          env:
            GH_TOKEN: ${{ github.token }}
            VERSION: ${{ steps.version.outputs.version }}
          run: |
            gh release create "$GITHUB_REF_NAME" \
              --title "zeo $VERSION" \
              --notes-file release/RELEASE_NOTES.md \
              "release/zeo-$VERSION-arm64.dmg" \
              "release/zeo-$VERSION-arm64.zip" \
              "release/SHA256SUMS"

    # PRD 8.2 appends a `cask` job here:
    #   cask:
    #     needs: [release]
    #     runs-on: ubuntu-latest
    #     steps: render the Homebrew cask template with
    #       needs.release.outputs.version, the release artifact download URL,
    #       and the dmg sha256, then push the rendered cask to
    #       vtmocanu/homebrew-tap using ${{ secrets.HOMEBREW_TAP_TOKEN }}.
    # 8.1 uses only the built-in GITHUB_TOKEN and never reads HOMEBREW_TAP_TOKEN.
  ```

- Triggering: `v*` tags only (no branch or PR trigger). `permissions:
  contents: write` is the sole grant (creating the Release and uploading its
  assets); nothing else is granted. `concurrency` groups by ref with
  `cancel-in-progress: false` so a release in flight is never cancelled by a
  re-push of the same ref.
- Runner: `macos-latest` (Apple Silicon), so the arm64 `.app`/`dmg` builds
  natively with no cross-compile. Toolchain versions match `ci.yml` exactly:
  `actions/checkout@v7` (`persist-credentials: false`), `pnpm/action-setup@v6`,
  `actions/setup-node@v7` with `node-version: 24` and `cache: pnpm`,
  `pnpm install --frozen-lockfile`.
- Job/step order and failure semantics:
  - **Version guard, fail fast.** Before any build, the `version` step compares
    the tag (`${GITHUB_REF_NAME#v}`) to the root `package.json` version and
    `exit 1`s with an explicit message if they differ, aborting the run before
    any build or package work. On success it exports `version` as a job output.
  - Then `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test`, `pnpm
    package`. `build` precedes `test` because `apps/desktop`'s Vitest imports
    the built `@zeo/core`; `package` re-runs `build` (via the root `package`
    script) and produces the artifacts. Any of these failing fails the job.
  - `SHA256SUMS` is generated in `release/` over the two artifacts (standard
    `<sha256>  <filename>` lines). The **CI-only smoke** (§8) asserts the app
    bundle exists and its Info.plist bundle id and version are correct;
    a mismatch fails the job.
  - Artifacts are uploaded (`actions/upload-artifact@v4`) and then the GitHub
    Release is created as the **terminal** step — `gh release create` on the
    pushed tag, titled `zeo <version>`, body = the CHANGELOG section for that
    version, attaching the `dmg`, `zip`, and `SHA256SUMS`. Because Release
    creation is last, any earlier failure means no Release is published.
- The 8.2 boundary: the `release` job exposes `outputs.version`, and the
  trailing comment names the `cask` job (with `needs: [release]`) that 8.2
  appends. No cask/tap logic is inlined into the `release` job.

### 7. In-app version surface — About settings section

- `packages/core/src/ipc.ts`: `TabsState` gains a required
  `appVersion: string`. Main sets it once from `app.getVersion()` and attaches
  it to every state snapshot before `broadcast()`, so it rides the existing
  `stateChange` broadcast with no new channel — exactly as `zoom`, `settings`,
  and `find` do; every `TabsState` producer and test fixture supplies it (a
  placeholder like `"0.0.0"` in fixtures).
- `packages/core/src/settings.ts`: extend the section registry with an About
  section so the settings surface exposes the version:
  - `SettingsSectionId` gains `"about"`:
    `"general" | "blocking" | "profiles" | "history" | "about"`.
  - Append `{ id: "about", title: "About" }` to `SETTINGS_SECTIONS` (last), so
    `nextSection("history") === "about"`, `nextSection("about") === "about"`,
    and `prevSection("about") === "history"`. `nextSection`/`prevSection` are
    unchanged pure index math; only the registry array grows.
- `apps/ui/src/App.tsx` + `apps/ui/src/App.css`: the settings renderer draws a
  fifth section row `data-testid="settings-section-about"` in registry order,
  and its body shows the product name and the version from
  `TabsState.appVersion` in an element `data-testid="settings-about-version"`.
  No new command is added for the About section (it is reached via the section
  list and the existing keyboard navigation), deliberately avoiding any change
  to `EXPECTED_COMMANDS_MODE_IDS` in `e2e/tests/app.spec.ts`.
- `app.getVersion()` returns the packaged version only when packaged; in the
  unpackaged dev/e2e build it returns `apps/desktop/package.json`'s `0.0.0`.
  The e2e (§8) asserts the About element is present and non-empty, not a
  specific number, so the unpackaged suite is unaffected.

### 8. Tests

- Unit (`packages/core`):
  - `release.test.ts` — the `parseChangelogSection` cases in §4.
  - `settings.test.ts` (extending PRD 6.5's) — `SETTINGS_SECTIONS` now lists the
    five ids in order with their titles; `nextSection("history") === "about"`,
    `nextSection("about") === "about"`, `prevSection("about") === "history"`,
    with the existing `general`/`history` end-clamps unchanged.
- e2e (`e2e/tests/settings.spec.ts`, extending PRD 6.5's, unpackaged build,
  offline): the settings section list has the five `settings-section-<id>` rows
  in registry order including `settings-section-about`; opening the About
  section shows a non-empty `settings-about-version`. No test runs against a
  packaged bundle.
- CI-only packaged-bundle smoke: the workflow step in §6 asserts
  `release/mac-arm64/zeo.app` exists and its `Info.plist` carries
  `CFBundleIdentifier == com.zeo.browser` and
  `CFBundleShortVersionString == <tag version>`. It runs **only** in
  `release.yml`, never in `ci.yml`.

## Constraints

- `packages/core` stays Electron-free (lint-enforced): `release.ts` holds only
  pure functions and types; `app.getVersion()` and every packaging concern live
  in `apps/desktop` and the build tooling.
- No Developer ID signing, no notarization, no hardened runtime, no auto-update,
  no Windows/Linux, no x64/universal — **arm64 only** for v1.
- **Nothing under `.github/workflows/` is created or modified by the run**; the
  release workflow is delivered as `docs/release/release.yml.template` + README
  for a human to commit (issue #20). 8.1's workflow uses only `GITHUB_TOKEN`;
  the cask/tap push and `HOMEBREW_TAP_TOKEN` are 8.2.
- TypeScript strict; no `any` without a stated reason.
- `pnpm package` and the packaged-bundle smoke are macOS-only (a mac
  `.app`/`dmg` cannot be produced on Linux); they run on `macos-latest` in
  `release.yml` (or locally on a Mac). Linux/CI (`ci.yml`) and the worker
  validate `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e`,
  the pure `release.ts` unit tests, and `pnpm release:check` — but not the mac
  packaging step.
- `release/` is git-ignored; artifacts are never committed.
- Version bump at rebase to the next free patch version with a dated
  `CHANGELOG.md` section; the number is not fixed in this PRD.
- CI stays offline-deterministic; the e2e suite runs against the unpackaged
  build and is otherwise unchanged.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- On macOS, `pnpm package` produces `release/mac-arm64/zeo.app`,
  `release/zeo-<version>-arm64.dmg`, and `release/zeo-<version>-arm64.zip`, where
  `<version>` is the root `package.json` version; the app is ad-hoc signed
  (`codesign -dv` reports `Signature=adhoc`), and its `Info.plist` carries
  `CFBundleIdentifier == com.zeo.browser` and
  `CFBundleShortVersionString == <version>`. `pnpm package` fails with a
  non-zero exit when the renderer/main are not built or packaging fails.
- `pnpm release:check` passes only when the root version, a matching dated
  `CHANGELOG.md` section with a non-empty body, and a clean working tree are all
  present, and fails with a specific message otherwise.
- `docs/release/release.yml.template` is a `v*`-tag-only workflow with the
  `contents: write` permission block, the concurrency block, the fail-fast
  tag-equals-`package.json`-version guard, the ordered lint/typecheck/build/
  test/package/checksum/smoke/upload/create-release steps, and the documented
  `needs: [release]` `cask` job boundary for 8.2 — and nothing under
  `.github/workflows/` is changed by the run.
- In the running app, the settings About section shows the version reported by
  `app.getVersion()`.
- CI green on the merge request branch.
