# PRD 6.2 — Downloads

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 3.4
(`prds/done/3.4-sqlite-persistence.md`) merged: state persists in a SQLite
database under `userData` with a `meta` singleton row (`id=0`), a `migrate()`
runner keyed on the schema version, and a `writeState`/`readState` pair that
covers profiles, spaces, and tabs only. It also builds on PRD 4.4
(`prds/done/4.4-command-mode.md`): the command bar has registry-driven modes,
and `bar.open-commands` is the precedent for a command that opens the bar in a
mode and leaves it open.

Epic 6 gives zeo the browsing chrome a daily driver needs. This PRD lands
downloads: files a page initiates are saved to the user's downloads directory
without a save dialog, tracked with live progress in a new command-bar mode
and a sidebar indicator, persisted across launches, and reachable by keyboard.
There is no download manager window; the command bar is the surface. Every
download record is owned by the main process and mirrored to the renderer over
the existing state broadcast, exactly as blocking counts are. History (PRD
6.1) is a separate feature with its own bar mode and suggestion kind; this PRD
adds a distinct `downloads` mode and a distinct `download` suggestion kind and
must not collide with them.

## Deliverables

### 1. Downloads state (core)

- New module `packages/core/src/downloads.ts`, pure TypeScript with no
  Electron import (the "no Electron" lint rule on `packages/core` stays as
  today). It exports the record and the reducers below and is unit-tested
  under plain Vitest.
- The `Download` record:

  ```ts
  interface Download {
    id: string;
    url: string;
    filename: string;
    path: string;
    totalBytes: number;
    receivedBytes: number;
    state:
      | "progressing"
      | "paused"
      | "completed"
      | "cancelled"
      | "interrupted";
    startedAt: number;
    completedAt: number | null;
    spaceId: string | null;
  }
  interface DownloadsState {
    items: Download[];
  }
  ```

  `totalBytes` is `0` when the origin sent no length; `receivedBytes` never
  exceeds `totalBytes` once `totalBytes` is known. `completedAt` is non-null
  exactly when `state` is one of the three finished states below.
- A download is **finished** when its `state` is `completed`, `cancelled`, or
  `interrupted`, and **active** when it is `progressing` or `paused`. These
  two terms are used by the reducers, the commands, and the sidebar below.
- `items` is ordered newest first by `startedAt` (ties broken by `id`) and
  capped at 100 entries in memory: when an insert would push the count past
  100, the oldest entry is dropped.
- Pure reducers, each returning a new `DownloadsState` and never mutating its
  input:
  - `upsertDownload(state, download)`: if an item with the same `id` exists,
    replace it in place (its position is recomputed from `startedAt`, which is
    immutable after insert, so an update never reorders); otherwise insert it
    at the newest-first position and drop the oldest if the cap is exceeded.
  - `removeDownload(state, id)`: drop the item with that `id`; a missing `id`
    is a no-op returning an equal state.
  - `clearFinishedDownloads(state)`: drop every finished item and keep every
    active one, order preserved; a state with no finished item is returned
    unchanged.
- Pure `uniqueFilename(name, exists)` where `exists: (candidate: string) =>
  boolean`. It returns `name` when `exists(name)` is false; otherwise it
  splits `name` into a stem and an extension at the last dot that is not the
  first character (so `.gitignore` has an empty extension and `archive.tar.gz`
  splits at the final dot only), and returns the first `"<stem> (n)<ext>"`
  with `n` counting up from `1` for which `exists` is false. A name with no
  dot, or a leading-dot name, keeps its whole value as the stem and an empty
  extension, yielding `"name (1)"`. The function performs no I/O; the caller
  supplies `exists`.
- `TabsState` (`packages/core/src/ipc.ts`) gains `downloads: DownloadsState`,
  placed beside the existing `blocking: BlockingState`. Like blocking, it
  rides the existing `stateChange` broadcast; no separate update channel.
- Unit tests: `upsertDownload` inserts newest first, updates in place without
  reordering, and enforces the 100 cap by dropping the oldest; `removeDownload`
  drops a match and no-ops on a miss; `clearFinishedDownloads` keeps active and
  drops finished; `uniqueFilename` returns the name when free, produces
  `report (1).bin` on the first clash and `report (2).bin` on the next, splits
  `archive.tar.gz` to `archive.tar (1).gz`, and treats `.gitignore` and a
  dotless `README` as an empty extension.

### 2. Persistence (`apps/desktop/src/main/db.ts`)

- `SCHEMA_VERSION` in `packages/core/src/persistence.ts` rises to **5**. Open
  PRDs 5.2 (allowlist) and 6.1 (history) take versions 3 and 4; if PRD 6.2
  lands before either of those, it takes the next free version at rebase and
  the migration step below is renumbered to match.
- `DDL` gains a `downloads` table with one column per `Download` field
  (`id` primary key; `state` stored as its string; `completedAt` and
  `spaceId` nullable; byte counts and timestamps as integers).
- One migration step `MIGRATION_STEPS[5]`, keyed by the version it produces
  (matching the existing convention where step `2` ends with
  `UPDATE meta SET schemaVersion = 2 WHERE id = 0`): it creates the
  `downloads` table and ends by setting `schemaVersion = 5`. `migrate()` runs
  it inside the existing single transaction, so a partially applied upgrade
  never commits. The migration-runner test covers the path up through 5.
- Row helpers, kept **out of `writeState`** (the full-state flush covers
  profiles, spaces, and tabs only, exactly as the blocking `enabled` setting
  is deliberately kept out of it): insert one row, update one row by `id`,
  delete one row by `id`, and list the last 100 rows ordered by
  `startedAt DESC` (ties by `id`). The list helper feeds the in-memory
  `DownloadsState` at startup. The insert helper also prunes the table to the
  newest 100 rows by `startedAt` (ties by `id`, matching the list helper and
  `upsertDownload`) after each insert, so the on-disk table stays
  bounded and matches the in-memory 100-cap: the same oldest entry that
  `upsertDownload` drops from memory is deleted from disk, and the two never
  diverge across a long-lived install.
- On launch, before the first window is created, any row whose stored `state`
  is `progressing` or `paused` is rewritten to `interrupted` with its
  `completedAt` set to the launch time, both on disk and in the loaded
  in-memory state: a download interrupted by a crash or quit is never shown as
  still running. This runs once per launch inside the same startup step that
  loads the rows.
- Unit tests (`apps/desktop`, `better-sqlite3` in-memory): migration to
  version 5 creates the table; insert/update/delete round-trip a row; list
  returns at most 100 rows newest first by `startedAt`; inserting a 101st row
  prunes the oldest so the table holds exactly 100; a `progressing` row present
  at load is returned as `interrupted`; download rows are untouched by a
  `writeState` call and a full-state flush does not delete them.

### 3. Main process — `will-download` (`apps/desktop/src/main/index.ts`)

- No `will-download` handling exists today. A single `will-download` handler
  is installed on every profile session `session.fromPartition("persist:" +
  profileId)`, registered exactly once per session, at the same three sites
  the content blocker is attached: the startup loop over all existing
  profiles, the `IPC.profilesCreate` handler, and `remapSpaceProfile`. A
  guard (a `Set` of sessions that already carry the handler) makes a repeated
  registration for one session a no-op, so a profile created later gets the
  handler exactly once and no session ever carries two.
- Save path: the downloads directory is `ZEO_DOWNLOADS_DIR` when
  `ZEO_E2E === "1"`, else `app.getPath("downloads")`. The final filename is
  `uniqueFilename(item.getFilename(), candidate =>` "a file named `candidate`
  already exists in the downloads directory or is the target of another
  in-flight download this launch"`)`, so two concurrent downloads of the same
  name resolve to distinct paths. The handler calls `item.setSavePath(...)`
  with the resolved absolute path, so Electron shows **no save dialog**. The
  reserved name is released when the download reaches a finished state.
- A `Download` record is created when `will-download` fires: `id` a fresh
  unique string, `url` from `item.getURL()`, `filename` and `path` the
  resolved values, `totalBytes` from `item.getTotalBytes()`, `receivedBytes`
  `0`, `state` `"progressing"`, `startedAt` the current time, `completedAt`
  `null`, and `spaceId` attributed as below. It is inserted through
  `upsertDownload` and persisted with the insert helper, and the row is
  broadcast.
- `spaceId` attribution: from the originating `webContents` via the existing
  `webContents.id -> tabId` reverse index (`webContentsToTab`), then the tab's
  space. A download whose `webContents` maps to no live tab (the sidebar or
  overlay renderer, or a tab already torn down) gets `spaceId: null`; it is
  never dropped.
- Progress: on the item's `updated` event the handler updates `receivedBytes`,
  and `state` between `"progressing"` and `"paused"` from
  `item.isPaused()`/the event state. Broadcasts are coalesced at most once per
  250 ms (the same window content-blocking counts use) and do **not** trigger
  the debounced full-state save; the row is persisted through the update
  helper at most once per second per download. The final in-memory value is
  always flushed on `done` regardless of the one-second throttle.
- Completion: on the item's `done` event the handler sets the terminal `state`
  from the event (`completed`, `cancelled`, or `interrupted`), sets
  `completedAt`, sets `receivedBytes` to the total received, persists the final
  row through the update helper, releases the reserved filename, and
  broadcasts. Ordering is: mutate in-memory state, persist, then broadcast, so
  the renderer never sees a state the database has not recorded.
- Failure paths: a `setSavePath` or filesystem error before the download
  starts leaves no record and no row; an item that errors mid-flight arrives
  at `done` with `interrupted` and is recorded like any other terminal state.

### 4. Bridge (`packages/core/src/ipc.ts`, preload, main)

- `DownloadsApi`, exposed as `window.zeo.downloads`:

  ```ts
  interface DownloadsApi {
    list(): Promise<Download[]>;
    cancel(id: string): Promise<void>;
    open(id: string): Promise<void>;
    reveal(id: string): Promise<void>;
    remove(id: string): Promise<void>;
    clearFinished(): Promise<void>;
  }
  interface ZeoApi {
    downloads: DownloadsApi;
  }
  ```

- Channel constants added to the `IPC` map, one per method, named
  `zeo:downloads:<verb-kebab>`: `downloadsList: "zeo:downloads:list"`,
  `downloadsCancel: "zeo:downloads:cancel"`,
  `downloadsOpen: "zeo:downloads:open"`,
  `downloadsReveal: "zeo:downloads:reveal"`,
  `downloadsRemove: "zeo:downloads:remove"`,
  `downloadsClearFinished: "zeo:downloads:clear-finished"`. Main, preload, and
  renderer use these constants only. Updates need no new channel:
  `DownloadsState` is part of `TabsState` and rides the existing `stateChange`
  broadcast.
- Contracts, each executed on the main thread:
  - `list()` returns the in-memory `items` (newest first, capped at 100).
  - `cancel(id)` cancels the underlying `DownloadItem` when the download is
    active; on a finished item (or an unknown `id`) it is a no-op that
    resolves without error. A successful cancel arrives at `done` with
    `cancelled` through the normal path.
  - `open(id)` resolves by opening the file with the OS handler only when the
    item is `completed` **and** the file still exists on disk; otherwise it
    rejects and changes nothing (an active, cancelled, or interrupted item, an
    unknown `id`, or a completed item whose file was since deleted or moved).
  - `reveal(id)` shows the item's `path` in Finder when the item exists;
    an unknown `id` rejects.
  - `remove(id)` removes the record from memory (`removeDownload`) and the
    database (delete helper) and broadcasts; it **never deletes the file on
    disk**. Removing an active download does not cancel it (use `cancel`
    first); an unknown `id` is a no-op.
  - `clearFinished()` removes every finished record from memory
    (`clearFinishedDownloads`) and the database and broadcasts; it never
    deletes any file and never touches an active download.

### 5. Commands (`packages/core/src/commands.ts`)

- Three new `CommandId`s, appended after the existing rows so registry order
  is unchanged for existing ids, all `menu: "view"`:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `downloads.open` | Show Downloads | `download`, `downloads`, `files`, `saved` | `CmdOrCtrl+Shift+J` | view |
  | `downloads.openFolder` | Open Downloads Folder | `download`, `downloads`, `folder`, `finder` | *(none)* | view |
  | `downloads.clearFinished` | Clear Finished Downloads | `clear`, `download`, `downloads`, `finished` | *(none)* | view |

- `downloads.open` opens the command bar in the new `downloads` mode and
  leaves it open (the `bar.open-commands` precedent), and toggles it closed
  when the bar is already open in `downloads` mode. `downloads.openFolder`
  reveals the downloads directory in Finder. Enablement:
  - `downloads.open` and `downloads.openFolder` are always enabled.
  - `downloads.clearFinished` is enabled only when at least one finished
    download exists.
- `CommandContext` gains a `hasFinishedDownload: boolean` input that
  `isCommandEnabled` reads for `downloads.clearFinished`; main computes it from
  the current `DownloadsState` whenever it builds the context, so the row
  appears and disappears as downloads finish or are cleared without retyping.
- All three are dispatched through `executeCommand`.
- Unit tests: the registry uniqueness and menu checks cover the three new ids;
  `downloads.open` and `downloads.openFolder` are in the always-enabled set;
  `downloads.clearFinished` is disabled when `hasFinishedDownload` is false and
  enabled when it is true.

### 6. Command bar `downloads` mode (core + ui + main)

- `CommandBarMode` gains `"downloads"` (today `"navigate" | "new-tab" |
  "commands"`). In `downloads` mode the bar opens with `initialText: ""`, the
  typed text is a filter only, `submit` is not a valid action, and there is no
  `navigate`/`search` row and no `command` row.
- The `Suggestion` union gains a `download` kind, distinct from PRD 6.1's
  `history` kind:

  ```ts
  { kind: "download"; id: string; filename: string; detail: string;
    state: Download["state"] }
  ```

  `detail` is a human-readable string: for an active download the received and
  total sizes and a percentage (or just the received size when the total is
  unknown), for a finished download the final size and a label for its state.
  Its `kindRank` slot is defined so `download` rows sort as a single block in
  `downloads` mode (no other kind appears in that mode, so the exact rank only
  needs to be stable and distinct from the existing kinds).
- `suggest(query, catalog, options)` with `options.mode === "downloads"`
  produces only `download` rows, built from the catalog's downloads. An empty
  or whitespace query lists every download newest first, uncapped up to the
  in-memory cap of 100; a non-empty query filters by a case-insensitive
  substring match on `filename` **or** `url`, order preserved (newest first),
  capped at `MAX_MATCHES`. `selectedIndex` starts at `0` when the list is
  non-empty and `-1` otherwise, matching the existing rule. No row 0.
- Key handling in `downloads` mode (renderer, over the bridge): Enter runs
  `open(id)` on the selected row (a no-op reject for a non-openable item leaves
  the bar open); `Cmd+Enter` runs `reveal(id)`; `Cmd+Backspace` runs
  `remove(id)` on the selected row and keeps the bar open, moving the selection
  to the next row (or `-1` when the list empties). Escape closes the bar as in
  the other modes.
- Live updates: while the bar is open in `downloads` mode,
  `refreshCommandState()` re-runs suggestions on each coalesced broadcast, so
  progress, size, and state on the visible rows update without retyping and a
  newly started download appears.
- Renderer: `apps/ui/src/CommandBar.tsx` draws the `download` row kind
  (filename, `detail`, state), and main-side `buildCatalog`,
  `recomputeSuggestions`, `acceptCommandBar`, and `performSuggestion` handle
  the new mode and kind. The bar placeholder in `downloads` mode reads
  `Filter downloads`.
- Unit tests (`suggest`): empty query lists all downloads newest first; a
  query matches on filename and on url; no `navigate`/`search`/`command`/`tab`
  row ever appears in `downloads` mode; the cap applies past `MAX_MATCHES`
  matches; `selectedIndex` follows the existing empty/non-empty rule.

### 7. Sidebar footer indicator (ui)

- `apps/ui/src/App.tsx` `sidebar__footer` gains an element with
  `data-testid="downloads-indicator"`, rendered only when `items` is
  non-empty. It shows the count of active downloads and their aggregate
  progress (the sum of `receivedBytes` over the sum of `totalBytes` across
  active downloads, shown as a percentage; when every active download has an
  unknown total it shows an indeterminate marker instead). When there are
  items but none are active it shows a completed/idle state with the item
  count. Clicking it runs `downloads.open` over the command bridge.
- New BEM-ish classes in the single stylesheet `apps/ui/src/App.css`,
  following the existing dark palette and class naming; no CSS tooling is
  added. The renderer forks no state: it reads `downloads` from the broadcast
  `TabsState` and dispatches through the bridge only.

### 8. Tests

- Unit: core reducers, `uniqueFilename`, and `suggest` `downloads` mode
  (`packages/core`); the migration, row helpers, interrupted-on-launch sweep,
  and `writeState` isolation (`apps/desktop`); the command registry additions.
- e2e (`e2e/tests/downloads.spec.ts`, Playwright Electron, offline): a
  loopback `http.createServer` on an ephemeral `127.0.0.1` port serves
  `/file.bin` with header `Content-Disposition: attachment;
  filename="report.bin"` and a 64 KiB body, following the fixture-server
  pattern of `e2e/tests/blocking.spec.ts`; the app launches with `ZEO_E2E=1`,
  `--user-data-dir`, and `ZEO_DOWNLOADS_DIR` pointing at a fresh temp
  directory. Reading state through `page.evaluate` on `window.zeo`:
  - Navigating a tab to `/file.bin` creates a download that reaches
    `completed`, and a file named `report.bin` exists in the temp directory
    with a size of 65536 bytes.
  - A second download of `/file.bin` in a new tab lands as `report (1).bin` on
    disk while `report.bin` is unchanged; `list()` shows both records newest
    first.
  - `remove(id)` on the first download drops it from `list()` while
    `report.bin` remains on disk.
  - Relaunching with the same `--user-data-dir` keeps the completed download in
    `list()`.
  - `downloads.open` shows the bar in `downloads` mode with the download row
    present; after deleting the completed file from disk, `open(id)` on that
    download rejects.
- CI stays offline-deterministic: the only server is the in-process loopback
  fixture; no test downloads from the network.

## Constraints

- No pause/resume UI, no save-as dialog, and no per-profile downloads
  directory in this PRD; all downloads for every profile land in the one
  downloads directory.
- `packages/core` stays Electron-free (lint-enforced): the record, reducers,
  `uniqueFilename`, and suggestion logic are pure; every Electron-facing part
  (`will-download`, `DownloadItem`, `shell.openPath`/`showItemInFolder`,
  `app.getPath`) lives in `apps/desktop`.
- SQL lives only in `apps/desktop/src/main/db.ts`; download rows live outside
  the `writeState` full-state flush.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged. CI must stay offline-deterministic.
- Version bump to 0.0.17 with a dated `CHANGELOG.md` section (Keep a
  Changelog). The 0.0.17 patch number and schema version 5 assume PRDs 5.2
  (allowlist) and 6.1 (history) merge first, taking 0.0.15/schema 3 and
  0.0.16/schema 4. If either of those PRDs has not merged when 6.2 rebases,
  the schema version and the patch number are renumbered to the next free
  values at rebase (this trigger matches the schema hedge in Deliverable 2).

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: downloading a file saves it to the downloads folder with
  no save dialog and shows live progress in the sidebar footer indicator;
  `Cmd+Shift+J` opens the command bar filtered to downloads, where Enter opens
  a completed file, `Cmd+Enter` reveals it in Finder, and `Cmd+Backspace`
  removes it from the list without deleting the file; a second download of the
  same name is saved as `name (1).ext`; downloads survive a relaunch, and one
  interrupted by quitting shows as interrupted rather than in progress.
- CI green on the merge request branch.
