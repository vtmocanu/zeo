# PRD 5.1 — Content blocking engine

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`. Requires PRD 4.3
(`prds/done/4.3-command-registry.md`) merged: epic 4 (command bar) is
complete and every profile maps to an Electron session partition
`persist:<profileId>`.

Epic 5 delivers built-in, filter-list based content blocking. This PRD lands
the engine and its wiring: the `packages/adblock` workspace the design doc
reserves, a blocker built from the standard uBlock Origin ad and tracking
lists through `@ghostery/adblocker-electron`, attached to every profile
session, with an on-disk engine cache so the app blocks from the first
request after a cold start and keeps working offline. A global on/off switch
and per-tab blocked-request counts are exposed over the bridge and shown in
the sidebar. Per-site allowlisting, the command-bar commands for it, and a
blocking settings surface arrive in PRD 5.2.

## Deliverables

### 1. `packages/adblock` workspace

- New workspace package `@zeo/adblock` (`packages/adblock`), TypeScript,
  built like `@zeo/core`, depending on `@ghostery/adblocker-electron` (pin
  the current stable major). It is the only package that imports the
  adblocker library; `packages/core` stays free of it and of Electron.
- Exports:

  ```ts
  interface BlockerSource {
    /** Loads the engine from cache or builds it from the lists; never throws. */
    load(): Promise<Blocker>;
  }
  interface Blocker {
    attach(session: Electron.Session): void;
    detach(session: Electron.Session): void;
    onBlocked(listener: (event: { tabWebContentsId: number; url: string }) => void): () => void;
    listVersion: string;
  }
  function createBlockerSource(options: {
    cacheFile: string;
    fetch: typeof fetch;
    lists?: string[];
  }): BlockerSource;
  function createBlockerFromFilters(filters: string): Blocker;
  ```

- `createBlockerSource.load()` order: read the serialized engine from
  `cacheFile` when it exists and deserializes with the installed library
  version; otherwise build from the lists (`lists` defaults to the library's
  prebuilt ads and tracking set) via `fetch`, serialize to `cacheFile`, and
  return. A fetch failure with no cache returns an engine built from the
  library's bundled fallback lists when it ships any, else an empty engine
  that blocks nothing, and reports which case happened through
  `listVersion` (`"cache"`, `"remote"`, `"bundled"`, `"none"` prefix plus a
  date or hash).
- `createBlockerFromFilters(text)` builds an engine from raw filter text
  synchronously; used by tests and by the e2e fixture.
- `attach` calls the library's session hook (`enableBlockingInSession`);
  `detach` its inverse. `onBlocked` adapts the library's `request-blocked`
  event to the tab's `webContents.id` and the blocked url.
- Unit tests (Vitest, no Electron): `createBlockerFromFilters` matches a
  request that a filter targets and passes one it does not; `load()` prefers
  the cache, falls back to the fetch, writes the cache after a fetch, and
  degrades to a no-op engine when both fail (fetch and filesystem injected).

### 2. Blocking state (core)

- `BlockingState` type in `packages/core`: `{ enabled: boolean; listVersion:
  string; blockedByTab: Record<string, number> }` where the key is the tab
  id and the value the count of blocked requests since the tab was created
  or last navigated to a new origin.
- `TabsState` gains `blocking: BlockingState`. A pure reducer
  `applyBlockedRequest(state, tabId)` and `resetBlockedCount(state, tabId)`
  with unit tests; counts reset on a top-level navigation to a different
  origin and are dropped when the tab is removed.
- Persisted setting: `enabled` is stored in the SQLite meta table (schema
  version 2 migration adds the key, default `true`); the migration runner
  test covers 1 to 2.
- Bridge: `BlockingApi { setEnabled(enabled: boolean): Promise<void>;
  state(): Promise<BlockingState> }` on `ZeoApi.blocking`, with channel
  constants. `setEnabled` attaches or detaches the blocker on every profile
  session, persists, and broadcasts.
- Command registry gains `blocking.toggle` ("Toggle Content Blocking",
  keywords `block`, `ads`, `tracking`, `adblock`, no accelerator, menu
  `view`), always enabled, dispatched through `executeCommand`.

### 3. Main process wiring

- On app ready, before the first window: create the blocker source with
  `cacheFile = app.getPath("userData") + "/adblock-engine.bin"` and the
  global `fetch`, start `load()`, and once it resolves attach the blocker to
  the session of every existing profile and to every profile created later
  (`profiles.create`, and the migration path that creates partitions). When
  the persisted `enabled` is false nothing is attached until `setEnabled(true)`.
- Tab views created before `load()` resolves simply attach late; the e2e
  waits on `listVersion` being non-empty before asserting.
- `onBlocked` maps the `webContents.id` to the owning tab id and applies
  `applyBlockedRequest`; broadcasts are coalesced (at most one per 250 ms)
  so a page loading many blocked resources does not flood the renderer.
- Test hook: when `ZEO_ADBLOCK_FILTERS` names a file, main uses
  `createBlockerFromFilters` on its contents instead of the network source,
  so e2e runs are deterministic and offline.
- Once a day (and on launch when the cache is older than a day), rebuild
  the engine from the lists in the background and swap it in on success;
  failures keep the current engine and log once.

### 4. Sidebar (ui)

- Each tab row shows a small shield glyph with the blocked count when the
  count is above zero; the glyph is dimmed when blocking is disabled. No
  other renderer changes; the toggle is reachable through the command bar
  and the View menu.

### 5. Tests

- Unit: package tests above; core reducers and migration.
- e2e (with `ZEO_ADBLOCK_FILTERS` pointing to a fixture list that blocks
  `||blocked.example^` and a local test page under `e2e/fixtures/` that
  requests `http://blocked.example/pixel.png` and `http://allowed.example/ok.png`
  through the existing e2e static server or a `file:` page):
  - The blocked request never reaches the page (the image's `error` event
    fires, or the resource entry is absent from `performance.getEntries()`),
    the allowed one loads, and the tab's `blockedByTab` count is 1.
  - `blocking.setEnabled(false)` then reload: both requests load and the
    count stays 0; `setEnabled(true)` restores blocking on the same session
    without relaunch.
  - Two spaces on distinct profiles both block (the second profile's session
    is attached).
  - Relaunch with `enabled` set to false persists the setting.
  - The `blocking.toggle` command row appears for the query `ads` and
    accepting it flips `enabled`.

## Constraints

- Only `packages/adblock` imports the adblocker library; only `apps/desktop`
  imports Electron; `packages/core` holds types, reducers, and the schema
  change.
- No per-site allowlist, no cosmetic-filter UI, no filter-list management
  UI in this PRD.
- Engine cache and list downloads live under `userData`; nothing is written
  into the repository or the app bundle at runtime.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged. CI must stay offline-deterministic: no test may
  depend on downloading filter lists.
- Version bump to 0.0.12 with a dated `CHANGELOG.md` section.

## Acceptance criteria

- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green.
- In the running app: ad-heavy sites show blocked counts on their sidebar
  rows within seconds of loading; toggling content blocking from the command
  bar stops and resumes blocking without relaunch; the second launch starts
  blocking immediately from the cached engine with no network.
- CI green on the merge request branch.
