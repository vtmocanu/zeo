# PRD 7.1 — Split view

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS. Design:
`docs/specs/2026-08-30-zeo-v1-design.md` (Goals: "Split view and a lightweight
quick-browse window"; milestone 7). `SCHEMA_VERSION` is `5` on main, in
`packages/core/src/persistence.ts`; all SQL lives in `apps/desktop/src/main/db.ts`
(`DDL`, `MIGRATION_STEPS` keyed by the version each step produces, `migrate()`, the
singleton `meta` row `id=0`).

This PRD claims an effective schema version `N`, defined as main's `SCHEMA_VERSION` at
rebase time PLUS 1. PRD 6.4 (zoom) is open on a branch not reachable from this clone and
also claims the next free version. If this PRD lands before 6.4, the implementer takes the
next free version at rebase so `N` ends up one more than main's value at that time. Under no
such collision `N` is `6`, and every version number this PRD writes as `6` — the
`MIGRATION_STEPS` step key, the `UPDATE meta SET schemaVersion = 6 WHERE id = 0` statement,
the migration-runner test's expected final version, and any schema-version acceptance
criterion — is that same `6` written as the illustrative, no-collision value of `N`; one
substitution of the actually-allocated `N` for `6` applies everywhere at once, so all stay
in lockstep.

Today the window shows exactly one tab's `WebContentsView` at a time:
`apps/desktop/src/main/index.ts` keeps a `views: Map<string, TrackedView>`
(`TrackedView = { view, spaceId }`, keyed by tab id) and `setActive(id)` makes exactly one
view visible and hides every other. The page region spans the whole content area right of
the 240px sidebar (`viewBounds()`; `SIDEBAR_WIDTH` in `packages/core/src/layout.ts`, which
also holds the pure `commandBarBounds`/`settingsBounds` geometry helpers). There is no
per-window layout state, no pane concept, and no divider anywhere in the tree.

This PRD adds split view: two tabs of the active space shown side by side in the one window,
separated by a draggable divider, backed by a per-window layout state (`single` | `split`)
that is a pure, Electron-free reducer in `packages/core`, persisted across relaunch, driven
from the keyboard and the command bar, and reflected in the sidebar. Split view pairs two
OPEN tabs of the ACTIVE space only (same profile/partition); there is no cross-space or
cross-profile split, and the quick-browse window named in milestone 7 is out of scope (a
later PRD). Feature epic 7, issue #87.

## Deliverables

### 1. Core split-view model (`packages/core/src/split-view.ts`)

New pure module, exported from the barrel (`packages/core/src/index.ts`), importing no
Electron. State:

```ts
export type PaneSide = "left" | "right";

export interface SingleLayout {
  readonly mode: "single";
}
export interface SplitLayout {
  readonly mode: "split";
  readonly left: string;   // open tab id of the active space
  readonly right: string;  // open tab id of the active space, distinct from `left`
  readonly ratio: number;  // left-pane fraction, clamped to [MIN_SPLIT_RATIO, MAX_SPLIT_RATIO]
  readonly focused: PaneSide;
}
export type WindowLayout = SingleLayout | SplitLayout;

export const SINGLE_LAYOUT: SingleLayout = { mode: "single" };
export const DEFAULT_SPLIT_RATIO = 0.5;
export const MIN_SPLIT_RATIO = 0.2;
export const MAX_SPLIT_RATIO = 0.8;
```

- `clampRatio(ratio: number): number` — returns `DEFAULT_SPLIT_RATIO` for any non-finite
  input, else clamps to `[MIN_SPLIT_RATIO, MAX_SPLIT_RATIO]`.

Pure reducers, each returning a NEW object (the input is never mutated, matching the
existing `packages/core` convention); all total over any input:

```ts
export function enterSplit(activeTabId: string, otherTabId: string): WindowLayout;
export function unsplit(layout: WindowLayout): WindowLayout;
export function swapPanes(layout: WindowLayout): WindowLayout;
export function setRatio(layout: WindowLayout, ratio: number): WindowLayout;
export function focusOtherPane(layout: WindowLayout): WindowLayout;
export function reconcileLayout(
  layout: WindowLayout,
  openTabIds: readonly string[],
  activeTabId: string | null,
): WindowLayout;
```

- `enterSplit(active, other)` → `{ mode:"split", left: active, right: other, ratio:
  DEFAULT_SPLIT_RATIO, focused:"left" }`; if `active === other` it returns `SINGLE_LAYOUT`
  (a total guard; main never calls it with equal ids).
- `unsplit(layout)` → `SINGLE_LAYOUT` (ignores its input).
- `swapPanes(layout)` — `single`: returns the input value unchanged. `split`: exchanges
  the two panes' tabs and flips `focused` so the SAME tab stays focused; `ratio` is
  preserved (the divider does not move — only the tabs swap): `{ mode:"split", left: right,
  right: left, ratio, focused: focused === "left" ? "right" : "left" }`.
- `setRatio(layout, ratio)` — `single`: unchanged. `split`: `{ ...layout, ratio:
  clampRatio(ratio) }`.
- `focusOtherPane(layout)` — `single`: unchanged. `split`: `{ ...layout, focused:
  focused === "left" ? "right" : "left" }`. Main applies this reducer ONLY together with
  `store.activate(focusedPaneTab(next))` (§6), so the §2 invariant (`store.activeTabId`
  equals the focused pane's tab) always holds; the reducer's focus flip is never used
  without that paired activate.
- `reconcileLayout(layout, openTabIds, activeTabId)` — the single lifecycle reducer:
  - `single` → `SINGLE_LAYOUT`.
  - `split`: if `left`/`right` are not both in `openTabIds`, or `left === right`, collapse
    to `SINGLE_LAYOUT`; else if `activeTabId === left` → `{ ...layout, focused:"left" }`;
    else if `activeTabId === right` → `{ ...layout, focused:"right" }`; else (the active tab
    is neither pane, or is `null`) collapse to `SINGLE_LAYOUT`.

Selectors:

```ts
export function focusedPaneTab(layout: WindowLayout): string | null; // split → focused pane's tab; single → null
export function paneOf(layout: WindowLayout, tabId: string): PaneSide | null; // pane holding tabId, or null
```

**Lifecycle reaction rules** (all realized by `reconcileLayout` plus the main wiring in §4,
so state is unit-testable without Electron):

| Event | Result |
|---|---|
| A paned tab is **closed** or **archived** | It leaves the active space's open-tab set → collapse to single; main activates the surviving pane's tab first (see §4), so the survivor — not an arbitrary MRU tab — becomes the single view. |
| A paned tab is **moved to another space** | No move-tab op exists today; when one lands it removes the tab from the active space's open tabs → same collapse, by construction. |
| The **active space changes** | The new space's open tabs exclude the old panes → collapse to single showing the new space's active tab. |
| A **non-pane** tab is activated while split | `activeTabId ∉ {left,right}` → collapse to single showing that tab. |
| A **pane** tab is activated | `focused` updates to that pane; stays split. |
| A paned tab's URL/title/favicon changes | Layout unaffected (reconcile keys on tab ids, not metadata). |

Unit tests: `clampRatio` (in-range, below min, above max, `NaN`/`Infinity` → default);
`enterSplit` (distinct → split with `left=active`/`focused="left"`/default ratio; equal →
single); `unsplit` (from split and from single); `swapPanes` (split swaps and flips focus,
preserves ratio; single unchanged); `setRatio` (clamps in split, no-op in single);
`focusOtherPane` (flips in split, no-op in single); `reconcileLayout` (both valid with
active=left/right/third; left-closed; right-closed; `left===right`; single-in); selectors
`focusedPaneTab`/`paneOf`; and that every reducer leaves its input object unmodified.

### 2. Pane focus and the active tab (semantics)

- Invariant: in `split` mode `store.activeTabId` equals the focused pane's tab; in `single`
  mode `store.activeTabId` is the sole visible tab exactly as today.
- `activateTab(id)` in main (the handler behind `tabs.activate` and command-bar tab picks)
  keeps its current behavior, then runs `reconcileLayout` (§4): activating a pane tab
  re-focuses that pane; activating a non-pane tab collapses split to single showing it.
- The focused pane is the one that receives keyboard focus (`webContents.focus()`); command
  enablement and `CommandContext.activeTab` (§7) read the focused pane's tab.

### 3. Geometry (`packages/core/src/layout.ts`)

Add, next to the existing pure geometry helpers:

```ts
export const DIVIDER_WIDTH = 6; // px, the draggable divider gutter between panes

export function splitPaneBounds(
  contentWidth: number,
  contentHeight: number,
  ratio: number,
): {
  left: { x: number; y: number; width: number; height: number };
  divider: { x: number; y: number; width: number; height: number };
  right: { x: number; y: number; width: number; height: number };
};
```

- `pageWidth = contentWidth - SIDEBAR_WIDTH`; `usable = pageWidth - DIVIDER_WIDTH`. When
  `usable <= 0` (a window too narrow to seat two panes and the divider) all three rects are
  all-zero, mirroring the defensive all-zero returns of `commandBarBounds`.
- Otherwise, with `r = clampRatio(ratio)` and `leftW = round(usable * r)`:
  - `left = { x: SIDEBAR_WIDTH, y: 0, width: leftW, height: contentHeight }`
  - `divider = { x: SIDEBAR_WIDTH + leftW, y: 0, width: DIVIDER_WIDTH, height: contentHeight }`
  - `right = { x: SIDEBAR_WIDTH + leftW + DIVIDER_WIDTH, y: 0, width: usable - leftW, height: contentHeight }`
- The three widths plus `DIVIDER_WIDTH` sum exactly to `pageWidth`, so no gap or overlap
  ever reaches the caller; `ratio` clamping guarantees both panes get a non-trivial share.

Unit tests: a `1280×800` window at `ratio 0.5` → `left.width === right.width === 517`,
`divider.x === 757`, and `left.width + DIVIDER_WIDTH + right.width === 1040`; an off-range
`ratio 0.9` is clamped to `0.8`; a window with `pageWidth <= DIVIDER_WIDTH` returns all-zero
rects; every rect's `height === contentHeight`.

### 4. Main process (`apps/desktop/src/main/index.ts`)

- Module state `let layout: WindowLayout = SINGLE_LAYOUT;` — the single source of truth,
  never forked to a renderer.
- `applyLayout()` — the one function that reconciles on-screen views to `layout` +
  `store.activeTabId`, replacing the direct `setActive` calls:
  - `single`: `ensureActiveView()`; for every tracked view `setVisible(tabId ===
    store.activeTabId)`, and the active view gets `setBounds(viewBounds())`; the divider view
    is hidden.
  - `split`: ensure both pane views exist (`createViewFor` for a missing one); compute
    `splitPaneBounds(contentWidth, contentHeight, layout.ratio)`; the left/right pane views
    `setBounds(...)` and `setVisible(true)`, every other tracked view `setVisible(false)`;
    the divider view is positioned at the divider rect and shown; the focused pane's view
    gets `webContents.focus()`. Each view op is guarded with an `isDestroyed()`/live-view
    check; a pane view destroyed between reconcile and its own call is skipped, not fatal.
  - Z-order re-raise after (re)adding pane/divider views keeps the invariant **tab views <
    divider view < settings view < command-bar overlay**, extending the existing
    settings-then-overlay re-add sequence to re-raise the divider first.
- Divider view: a dedicated `WebContentsView` loading `?view=divider` (default session, same
  preload as the sidebar/overlay), created lazily on first entering split and kept for the
  window's lifetime (visibility toggled), nulled on window close alongside `overlay`/
  `settingsView`.
- Divider drag protocol: whenever `ratio` or geometry changes, main sends the divider view a
  `DividerGeometry` event (§6) `{ ratio, dividableWidth }` where `dividableWidth =
  contentWidth - SIDEBAR_WIDTH - DIVIDER_WIDTH`. The divider renderer converts a pointer
  drag to an absolute ratio and calls `splitView.setRatio` (§6, §8). `setRatio` re-bounds
  both panes and the divider live and broadcasts; the persisted write is debounced so a drag
  writes once after it settles.
- Resize (`win.on("resize")`): call `applyLayout()` so both pane views and the divider
  re-bound (extending today's active-view-only re-bound), plus the existing settings/overlay
  handling; re-send `DividerGeometry`.
- Window re-create on macOS: `createWindow(false)` (from `app.on("activate")` when no window
  exists) reads the persisted layout (§5), runs it through `reconcileLayout` against the
  restored active space's open tabs, sets `layout`, then `applyLayout()` lazily materializes
  the pane views (mirroring today's `ensureActiveView` lazy restore). `views` is cleared on
  window close, so both pane views are rebuilt on demand exactly like the single active view.
- Reconcile triggers: after any store mutation that can invalidate a pane — `tabs.close` /
  `tabs.archive` / `tabs.remove` of a pane tab, and `spaces.activate`/`setActiveSpace` — main
  sets `layout = reconcileLayout(layout, store.list().map(t => t.id), store.activeTabId)`.
  For a pane-tab close/archive, main first `store.activate(<surviving pane tab>)` so the
  survivor becomes active before the collapse; `broadcast()` runs `reconcileLayout` as a
  final idempotent guard.
- `fullSnapshot()` attaches `layout` (§6) so every `stateChange` carries it, exactly as it
  carries `blocking`/`settings`.
- Failure paths: a `splitView` op on a destroyed/missing pane view is a no-op that changes
  no persisted state and broadcasts nothing beyond the reconcile that removes the dead pane;
  a persisted-write failure in `writeWindowLayout` (§5) is logged and does not corrupt the
  in-memory `layout` or the on-screen views.

### 5. Persistence (`apps/desktop/src/main/db.ts`)

- Effective schema version `N` (Context; `6` under no collision). The `MIGRATION_STEPS` step
  keyed at `N` adds five columns to the singleton `meta` row and bumps
  `meta.schemaVersion`; the SQL below assumes the no-collision `N = 6` illustratively, with
  `6` substituted for the actually-allocated `N`:

  ```sql
  ALTER TABLE meta ADD COLUMN layoutMode TEXT NOT NULL DEFAULT 'single';
  ALTER TABLE meta ADD COLUMN layoutLeftTabId TEXT;
  ALTER TABLE meta ADD COLUMN layoutRightTabId TEXT;
  ALTER TABLE meta ADD COLUMN layoutRatio REAL NOT NULL DEFAULT 0.5;
  ALTER TABLE meta ADD COLUMN layoutFocused TEXT NOT NULL DEFAULT 'left';
  UPDATE meta SET schemaVersion = 6 WHERE id = 0;
  ```

  The fresh `DDL` `meta` table gains the same five columns, so a brand-new database has them
  without migrating. The layout lives on `meta` — the single-window session row that already
  holds `activeSpaceId`/`enabled`/`searchEngine` — not a new table: this is "per window,
  under the existing session/space persistence" (there is exactly one window today; when a
  second window lands with the quick-browse PRD, layout moves to a per-window table).
- Helpers kept OUTSIDE `writeState`, the precedent `readBlockingEnabled`/
  `writeBlockingEnabled` and `readSearchEngine`/`writeSearchEngine` set:

  ```ts
  export function readWindowLayout(): WindowLayout;
  export function writeWindowLayout(layout: WindowLayout): void;
  ```

  `readWindowLayout()` reads the five columns and returns `SINGLE_LAYOUT` when `layoutMode`
  is not `'split'` or either tab id is `NULL`; otherwise `{ mode:"split", left, right, ratio:
  clampRatio(layoutRatio), focused: layoutFocused === "right" ? "right" : "left" }`. It does
  NOT validate against live tabs — main's `reconcileLayout` at restore (§4) does that.
  `writeWindowLayout(layout)` writes `layoutMode` and, for a split, the tab ids/ratio/focused;
  for single it writes `layoutMode='single'` and `layoutLeftTabId=layoutRightTabId=NULL`.
  Discrete layout changes persist immediately; ratio changes during a divider drag persist
  through a debounced `writeWindowLayout` (coalesced with the existing save debounce) so a
  drag writes once.
- Migration-runner and helper tests: `persistence.test.ts` asserts `SCHEMA_VERSION` is `N`
  and the `migrationAction` chain (`create(0)`, `migrate(1..N-1)`, `noop(N)`, `abort(N+1)`);
  `db.test.ts` covers `(N−1) → N` (a database at `N−1` gains the five layout columns with
  their defaults and `meta.schemaVersion` reads `N`, existing rows preserved), a fresh
  create at `N` (columns present), a no-op at `N` (a database already at `N` with non-default
  layout values is unchanged by `migrate`), and a `readWindowLayout`/`writeWindowLayout`
  round-trip (single; a split; and a stored split with a `NULL` tab id reading back as
  single) — validating the actually-allocated version, not a hard-coded `6`.

### 6. Bridge (`packages/core/src/ipc.ts` + preload)

- New types and api, added to `ZeoApi`:

  ```ts
  export interface DividerGeometry {
    ratio: number;
    dividableWidth: number;
  }
  export interface SplitViewApi {
    split(): Promise<void>;                 // split with active tab + MRU other open tab
    splitWith(tabId: string): Promise<void>;// split with the active tab + a chosen tab
    unsplit(): Promise<void>;
    swap(): Promise<void>;
    focusPane(pane: PaneSide): Promise<void>;
    focusOther(): Promise<void>;
    setRatio(ratio: number): Promise<void>;
    state(): Promise<WindowLayout>;
  }
  ```

  `ZeoApi` gains `splitView: SplitViewApi` and `onDividerLayout(listener: (geom:
  DividerGeometry) => void): () => void` (the same unsubscribe-closure shape as
  `onStateChange`/`onCommandBarChange`; delivered only to the divider view). `TabsState`
  gains `layout: WindowLayout`, riding the existing `IPC.stateChange` broadcast exactly as
  `BlockingState` does — no dedicated layout-change channel.
- Channel constants added to `IPC`, following the `zeo:<domain>:<verb-kebab>` naming every
  entry uses (the one broadcast channel `zeo:state-change` is the pre-existing exception):

  | constant | channel | request | response |
  |---|---|---|---|
  | `splitViewSplit` | `zeo:split-view:split` | none | `void` |
  | `splitViewSplitWith` | `zeo:split-view:split-with` | `string` | `void` |
  | `splitViewUnsplit` | `zeo:split-view:unsplit` | none | `void` |
  | `splitViewSwap` | `zeo:split-view:swap` | none | `void` |
  | `splitViewFocusPane` | `zeo:split-view:focus-pane` | `PaneSide` | `void` |
  | `splitViewFocusOther` | `zeo:split-view:focus-other` | none | `void` |
  | `splitViewSetRatio` | `zeo:split-view:set-ratio` | `number` | `void` |
  | `splitViewState` | `zeo:split-view:state` | none | `WindowLayout` |
  | `splitViewDividerLayout` | `zeo:split-view:divider-layout` | (main→divider event) | `DividerGeometry` |

- Failure and idempotency contracts (main-side handlers):
  - `split()` REJECTS when there is no active tab, the layout is already split, or the active
    space has fewer than 2 open tabs. On success it picks the most-recently-active OTHER open
    tab of the active space (max `lastActiveAt`, ties broken by ascending order in
    `store.list()` so the pick is fully deterministic, excluding the active tab), enters split
    with the active tab focused in the left pane, persists, `applyLayout`, broadcasts.
  - `splitWith(tabId)` REJECTS when there is no active tab, the layout is already split,
    `tabId` equals the active tab id, or `tabId` is not an OPEN tab of the ACTIVE space. On
    success it enters split (active tab left/focused, `tabId` right), persists, `applyLayout`,
    broadcasts.
  - `unsplit()` resolves as a no-op when already single; else collapses to single keeping the
    focused pane's tab active, persists, `applyLayout`, broadcasts.
  - `swap()` resolves as a no-op when single; else swaps panes, keeps the same tab active
    (now in the other pane), persists, `applyLayout`, broadcasts.
  - `focusPane(pane)` resolves as a no-op when single or when `pane` is already focused; else
    it sets `layout` to the pane-focused layout and calls `store.activate` on that pane's tab
    (so `store.activeTabId` tracks the focused pane, §2), then reconcile confirms `focused`,
    persists, `applyLayout`, broadcasts. `focusOther()` computes `focusOtherPane(layout)`
    (§1) and activates the newly-focused pane's tab via `focusedPaneTab` — it is the ONLY
    caller of the `focusOtherPane` reducer, always paired with that `store.activate` so the
    §2 invariant holds; it is a no-op when single.
  - `setRatio(ratio)` resolves as a no-op when single, or when `clampRatio(ratio)` equals the
    current ratio (no broadcast); else it updates the ratio, re-bounds both panes and the
    divider, sends `onDividerLayout`, broadcasts, and schedules the debounced persist.
  - `state()` returns the current `WindowLayout`.
- Preload (`apps/desktop/src/preload/index.ts`) exposes `window.zeo.splitView` and
  `window.zeo.onDividerLayout` via `contextBridge.exposeInMainWorld("zeo", api)`, typed
  `satisfies ZeoApi`. Main, preload, and both renderers use the `IPC` constants only — no
  inline channel strings.

### 8. Sidebar and divider UI (`apps/ui/`)

- `App.tsx` `TabRow`: when a tab is a pane (`paneOf(state.layout, tab.id) !== null`) the row
  gets `tab-item--paned`, `data-testid="tab-pane"`, and `data-pane="left"|"right"`; the
  focused pane's tab additionally gets `tab-item--pane-focused` (accent `#6b6bff`, the
  existing focus accent). The focused pane's tab is already the active tab
  (`aria-current`). Clicking a paned tab calls `window.zeo.splitView.focusPane(side)`;
  clicking a non-paned tab keeps today's `tabs.activate` (which, in split mode, collapses to
  single via main's reconcile). The pane/focus flags are derived from `state.layout` with the
  pure `paneOf` selector — no split logic in the component.
- Divider render mode: `apps/ui/src/main.tsx` gains a `view === "divider"` case mounting a
  new thin `apps/ui/src/Divider.tsx`. `Divider.tsx` subscribes to `window.zeo.onDividerLayout`
  for `{ ratio, dividableWidth }`; renders a full-height grab handle; on `pointerdown` it
  `setPointerCapture` and records `startX`/`startRatio`; on `pointermove` it computes
  `ratio = clampRatio(startRatio + (clientX - startX) / dividableWidth)`, calls
  `window.zeo.splitView.setRatio(ratio)`, and sets `globalThis.__zeoDivider = { ratio }` (the
  renderer-ack global for e2e, mirroring how `App.tsx` sets `__zeoDrag` in its pointermove
  handler); on `pointerup` it releases capture. No app logic beyond this.
- `CommandBar.tsx`: `"split"` mode shows the placeholder "Split with tab…"; rows reuse
  `data-kind="tab"` (e2e confirms the mode via `commandBar.state()`, so no new `data-mode`
  attribute is introduced).
- `App.css`: new BEM-ish classes `tab-item--paned`, `tab-item--pane-focused` (accent
  `#6b6bff`), and a divider handle style (thin bar, `col-resize` cursor, hover highlight),
  matching the existing dark palette; no new CSS tooling.

## Constraints

- `packages/core` stays Electron-free (lint-enforced): `split-view.ts` and the `layout.ts`
  geometry hold only pure functions and types; every `WebContentsView`/`BrowserWindow` call
  (pane views, the divider view, bounds, focus, z-order) lives in
  `apps/desktop/src/main/index.ts`.
- State lives in the main process; the sidebar and divider renderers subscribe (via
  `TabsState.layout` on `stateChange`, and `onDividerLayout`) and dispatch over the bridge;
  neither forks layout state.
- Split view is scoped to two OPEN tabs of the ACTIVE space (one profile); no cross-space or
  cross-profile split; the quick-browse window is out of scope.
- TypeScript strict mode; no `any` without a stated reason in review.
- Do not create or modify anything under `.github/workflows/`; root script names stay
  unchanged; CI stays offline-deterministic.
- Effective schema version `N` (Context; illustratively `6`) moves in lockstep across
  `packages/core/src/persistence.ts` (`SCHEMA_VERSION` + its test), `apps/desktop/src/main/db.ts`
  (the `MIGRATION_STEPS` step key, the `UPDATE meta SET schemaVersion = N` statement,
  and the fresh `DDL`), and the `persistence.test.ts`/`db.test.ts` version assertions.
- Version bump the root `package.json` patch to the next free version at rebase time
  (illustratively `0.0.18`; do not hard-code — take the next free patch above main's value
  at rebase) with a dated `CHANGELOG.md` section.
- `pnpm lint && pnpm typecheck && pnpm build && pnpm test && pnpm e2e` green (build before
  test — the `apps/desktop` tests import the built `@zeo/core`).
