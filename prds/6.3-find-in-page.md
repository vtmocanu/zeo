# PRD 6.3 — Find in page

## Context

zeo is a keyboard-first, workspace-centric open-source browser for macOS.
Design: `docs/specs/2026-08-30-zeo-v1-design.md`, milestone 6 (history,
downloads, find-in-page, zoom, settings). Feature #86, Epic 6 table stakes.
Requires PRD 4.4 (`prds/done/4.4-command-mode.md`) merged: the command
registry drives the menu and the command bar, every dispatch goes through
`executeCommand`, and the command-bar overlay is a single `WebContentsView`
whose state is pushed on `IPC.commandBarChange`.

This PRD adds in-page text search over the active tab. A find bar is anchored
top-right of the content area; typing highlights every match of the query in
the active tab and a counter reports the active match and the total. Enter and
`Cmd+G` cycle forward, Shift+Enter and `Cmd+Shift+G` backward, Escape closes
and returns focus to the page. Exactly one find session exists at a time,
bound to the active tab; there is no cross-tab search, no regex, and no
match-case toggle. Search is driven through Electron's `webContents.findInPage`
and its `found-in-page` events; the find bar reuses the command-bar overlay's
`WebContentsView` as a second surface rather than adding a window.

## Deliverables

### 1. Find reducers (core)

- New module `packages/core/src/page-search.ts` with the session type

  ```ts
  interface FindState {
    open: boolean;
    query: string;
    activeMatch: number;
    matchCount: number;
    tabId: string | null;
    activeRequestId: number | null;
  }
  ```

  `TabsState` (in `packages/core/src/ipc.ts`) gains `find: FindState`, so
  every find change rides the existing `stateChange` broadcast. `open` is
  whether the bar is showing; `query` is the committed search text;
  `activeMatch` is the 1-based ordinal of the highlighted match (0 when there
  is none); `matchCount` is the total number of matches; `tabId` is the tab
  the session is bound to (`null` when closed). One session exists at a time.
  `activeRequestId` is the Electron `found-in-page` request id of the single
  `findInPage` call whose results this session currently treats as
  authoritative, or `null` when none is outstanding (the session is closed or
  freshly opened, the query is empty or whitespace-only, or the bound tab has
  just navigated). It makes `applyFindResult` accept only that request's
  results and is never rendered. The documented shape is those six fields.
- Pure reducers, each returning a fresh `FindState`, never mutating input:
  - `openFind(state, tabId)` — when `state.open` is false, returns
    `{ open: true, query: "", activeMatch: 0, matchCount: 0, tabId,
    activeRequestId: null }`; when already open, returns `state` unchanged
    (re-opening is a focus/select concern handled in main, not a state
    change).
  - `setFindQuery(state, query)` — sets `query`. On a non-empty query it
    leaves `activeMatch`, `matchCount`, and `activeRequestId` unchanged (main
    issues the new search and records its id via `beginFindRequest` in the
    same handler). When `query` is empty or whitespace-only it also resets
    `activeMatch` and `matchCount` to 0 and `activeRequestId` to `null` (an
    empty query shows `0/0` and, in main, clears highlights with no request, so
    a delayed result for the cleared query is rejected).
  - `applyFindResult(state, requestId, activeMatchOrdinal, matches,
    finalUpdate)` — returns `state` unchanged when `state.open` is false, when
    `state.tabId` is `null`, or when `requestId !== state.activeRequestId` (any
    result that is not the outstanding request's; this also rejects every
    result while `activeRequestId` is `null`, since `null` never equals a
    numeric id). Otherwise returns `state` with
    `activeMatch = activeMatchOrdinal` and `matchCount = matches`, leaving
    `activeRequestId` unchanged. `finalUpdate` is accepted and documented:
    Electron emits one or more intermediate `found-in-page` events
    (`finalUpdate: false`) and a final one (`finalUpdate: true`) for a single
    request, all carrying counts and all matching that request's id; every one
    is applied and the last wins. Because the id is matched exactly against the
    one request main recorded via `beginFindRequest`, and that id is reset to
    `null` at every query, navigation, and session boundary (below), a delayed
    result from a superseded query, a pre-navigation page, or a closed session
    no longer matches and is dropped — regardless of how Electron numbers
    request ids across a `WebContents`.
  - `beginFindRequest(state, requestId)` — records the outstanding request:
    returns `state` with `activeRequestId` set to `requestId`. Returns `state`
    unchanged when `state.open` is false or `state.tabId` is `null`. Main calls
    it immediately after each `findInPage` (a fresh query, `next`, or
    `previous`) returns its id, so the new id supersedes any prior one and
    `applyFindResult` binds to it.
  - `clearFindResults(state)` — resets `activeMatch` and `matchCount` to 0 and
    `activeRequestId` to `null`, keeping `open`, `query`, and `tabId`. Main
    calls it when it clears highlights on the bound tab without issuing a
    replacement search (a navigation of the bound tab), so a straggler from
    before the navigation is rejected and the counter reads `0/0`.
  - `closeFind(state)` — returns `{ open: false, query: "", activeMatch: 0,
    matchCount: 0, tabId: null, activeRequestId: null }` regardless of prior
    state (idempotent).
- Unit tests (Vitest, no Electron): `openFind` opens an empty session bound to
  the tab and is a no-op when already open; `setFindQuery` stores the query,
  resets counts to 0 and `activeRequestId` to `null` on an empty/whitespace
  query, and leaves them untouched on a non-empty query; `beginFindRequest`
  records the outstanding id and supersedes a prior one; `applyFindResult`
  writes counts for a `requestId` equal to `activeRequestId`, drops any other
  id, and is a no-op when closed, when `tabId` is `null`, or when
  `activeRequestId` is `null`; every event of the outstanding request applies
  and the last wins. Delayed results are rejected: a result carrying the prior
  id after a query clear (`setFindQuery` empty), a result carrying the
  pre-navigation id after `clearFindResults`, and a result carrying the old
  session's id after `closeFind` then `openFind` on the same tab. `closeFind`
  resets every field.

### 2. Main process (`apps/desktop/src/main/index.ts`)

- Search runs against the active tab's `WebContentsView` with
  `webContents.findInPage(text, { findNext, forward, matchCase: false })`.
  Match-case is always false. A newly committed non-empty query issues
  `findInPage(text, { findNext: false, forward: true })` (a fresh search that
  selects the first match); `next` issues
  `findInPage(query, { findNext: true, forward: true })`; `previous` issues
  `findInPage(query, { findNext: true, forward: false })`. Each call's returned
  request id is recorded via `beginFindRequest`, in the same synchronous
  handler that applied `setFindQuery` and issued the `findInPage` and before it
  broadcasts, so results are routed to that request by exact id and no
  `found-in-page` event can arrive before the id is recorded.
- A `found-in-page` listener is registered per view in `createViewFor`,
  alongside the existing `did-navigate`, `did-navigate-in-page`,
  `page-title-updated`, and `did-finish-load` listeners. It applies a result
  only when find is open and `FindState.tabId` equals the view's tab id,
  through `applyFindResult(state.find, result.requestId,
  result.activeMatchOrdinal, result.matches, result.finalUpdate)`, then calls
  `broadcast()`. A result for any other view is ignored.
- `stopFindInPage("clearSelection")` is issued on the bound tab's view in each
  of these cases, and never leaves highlights behind: on `close`; on a tab
  switch to a different tab; on a navigation of the bound tab (`did-navigate`
  or `did-navigate-in-page`); and when the bound tab closes.
- On a navigation of the bound tab (`did-navigate` or `did-navigate-in-page`)
  the session stays open on the same tab, so alongside
  `stopFindInPage("clearSelection")` main applies `clearFindResults` and
  broadcasts: the counter reads `0/0`, `activeRequestId` becomes `null` so a
  pre-navigation straggler is rejected, and the query text stays in the bar
  with no automatic re-search until the user edits it or triggers next or
  previous.
- When the active tab changes while find is open, find closes: main runs
  `stopFindInPage("clearSelection")` on the previously bound view, applies
  `closeFind`, sets the overlay surface back to the command-bar surface (see
  §4), hides the overlay, and broadcasts. Find never follows the newly
  activated tab; the user reopens it there.
- An empty (or whitespace-only) query clears highlights with
  `stopFindInPage("clearSelection")` on the bound view and issues no
  `findInPage`; `FindState` shows `0/0` via `setFindQuery`.
- No new per-tab map is introduced: the `found-in-page` listener is owned by
  the view and torn down with it. When the bound tab is closed, removed,
  archived, or its space deleted — the same paths that clear
  `webContentsToTab` — main applies `closeFind` if that tab held the session,
  so a destroyed view never keeps an open session pointed at it.
- `refreshCommandState()` computes its `CommandContext` (see §5) from the
  current `FindState`, so `find.next` and `find.previous` enable and disable in
  the View menu and the open command bar as the session opens, gains a query,
  empties, and closes, without the user retyping.

### 3. Bridge (`packages/core/src/ipc.ts`, preload, main handlers)

- New bridge interface, added next to the existing APIs:

  ```ts
  interface FindApi {
    open(): Promise<void>;
    setQuery(text: string): Promise<void>;
    next(): Promise<void>;
    previous(): Promise<void>;
    close(): Promise<void>;
    state(): Promise<FindState>;
  }
  interface ZeoApi { find: FindApi }
  ```

- New channel constants in `IPC`, one per method, in the shared
  `zeo:<domain>:<verb-kebab>` form; the `find` domain is introduced by this
  PRD and used nowhere else:

  | constant | value | payload | response |
  |---|---|---|---|
  | `findOpen` | `zeo:find:open` | none | `void` |
  | `findSetQuery` | `zeo:find:set-query` | `string` | `void` |
  | `findNext` | `zeo:find:next` | none | `void` |
  | `findPrevious` | `zeo:find:previous` | none | `void` |
  | `findClose` | `zeo:find:close` | none | `void` |
  | `findState` | `zeo:find:state` | none | `FindState` |

  Updates need no channel of their own: `FindState` is part of `TabsState`, so
  every change is delivered on the existing `stateChange` broadcast. Main,
  preload, and renderer reference these constants only.
- Contract and rejection rules, executed on the main thread:
  - `open()` rejects when there is no active tab and changes nothing. With an
    active tab, when find is closed it opens a fresh session bound to that tab
    (`openFind`), closing the command bar first if it is open (§4). When find
    is already open, it re-focuses the find input and selects its text and
    leaves the session otherwise unchanged.
  - `setQuery(text)` requires the session open with an active tab, else
    rejects. It applies `setFindQuery`, debounced-issues the search as in §2
    (empty query clears highlights and issues no request), and broadcasts.
  - `next()` and `previous()` with an empty query are no-ops that resolve
    without issuing a request; with a non-empty query they issue the
    directional `findInPage`. A call with no active tab rejects.
  - `close()` is idempotent: it resolves whether or not a session is open. When
    open it runs `stopFindInPage("clearSelection")`, applies `closeFind`,
    restores the overlay to the command-bar surface, hides the overlay, and
    broadcasts.
  - `state()` returns the current `FindState`.
- The preload exposes `window.zeo.find` implementing `FindApi` through these
  constants only, kept in lockstep with `@zeo/core` via `satisfies ZeoApi`;
  it never exposes `ipcRenderer`.

### 4. Find bar surface (ui, `layout.ts`)

- `CommandBarState` (in `packages/core/src/command-bar.ts`) gains
  `surface: "bar" | "find"`, defaulting to `"bar"`. It is pushed on the
  existing `IPC.commandBarChange` channel and tells the one overlay
  `WebContentsView` which surface to render. The command bar and the find bar
  are mutually exclusive surfaces of that overlay; at most one is visible.
  - Opening the command bar (any of `navigate`, `new-tab`, `commands`) while
    find is open first closes find (`stopFindInPage("clearSelection")`,
    `closeFind`), sets `surface: "bar"`, and then opens the bar as today.
  - Opening find while the command bar is open first closes the command bar,
    sets `surface: "find"`, and opens the session.
  - Whichever surface is active owns the overlay's bounds, visibility, and
    focus for as long as it is shown.
- `broadcast()` additionally sends `IPC.stateChange` with the full snapshot to
  `overlay.webContents` (today it targets only the main window), so the find
  surface renders its counter and echoes its committed query from
  `TabsState.find`. The routing selector (`surface`) travels on
  `commandBarChange`; the find data (`query`, `activeMatch`, `matchCount`)
  travels on `stateChange`.
- `layout.ts` gains `findBarBounds(contentWidth)` and the constants
  `FIND_BAR_WIDTH = 360` and `FIND_BAR_HEIGHT = 44`, with a fixed
  `FIND_BAR_INSET = 12` and `FIND_BAR_TOP = 12`. Geometry, anchored top-right
  of the page region (the content to the right of the sidebar): `pageWidth =
  contentWidth - SIDEBAR_WIDTH`; `width = Math.max(0, Math.min(FIND_BAR_WIDTH,
  pageWidth - 2 * FIND_BAR_INSET))`; when `width === 0` return the all-zero
  rect `{ x: 0, y: 0, width: 0, height: 0 }`; otherwise `x = SIDEBAR_WIDTH +
  pageWidth - width - FIND_BAR_INSET`, `y = FIND_BAR_TOP`, `height =
  FIND_BAR_HEIGHT`. Height and `y` are fixed, so the signature takes only
  `contentWidth`. Main lays out the overlay with `findBarBounds` while the
  find surface is active and with `commandBarBounds` while the bar surface is.
- The overlay renderer (`apps/ui/src/main.tsx`, mounted for
  `?view=command-bar`) renders the find bar when `surface === "find"` and the
  command bar otherwise, subscribing to `onCommandBarChange` for the surface
  and command-bar state and to `onStateChange` for `find`. Find bar elements
  and test ids:
  - text input `data-testid="find-input"`;
  - counter `data-testid="find-count"` showing the string
    `` `${activeMatch}/${matchCount}` ``, i.e. `0/0` when `matchCount` is 0;
  - previous button `data-testid="find-previous"`;
  - next button `data-testid="find-next"`;
  - close button `data-testid="find-close"`.
  Keys handled in the input: Enter calls `find.next()`, Shift+Enter calls
  `find.previous()`, Escape calls `find.close()` (which refocuses the active
  tab view in main). Typing updates the query live through `find.setQuery`,
  debounced 50 ms. The three buttons call `find.previous`, `find.next`, and
  `find.close`. Styling lives in the single `apps/ui/src/App.css` with the
  existing BEM-ish classes and dark palette; no CSS tooling is added.

### 5. Commands (core, `menu: "view"`)

- `CommandId` gains `find.open`, `find.next`, and `find.previous`. Their
  registry rows are appended after `blocking.toggle`, so the order of every
  existing id is unchanged:

  | id | title | keywords | accelerator | menu |
  |---|---|---|---|---|
  | `find.open` | Find in Page | `find`, `search`, `page`, `text` | `CmdOrCtrl+F` | view |
  | `find.next` | Find Next | `find`, `next`, `search` | `CmdOrCtrl+G` | view |
  | `find.previous` | Find Previous | `find`, `previous`, `search` | `CmdOrCtrl+Shift+G` | view |

  `CmdOrCtrl+F`, `CmdOrCtrl+G`, and `CmdOrCtrl+Shift+G` are unused by any
  existing `COMMANDS` row, and are disjoint from the accelerators other open
  PRDs claim (`Cmd+,` settings 5.2, `Cmd+Y` history 6.1, `Cmd+Shift+J`
  downloads 6.2). No other open PRD claims the `find` command, channel, or
  test-id namespace.
- `CommandContext` gains `find: { open: boolean; hasQuery: boolean }`.
  `isCommandEnabled`: `find.open` is enabled when `context.activeTab !== null`
  (its handler selects the input text when find is already open);
  `find.next` and `find.previous` are enabled only when
  `context.find.open && context.find.hasQuery`. `menuEntries` and the View
  menu pick up the three rows with no other rule change (each has a distinct
  non-null accelerator, so none is grouped). `find.next` / `find.previous`
  dispatch the directional search through `executeCommand`; `find.open`
  toggles into the find surface as in §4.
- Unit tests: registry uniqueness and enablement checks cover the three ids;
  `find.open` is enabled with an active tab and disabled when
  `activeTab === null`; `find.next` and `find.previous` are enabled only when
  `find.open` is true and `find.hasQuery` is true, and disabled otherwise.

### 6. Tests

- Unit: the reducers in §1 and `findBarBounds` in §4 — the bar right-aligns
  within the page region at the top inset, insets on both sides, and collapses
  to the all-zero rect when `pageWidth - 2 * FIND_BAR_INSET <= 0`.
- e2e `e2e/tests/page-search.spec.ts`: a loopback `http.createServer` fixture
  on an ephemeral 127.0.0.1 port (the pattern from `e2e/tests/blocking.spec.ts`,
  `ZEO_E2E=1`, offline and deterministic) serving a page whose visible body
  contains the word `needle` exactly three times. Tests read state through
  `page.evaluate` on `window.zeo` and locate the bar by test id. Where a native
  accelerator would be needed, the command is dispatched through its menu item
  (walking `Menu.getApplicationMenu()` via `app.evaluate`) or through
  `window.zeo.commands.run` / `window.zeo.find`, since Playwright's synthetic
  key events do not fire Electron native menu accelerators. Steps and
  assertions:
  - Load the fixture page in a tab and run `find.open`; the find bar shows
    (`find-input` is present) and `window.zeo.find.state()` reports
    `open: true`.
  - Type `needle`; `find-count` reads `1/3`.
  - Trigger next (Enter / `find.next`); `find-count` reads `2/3`.
  - Trigger previous (Shift+Enter / `find.previous`); `find-count` reads back
    `1/3`.
  - Trigger close (Escape / `find.close`); the bar is hidden and
    `find.state().open` is false.
  - Reopen find, then activate a different tab; find closes
    (`find.state().open` is false).
  - Type a query that appears nowhere on the page; `find-count` reads `0/0`.

## Constraints

- Find state and reducers live in `packages/core`
  (`packages/core/src/page-search.ts`) and stay Electron-free; main owns
  `findInPage`, the `found-in-page` listener, `stopFindInPage`, and surface
  coordination; the overlay renderer adds the find surface; `layout.ts` adds
  `findBarBounds`.
- No cross-tab search, no regex, no match-case toggle in this PRD.
- No schema change: `FindState` is in-memory only and is never persisted, so
  `SCHEMA_VERSION` is untouched. Should this PRD nonetheless ever be paired
  with a schema change at rebase, it would take the next free version so
  `SCHEMA_VERSION` equals `main`'s value plus one — but none is expected here.
- Do not create or modify anything under `.github/workflows/`; root script
  names stay unchanged.
- Version bump to 0.0.18 with a dated `CHANGELOG.md` section.
